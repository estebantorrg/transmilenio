# TransMilenio Explorer — Technical Specification

Authoritative spec for TransMilenio Explorer transit intelligence platform, governs all architecture, security, compliance. Follow precisely.

---

## 1. Priorities (Strict Order)

1. **Certainty** — Don't assume, don't guess. Verify facts via upstream APIs or ArcGIS query interfaces.
2. **Performance** — Sub-5s initial map load. Sub-100ms route search. Sub-250ms route selection response.
3. **Stability** — Resilient catalog fallback. App opens even if live tracking or ArcGIS layers degrade.
4. **Accuracy & Freshness** — Combine official app data, ArcGIS feature geometry, local normalization.
5. **Simplicity** — Minimize code complexity. No duplicated logic. Direct, predictable data pipelines.
6. **User Experience** — Seamless map-based exploration. Dense, glanceable info. Smooth sidebar/map flows.

### 1.1 Engineering Rules (Non-Negotiable)

These rules govern every change. Violations block merge.

| Rule | Mandate |
|---|---|
| **R1 — Zero band-aid fixes** | Every defect fixed at root cause. No try/catch swallowing symptoms. No commented-out code, no `// TODO: revisit`, no `eslint-disable` silencing warnings. If proper fix too large for current change, open tracked issue. |
| **R2 — Clean, performant, maintainable** | Every change preserves: (a) **cleanliness** — no dead code, no duplicated logic; (b) **performance** — no blocking ops on Node event loop, optimized client-side MapLibre render; (c) **maintainability** — clean function signatures, clear naming, config documented in this spec. |
| **R3 — Conventional Commits, never auto-commit** | The agent NEVER runs `git commit` or `git push` unless the user explicitly asks for it in that request. Instead, for every change the agent produces a Conventional Commit message and includes it in its output for the user to use. When the user does ask to commit/push, default target is `main` unless a different branch, pull request, or release flow is requested. Commits are **title-only** — a single `type(scope): subject` line (≤72 chars), no body, with valid types (feat, fix, docs, style, refactor, perf, test, chore). **A push that includes any `mobile/` or `client/mobile/` change must ship with a `vX.Y.Z` tag push** (§1.1 apk-release-tag-rule, §5.2.1b) — `android-apk.yml` only fires on `push: tags: v*`, so pushing `main` alone silently leaves the APK unbuilt; bump the next patch/minor tag and push it in the same action, don't ask the user to remember it separately. |
| **R4 — APK build verification before reporting done** | Before telling the user an APK-affecting edit (`mobile/`, `client/mobile/`) is finished — even a "done editing" status short of a push — first verify it actually builds: `npm run bundle:mobile` (regenerates the APK-bundled data) then `npm --prefix client run build:mobile` at minimum; run the full `mobile/` Gradle build when the change touches native (Capacitor plugins, Android config, `mobile/android/`). A green typecheck is not a build — report completion only after the build step itself has been run and passed. |
| **R5 — Reachable by everyone, on both clients** | Neither client may block pinch zoom (`maximum-scale=1` / `user-scalable=no` is a WCAG 1.4.4 failure — MapLibre consumes its own gestures over the canvas, so the map is unaffected). Anything that behaves as a modal is one: the app's bottom sheets carry `role="dialog"` + `aria-modal`, trap Tab, close on Escape, restore focus on close and mark the shell `inert` so a screen reader cannot wander into the tab bar behind them (`ui/sheet.ts`). Tab strips are real ARIA tablists — `role="tab"`/`aria-selected`/`aria-controls`, panels `role="tabpanel"` + `aria-labelledby`, roving tabindex, ←/→/Home/End — on the app's bottom bar and the website's sidebar alike. |

## 2. Technology Stack & Architecture

### 2.1 Stack Definition

| Layer | Technology |
|---|---|
| **Frontend Client** | Vite 5 + TypeScript + MapLibre GL JS + three.js (3D bus layer, §5.2.6) |
| **Backend API** | Node.js + Express + TypeScript (compiled to ESModule) |
| **Data Sync / Exec** | tsx (TypeScript Execute) + PowerShell scripts |
| **Data / Cache** | Local JSON (`master_catalog.json`) + In-memory TTL caches |
| **Mobile Shell** | Capacitor 6 (Android, `mobile/`) bundling a dedicated app UI; native HTTP **direct to the official TransMi / public hosts** for all data, catalog + POI bundled in the APK — no web server of ours in the path (§5.2.1b) |

### 2.2 System Flow

```
Browser (MapLibre GL JS) → Express API (Node.js) → Master Catalog (Local JSON)
        │                          ↓             ↓
        │                    ArcGIS Server   Colombia Live Relay / public CO proxy
        └─ live (§5.2.1a): Live Bridge extension / CO relay direct → TransMi live API
```

### 2.3 Architecture Rules

* **Client Isolation**: Vite client is presentation layer only. Manages MapLibre layers, search states, timeline renderings. Requests `/api/*` from backend, never calls external transit APIs directly. **Exception — live tracking (§5.2):** when the Live Bridge extension is present, the client routes live-bus requests through it so they originate from the *user's* Colombian connection; the page itself still never `fetch`es the live API (browser CORS forbids it), and absent the extension it falls back to `/api/buses`.
* **Express Engine**: Backend Express API is data aggregator and query cache. Sole component reading master catalog JSON or calling external ArcGIS/TransMi endpoints.
* **Relay Separation**: Live vehicle positions routed through a separate Colombia-based relay for geographic API constraints. The main Express backend authorizes server→relay requests with a secret (§3.1); in browser-direct mode the relay instead trusts allow-listed origins via CORS (§5.2.2).

## 3. Security & Isolation

### 3.1 Relay Secret Verification
When `TRANSMILENIO_COLOMBIA_RELAY_SECRET` set in environment, main Express server signs/authorizes relay requests. Relay verifies secret by inspecting headers:
```text
Authorization: Bearer <secret>
x-relay-secret: <secret>
```

### 3.2 CORS & Origins
* **Production**: Express server allows origins matching `CLIENT_ORIGINS` env var (comma-separated).
* **Development**: Allows `localhost` and `127.0.0.1` by default.

### 3.3 Safe Data Processing
* **Text Escaping**: All external string data from official/ArcGIS APIs treated as untrusted. Escape before inserting into UI popups or DOM.
* **Zero PII Storage**: No user personal data, account info, or credentials stored. Geolocation permissions processed client-side only.

### 3.4 Rate Limiting & Flow Control
* Client enforces 15-second polling window on live bus tracking. **Polling is gated on the app being in front of the user** (`utils/appActive.ts`, shared by `layers/buses.ts` and the app's `LivePoller`): a backgrounded tab or a phone with the app behind another one kept issuing a Colombian round-trip every 15 s against a screen nobody could see. Returning to the foreground refreshes immediately rather than waiting out the timer.
* Network retries rate-limited via exponential backoff (2s, 4s, 8s, 16s) up to 4 retries for standard endpoints, **1 retry for ArcGIS-backed map layers** (they are fetched in parallel at boot and must not stall first paint — deeper recovery is §4.2's background pass), 0 retries for live bus requests.
* **Retryable = every `5xx` + every transport failure** (`isRetryable`, `client/src/services/api.ts`). Singling out `502/503/504` made a plain `500` terminal, so the ladder never ran for the failure it exists for; `4xx` stays non-retryable.

## 4. Error Handling & Resilience

### 4.1 Express API
* **No Silent Failures**: Unhandled exceptions are caught and logged server-side; clients never receive stack traces. This needs a **terminal error handler mounted last** (`apiErrorHandler`, `index.ts`) — Express walks the stack *forward* from where an error was raised, so the body-parser handler mounted before the routes cannot catch what a route throws, and without a final handler Express's default one writes the stack into the response body unless `NODE_ENV` happens to be `production`.
* **Structured Responses**: Routing/unknown-endpoint errors return `{ status: "error", message: string }`; data endpoints return `{ success: false, error: string }`.
* **Resilient Upstream Handling**: If ArcGIS/TransMi APIs timeout or error, API returns a structured HTTP fallback status — no crashes, no leaked stack traces. The ArcGIS-backed feature endpoints answer **`503` + `Retry-After`**, never `500`: the layer is momentarily unreachable, not broken, and the distinction is what keeps the client's backoff ladder alive (§3.4). All eight share one handler (`featureEndpoint`, `routes/api.ts`).

### 4.2 Vite Client (Graceful Degradation)
* **Outage Fallback**: Master catalog is critical. If loading fails, blocking UI overlay shown.
* **ArcGIS Failure — no layer is ever lost for a session.** Every ArcGIS-backed layer is fetched once, in parallel, at page open. A transient upstream failure there used to be permanent: the layer rendered empty and nothing retried, so a random default-on layer (trunk trazado, station pins) was simply missing until the user reloaded. Three mechanisms make that impossible:
  1. **Substitute immediately from the catalog.** Stations rebuild from the (required) master catalog (`catalogStationsToFeatures`, `stations.ts`) — and a station is drawn when the catalog files **service** at it, never by name: the hide-list that used to answer this (`ISLANDIA`, `LOSLAURELES`, `TIBANICAPRIMAVERA`, added while those were building sites) could not know when they opened, and kept the three newest estaciones off the map for the whole month they were running. The same rule now hides the nine that are **closed** — Tercer Milenio, Calle 19, Calle 45, Calle 63, Calle 76, Hospital and Temporal Calle 34 (Metro Línea 1 works on Caracas), Patio Bonito (remodelling) and SENA — because upstream files no service at any of them, which is the same fact. That the list *moves* is the point of not keeping one: on **2026-08-25** the Caracas works swapped a pair — Calle 72 reopened as `TM0002` carrying 18 services across three vagones, and Calle 76 (`TM0001`) took its place with none — and no code changed for it (§5.1.3, *variants upstream re-issues*). They stay in the register and in the station audit; they stop being offered to a rider as somewhere a bus stops, since a pin whose popup is empty is worse than no pin; trunk corridors rebuild from the official `trazado` of the routes that ride them, merged per trunk letter (`catalogCorridorsToFeatures`, `routes.ts`) — the ArcGIS centreline is survey geometry with no catalog twin, so the routes' own traces are the substitute. Troncal route lines already come from catalog `trazado` (ArcGIS only enriches them), so `/troncal/routes` failing is invisible. ArcGIS-only metadata (wifi, biciestación) is simply absent in that mode. TransMiCable has no catalog twin at all and can only be recovered.
  2. **Recover in the background** (`recoverLayer`, `main.ts`). Whatever opened degraded is retried after first paint on a widening schedule (4s, 12s, 30s, 60s) and applied in place through the layers' own update paths (`updateStationsLayer`, `updateTroncalCorridors`, `updateCableLayers`, `updateStopsLayer`). Every `add*Layer` is idempotent so a recovered payload re-enters the same pipeline instead of throwing on a live source.
  3. **Never lose the pins to a missing icon.** A symbol layer whose `icon-image` is unregistered renders *nothing*. `map.ts` registers the three pin icons up front **and** answers `styleimagemissing`, so a pin cannot be lost to ordering or a style reload.
  * Covered by `tests/arcgis-layers.spec.ts` (healthy boot renders every default layer; a simulated ArcGIS outage still draws corridors + stations and then recovers them).
  4. **A trunk the survey has not caught up with is patched, not left as a hole** (`corridorGapFeatures`, `routes.ts`). ArcGIS publishes 20 centrelines over 12 corridors and files a new one **late**: the Bosa–Tibanica stretch opened with its three estaciones filed under `TZ022`, a corridor `consulta_trazados_troncales` has never heard of, so the Troncales layer simply stopped mid-city with riders standing on a trunk it did not draw. The routes that ride it carry the geometry, so the gap is filled from their catalog `trazado` — and *only* the gap: a point within **80 m** of any surveyed centreline (hash-grid index, ~110 m cells) is already drawn, and `Z63` runs two thirds of its length up the Américas trunk. Three rules keep the patch honest, and each was measured against the live layers:
     * **Estaciones define it.** Only runs passing within 250 m of an estación that *no* surveyed corridor covers are kept. Without that test, every troncal route driving down an ordinary street qualified — 13 letters and ~50 km of mixed traffic, including the K86's airport run — in a layer whose whole meaning is "dedicated trunk". With it: **one** feature, 4.1 km, reaching Tibanica - Primavera (32 m), Islandia (129 m) and Los Laureles (239 m), and stopping 3.5 km short of Banderas.
     * **The unsurveyed letter names it.** Both directions reach those stations under different letters (`F63` and `Z63`); drawing both lays Américas red over the amber and makes a brand-new trunk read as an extension of one it never touches. The letter with no surveyed corridor of its own wins — it is new for the same reason the corridor is — so the stretch draws as **Z, `#EAB308`**.
     * **A run that starts and ends inside the survey and reaches no new station is dropped** — that is the route stepping onto a service road for a block, and it would be drawn on top of the line it just left.
     * **Both ends walk on into the covered trace until the patch is within 20 m of the surveyed centreline** (`CORRIDOR_JOIN_M`, capped at 600 m of chase so a terminus is not pursued). Ending at the last uncovered vertex leaves the stretch between the two lines drawn by nobody: the coverage test fires up to ~165 m out from a corridor vertex, and one vertex step on the light catalog's geometry is 700 m. The test is **point-to-segment**, not point-to-vertex (`metersToSegment`) — the surveyed centrelines are sparse where they run straight, so a point sitting *on* the corridor can be 200 m from its nearest vertex, and a vertex test would keep walking along a corridor it had already reached. Measured at the junction with Américas: the tip lands **0.5 m** from the centreline on the full trace, 3.0 m on the light one. They share a colour and a casing, so the overlap is invisible; the break was not.
     * **Drawn at catalog resolution, then settled onto the road** (`refineCorridorPatch`, `main.ts`). The light catalog caps a variant at 320 points and Z63 arrives with **53** — enough to cut the corner off a 700 m straight. The deep route payload has **374**, so the patch is redrawn from it (`getRouteDetail` for the source códigos only) *after* first paint: 154 points, widest vertex spacing 202 m instead of 698. Boot never waits on it, and a failed refine leaves the coarse patch — a corridor slightly off the kerb rather than none (§4.2).
     The recovery pass re-applies the patch, or a recovered ArcGIS payload would silently drop it.
* **Live Outage**: If live tracking fails, route detail panel continues displaying static timeline stops. If a recent fix is cached (§5.2.5), the server serves it tagged `stale`/`asOf` and the client shows the last positions with a "datos de HH:MM" indicator rather than blanking the map.

### 4.3 Database & Catalog Writes
* **Atomic Writing**: `syncMasterCatalog()` writes to temp file (`master_catalog.json.tmp`), atomic rename once successful.
* **Read Continuity**: During catalog sync, Express backend serves previous catalog from memory. In-memory catalog replaced only after atomic write finishes.

## 5. Core Features & Data Flow

### 5.1 Catalog Sync & TransMi API

#### 5.1.1 Catalog Loader Endpoint
* **Base URL**: `https://api.buscador-rutas.transmilenio.gov.co/loader.php`
* **Sync Client File**: `server/src/services/tm_api.ts`
* **Required Headers**:
  ```text
  Accept-Encoding: gzip
  Connection: Keep-Alive
  Host: api.buscador-rutas.transmilenio.gov.co
  User-Agent: okhttp/4.12.0
  uuid: fd1be953-d85e-4c63-8c23-234f143f445d
  version: 2.9.5
  ```

#### 5.1.2 API Functions
* **Route Search**:
  `lServicio=Rutas & lTipo=api & lFuncion=searchRutaByTipo & tipo_ruta=TIPORUTA & search=<seed>`
  * Seed set: `["", "A".."Z", "0".."9"]`
* **Route Detail**:
  `lServicio=Rutas & lTipo=api & lFuncion=infoRuta & idRuta=<id> & nombre=<name> & codigo=<code>`
  * Extracts: `recorrido.data[]` (ordered stops), `0.color`, `0.horarios` (parsed into service windows, §5.6.2), `0.sistema`, `0.tipoServicio`, `0.trazado` (GeoJSON LineString/MultiLineString).

#### 5.1.3 Catalog Sync Algorithm
1. Search routes using complete seed set.
2. Filter to `TransMilenio` and `TransMiZonal` families.
3. Fetch detail payload (`infoRuta`) for each distinct route.
4. Normalize stop/station mappings under `stations.wagons`.
5. Write catalog atomically to `server/src/data/master_catalog.json`.
* **Sync Safeguards**:
  * Random delay 800ms–1500ms between calls.
  * Max retries: 3. Retry delay: 3000ms.
  * Stale catalog limit: 7 days.
  * **Merge policy — fresh wins, except on `trazado`.** `mergeCatalogs` treats the fresh fetch as authoritative for every field it returns and retains only what fresh *lacks* (routes, variants, station-wagon mappings), because the upstream listing drifts run to run and a partial fetch would otherwise delete real services. Geometry is the one field-level exception: `infoRuta` intermittently answers with **no `trazado` at all** for a route it previously traced — 66 variants lost a good trace that way in the 2026-08-17 sync (verified against the live endpoint: absent for `H641`/`A020`/`B27`, still served for `1`) — and a variant-level overwrite took the trace with it. A missing trace is never evidence that a route has no geometry (§1 Certainty), and since §5.6.3 the planner *charges ride distance along the trace*, so losing one silently degrades routing as well as drawing. An absent/empty fresh `trazado` therefore falls back to the previous one; every other field still takes the fresh value.
  * **Retention has a clock** (`seenAt` per variant; `expireUnseenVariants`). Every variant the fetch lists is stamped with the run's start, and a variant no sync has seen for **`TM_ROUTE_RETENTION_DAYS` = 21** is dropped. Without it, retention — which exists because one run's absence proves nothing — also kept routes TransMi genuinely retired, forever, and the id-keyed rename purge only catches a route that comes back under a new código. Three weeks covers three Sundays and three festivos (when Ciclovía services are listed) plus a missed sync. Two guards keep it honest: expiry runs **only after a healthy sync** (zero errors and ≥90% of the códigos the catalog already had — a short fetch is precisely what retention is for and must never read as a retirement), and an **unstamped variant is stamped, not judged**, so the first sync after this shipped starts every clock instead of emptying the catalog. Station-wagon mappings are reaped separately by `pruneUnservedStationRoutes` against each route's authoritative `recorrido`.
  * **Upstream facts this project overrides are data with evidence** (`data/recorrido_corrections.json`, `recorrido_corrections.ts`). The operator's data lags its own network, and three kinds of lag are not opinions but stale rows: a stop left on a recorrido after the service stopped making it, a código still listed after the route it named was retired, and a **variant upstream re-issues under a new id** while keeping its código. All three are corrected at the **edge of the sync**, so the catalog on disk records the network as it is run and nothing downstream knows there was a difference.
    * The case that opened this: when `A61` was extended down Av. Ciudad de Cali it started at Tibanica - Primavera, and upstream left the old cabecera attached — `Portal Américas` filed at `posicion` **0**, tied with the new head, while every other stop increases from Tibanica (541, 1695 … 21287). Published as-is it puts a parada on the route page no bus calls at and hands the planner a 4 km leg measured as zero. `Z61`, the same corridor in reverse, carries no such entry.
    * **`F61` is filed as retired** for a reason worth recording: upstream issued `Z61` under a **new id (5467)** instead of re-coding `F61`'s (1190), so the id-keyed rename purge cannot see it and retention would hold the código for its full 21-day window. An answered retirement short-circuits that clock — the sync refuses to re-index the código and `expireUnseenVariants` drops it at once.
    * **A variant re-issued under a new id is the mirror of `F61`, and the purge is blind to it** (`retiredVariants`, `isRetiredVariant`, `dropRetiredVariants`). The rename purge reads **id → código**, so it only sees a route that keeps its id and changes código. When Calle 76 closed on **2026-08-25** upstream did the opposite: it kept the códigos and issued new ids — `A60`'s `Calle 76` run became id `5711 Calle 72`, leaving `1187` delisted; `6` became `691`/`5709`, leaving `692`. Nothing in the fresh listing then mentions the old id at all, and three separate rules each decline to act on that: the purge sees no código change, the variant key is the route's *name* so `Calle 76` is retained as if it were a second service, and `pruneUnservedStationRoutes` reads that retained variant's own recorrido as the proof its platform tags are real. The closed station therefore kept **four** services — `A60`, `6` twice and `G52` — that no bus runs, for the full 21-day window. Filed by hand as `{codigo, id}`, they are refused by `mergeCatalogs` on the way in and dropped from the catalog already on disk by `npm run prune`, which is a two-second repair against a 70-minute re-sync. The evidence is what upstream itself answers when the delisted id is queried: `infoRuta` for `1187` returns `codigo A60, nombre "Calle 72"` ending at `TM0002` — the same route under its pre-closure name, which is positive evidence and not the absence retention exists to ignore. `G52` is the one filed on its **recorrido** instead: no successor in the listing and `{"STATUS":false}` from `infoRuta`, but a stop list that rides a station upstream now files zero service at, which is stale whether or not the código returns.
    * **Every entry is re-checked on each sync** (`reportUnusedCorrections`, called at the end of `syncMasterCatalog`). When upstream fixes itself the run logs `no longer needed`, naming the entry to delete; a correction that outlives its cause is the same stale fact it was filed to remove. Entries carry the evidence (`note`) that justified them, because a correction filed on a hunch is a second wrong answer (§1). A *variant* retirement is judged against the previous catalog rather than against the fetch — once the twin it names is gone it has nothing left to match, and keeping it would leave a permanent veto on a `(código, id)` pair upstream is free to re-use.
    * **The class is detected, the answer is not guessed** (`warnTiedChainage`). Any recorrido filing two stops at one metre while they sit more than 400 m apart is warned about on every sync — that is the shape of this bug, and opposite kerbs of one street legitimately share a chainage. Which of the two is the stale one is a question about the network, answered in the file, never inferred in code.
  * **The register being a step behind is said out loud** (`unregisteredServedStations` → `warnUnregisteredStations`, at boot and after every sync). Answering "is this an estación?" from a generated file (§5.5.6) has one silent failure: a station that opens without a TM code before `npm run sync:stations` runs is unknown to every surface, and since the map draws only stations the catalog files service at, the symptom is a *missing pin* rather than something visibly wrong. The check names them and the command to fix it.
  * **Memory**: a full sync briefly holds the previous + freshly-fetched catalogs at once; `mergeCatalogs` grafts the previous INTO the fresh catalog **in place** (no third ~220 MB copy). Boot **auto-sync is OFF by default** — it OOM-kills a small web instance and would overwrite the curated Git-LFS catalog with a partial fetch. Production serves the committed catalog read-only (§4.3); refresh it offline via `npm run sync` (its own process) and redeploy. Opt into boot auto-sync with `TM_ENABLE_AUTO_SYNC=1` only on a host with ≥1 GB headroom.
  * **Heap sizing**: the web process caps V8 old-space to fit its container (`node --max-old-space-size=460`, root `start`) so GC runs before the platform OOM-kills — never `2048` on a 512 MB instance. `GET /api/health` exposes `memory` (`rssMB`, `heapUsedMB`, …) for monitoring.

#### 5.1.4 Lightweight Catalog
`getCatalogLight()` formats condensed payload for browser transport:
* Compresses zonal stops to basic codes and color tags.
* Stamps each troncal station with `estacion: true` — **whether this node is an estación at all**, answered from the official register (`station_registry.ts`, `data/troncal_stations.json`, §5.5.6) rather than from the shape of its code. `/^TM\d+$/` was that test in nine places, and it is a proxy: TransMi opens stations before assigning them a TM code, so Tibanica - Primavera, Los Laureles and Islandia (catalog codes `90009`/`90010`/`90011`, opened on the still-unnamed `TZ022` corridor) arrived as real estaciones that every surface drew as zonal paraderos — cyan pin, no estación page, no station popup, no vagón plan, and a second unresolved pin from the ArcGIS layer beside each. Both clients read the stamp through **one** predicate (`isStationStopCode`, fed by `setCatalogIndexes` at catalog load), with the code shape kept as the fallback for the 140 stations that have one.
* Stamps each troncal station with `vagonLabels` — the vagón number printed on each platform's sign, where the plano plate count backs it (`printedVagonLabels`, §5.5.4). Derived from a server-side dataset the browser never receives, so both clients and the prerendered pages read one answer instead of deriving three.
* Stamps each troncal station with `corridor` — `{ nombre, letra }`, the troncal it physically sits on and that corridor's letter (`stationCorridor`, §5.5.6). Same reason: it is answered by the official station maps, not derivable from anything the browser holds, and it is what names and colours the estación page.
* Simplifies trace coordinate arrays (Ramer–Douglas–Peucker, so turns survive) to **320** coordinates per route variant.
  * The cap is not a drawing budget any more. Since §5.6.3 the planner *rides* the trace — it projects each route's stops onto it and charges the metres between them — so how coarse the trace arrives decides both what the map draws and how many legs get a real driven distance. Measured over the committed catalog: at 160 points the planner could use **91.3%** of ride legs and drew them with vertices a median 145 m apart; at 320 it is **93.1%** and 78 m, for **+0.28 MB gzipped** on a payload the service worker already caches (`master-catalog` is network-first, so the change lands on the next load without a cache bump). Past 320 the curve is flat — the untouched traces buy no further legs for +4.4 MB.

### 5.2 Live Tracking & Colombia Relay

#### 5.2.1 Target API Host
* **Base Host**: `https://tmsa-transmiapp-shvpc.uc.r.appspot.com`
* **Constraints (verified)**: The host is **CO-IP geofenced** (non-CO egress → `401`/`451`) and serves **no CORS** — `OPTIONS` preflight → `403 Invalid CORS request`, response carries no `Access-Control-Allow-Origin`. A normal page `fetch` therefore cannot read it; only `Appid` is a required request header (`User-Agent`/`uuid`/`version` are not).

#### 5.2.1a Client-Direct Bridge (preferred)
* Live requests are made from the **user's own browser** via the optional **Live Bridge** extension (`extension/`). Its background fetch is exempt from page CORS and egresses from the user's Colombian IP, satisfying both constraints with no server in the live path.
* Transport: private `window.postMessage` channel `tm-live-bridge/v1` (page ⇄ content script ⇄ background worker). Client module: `client/src/services/liveBridge.ts`; the background worker only ever contacts the live host with fixed request shapes (no page-supplied URLs). It also **caps the candidate list at 12** (`MAX_CANDIDATES`, mirroring the server's `LIVE_NAME_CANDIDATE_LIMIT`): candidates are fired in parallel, so the array length is a fan-out multiplier on the *user's own* connection and any script on a matched page can post a `fetch` message — the worker must not take the page's word for how many requests to make.
* **Fallback chain** (`client/src/services/api.ts` → `getLiveBuses`): native app HTTP (§5.2.1b) → Live Bridge extension → direct CO relay (`VITE_LIVE_RELAY_URL`, §5.2.2 browser-direct) → `/api/buses` (main server relay). Each tier degrades gracefully to the next (spec §4.2); absent both the extension and a configured relay, behavior is unchanged.

#### 5.2.1b Native Android App (`mobile/`)
* Capacitor 6 shell bundling a **dedicated app UI** ("TransMi Go", `client/mobile/`) — a ground-up bottom-tab front-end (**Inicio · Buscar · Planear · Mapa · Cerca · Saldo**) that must look nothing like the website but reuses ONLY the website's data/service layer via the `@shared` alias (→ `client/src`), so the two clients never drift (spec §1.1 R2). Built by `client`'s `build:mobile`/`dev:mobile` scripts (Vite `--config mobile/vite.config.ts`); `mobile/scripts/build-web.mjs` runs `build:mobile` → `mobile/www` (website `client/dist` untouched). Runtime-only Capacitor detection (`window.Capacitor`), so the web build gains no dependency.
* **No server of ours in the path** — the app is a native peer of the official TransMi app, not a client of our website. It talks to the official government / public hosts **directly** via native HTTP (`CapacitorHttp`, exempt from webview CORS, egressing from the phone's own Colombian IP), and reads the two payloads with no single official endpoint from **APK-bundled assets**. This is the mobile exception to §2.3 (the browser client still calls `/api/*`); `CLIENT_ORIGINS` needs no app entry because the app never calls our server. The switch is one branch in the shared `api.ts` (`isNativeLiveAvailable()` → `client/src/services/officialApi.ts`), so the two clients stay in sync (spec §1.1 R2).
* **Bundled offline data**: the master catalog and the offline-aggregated POI/demand datasets (recharge points §5.5.1, TransMiBici §5.3, station-demand §5.8) have no single official endpoint, so they ship **inside the APK** — generated from the committed server data by `npm run bundle:mobile` (`server/src/bundle_mobile_data.ts` → `client/mobile/src/generated/`, regenerated on every `mobile` build:web, gitignored). `data.ts` reads them from local assets (`?url`, served by Capacitor with no network), so boot is instant and fully offline; they refresh only on app update. The catalog uses the exact `getCatalogLight()` transform the API serves, so the two clients never drift (spec §1.1 R2).
* **Direct hosts** (native, gated by `isNativeLiveAvailable()` in `api.ts` → `officialApi.ts`): **ArcGIS** troncal/zonal layers → `gis.transmilenio.gov.co` (§5.3, same pagination as the server); **live tier 0** troncal/zonal buses → the live host (`CapacitorHttp`, same name-candidate loop as the extension worker); **arrivals** → `POST /paradero/buses`; **card ledger** → `POST /lectura_tarjeta` (§5.5.1a — the phone's CO IP satisfies the geofence natively, no proxy); **walking geometry** → public OSRM foot (§5.6); **address/place geocoding** → public Photon, Bogotá-bboxed (`officialApi.geocode`, the same instance and filtering the server's place tier uses, §5.5.1) — without it the app could only plan between catalog points, so a trip to a street address was impossible on the client whose riders are standing in the street. Outside CO the geofence rejects the live/card calls and they degrade exactly as the web tiers do.
* **Typefaces ship in the APK** (`client/public/fonts/*.woff2`, `@font-face` in `app.css`): the app is offline-first, so a render-blocking `fonts.googleapis.com` stylesheet was a hard network dependency in front of first paint that simply never resolved with no data. The website self-hosts the same Inter subset for the same reason plus one fewer third party (§5.5.2 static-asset caching applies).
* **Service worker**: not registered inside the app (main-entry guard) — assets ship in the APK, and the bundled catalog above replaces any need for SW caching (which would only risk stale catalogs).
* **Permissions**: `INTERNET`, `ACCESS_COARSE_LOCATION`/`ACCESS_FINE_LOCATION` (webview geolocation for "mi ubicación").
* **The GPS is never the only way to name a place.** Permission can be denied, a fix can fail indoors, and a rider often plans *from somewhere they are not* — so every location-dependent surface (Cerca, both planner endpoints) offers **"Elegir en el mapa"**: `MapController.pickPoint(signal)` + the Mapa view's prompt banner, cancellable from the banner or the hardware back key. **Every** locate button on **both** clients names *which* failure happened (denied / no fix / outside Bogotá) and appends its own recovery, never a bare "No se pudo ubicarte" — the classification is one shared function (`utils/locationError.ts` → `classifyLocationFailure`), not four inline `err.code === 1` chains that drift apart.
* **"Cerca de ti" means walkable, and says so when nothing is** (both clients, `NEARBY_RADIUS_METERS` = 3 km in `utils/geo.ts` — one constant, since a coarse fix used to present things kilometres away as "cerca de ti"). When the radius holds nothing, the empty state names the kind (`Sin recargas a menos de 3 km`), and — this is the useful part — names **the nearest match beyond it with its real distance and walking time**, one tap away (`Ver el más cercano`). "Sin resultados · prueba con otro tipo de punto" left the rider unable to tell an empty catalogue from a far-away one.
* **The planner is a tab, not a sheet** (`views/planner.ts` → `createPlannerView`, tab `planner`, sixth in the bottom bar). Planning is the app's headline job and it was a stacked bottom sheet: it covered the app, and both flows that need the map — "Elegir en el mapa" and "Ver en el mapa" — had to **destroy** it, so the sheet was rebuilt from a seed and everything not in that seed (the other endpoint, the options, the itineraries just computed) was gone. As a screen it is long-lived: the map is one tab away and back, and the trip survives it.
  * **Layout**: a trip card (both endpoints joined by a gutter rail, swap centred between them), the **Salida** card (§5.6.2), an **Opciones** disclosure that folds Horarios/Transporte/Preferencia behind a summary of what they are currently set to, a **sticky "Buscar ruta"** action, then the results. The action is `order: 99` + `position: sticky` — a sticky `bottom` only pins a box still ahead of you in flow — while the DOM keeps it before the results so it stays early in the tab order. `.screen-planner` deliberately carries a *small* bottom padding: a sticky inset resolves against the scrollport inset by the scroller's own padding, so the tab-bar-sized padding the other screens use would float the bar ~90 px up the screen.
  * **Recent trips** (`lib/storage.ts` → `getRecentTrips` / `pushRecentTrip`, 6 max, device-local, zero PII §3.3): a rider repeats two or three journeys, and re-typing both endpoints was the planner's real cost. Saved on every search — including one that found nothing, since the same trip at another hour may have an answer — keyed on the two coordinates so relabelled endpoints don't duplicate. Before the first trip exists, the same block explains the three ways to name a point (type / GPS / tap the map), two of which are icons a rider has no reason to try first.
  * **Entry points**: the Inicio "Planear" action and a place sheet's "Desde aquí" / "Hasta aquí" both go through `AppContext.openPlanner(seed?)` — navigate to the tab, then seed one endpoint. Seeding clears the previous answer (it is a new intent), never the other endpoint.
* **The planner draws its itinerary.** The app's planner produced text only — an itinerary you could read but never see, on a client built around a map. Each result card carries **"Ver en el mapa"**, rendered by the website's own `layers/journeyLayer` (per-leg colours, dashed walk legs, tunnel legs, boarding/alighting markers), lazy-loaded on first use; a drawn journey and a tracked route are mutually exclusive, and hardware back clears the journey first.
* **A failed boot offers a retry.** `loadCore` throwing (no cache + unreachable catalog) used to freeze the splash with no way out but force-quitting the app. The website's loading overlay gained the same button — and, because boot is gated on MapLibre's `load` event, which never fires while a tab is in the background (rAF is frozen there), it now explains that after 12 s instead of appearing hung.
* **Connectivity is stated once** (`ui/netBanner.ts`): browsing routes, stops and horarios works offline from the bundled data; live buses, arrivals and saldo do not. One banner beats each of those failing separately with a generic toast.

#### 5.2.2 Relay Setup
* Live tracking requires Colombia egress IP. Relay file: `server/src/colombia_live_relay.ts`. Recommended host: an always-on CO box or an **Oracle Cloud Always Free** VM in the **Bogotá** region, exposed over **HTTPS** (Tailscale Funnel / Cloudflare Tunnel — required, the app is https and mixed content is blocked).
* Relay checks egress country using `https://www.cloudflare.com/cdn-cgi/trace` (cached 30s).
* Egress `/health` responses: `200` (Colombia), `451` (outside CO), `503` (check error).
* **Browser-direct mode (preferred, PC + mobile, no install):** set `RELAY_CLIENT_ORIGINS` (comma-separated app origins). The relay serves CORS for those origins and the browser calls it straight (`VITE_LIVE_RELAY_URL` on the client). Allow-listed browser origins need no secret; the relay returns only public, CO-gated bus positions. The relay races the troncal name candidates itself, **in parallel** (§5.2.4) — a sequential loop there paid a round-trip, or the full 9 s timeout, per miss before reaching the matching name.
* **Never open by default.** An unconfigured relay — no `TRANSMILENIO_COLOMBIA_RELAY_SECRET` *and* no `RELAY_CLIENT_ORIGINS` — used to authorize **every** caller, i.e. a public deployment was an open proxy onto the geofenced live host from a Colombian IP. It now serves only `localhost` origins in that state (local dev) and warns at boot. A blanket `localhost` trust is also withdrawn as soon as the relay *is* configured: `Origin` is trivially forged by a non-browser caller, so `-H "Origin: http://localhost"` would otherwise skip the secret entirely.
* **Server-relay mode (fallback):** `TRANSMILENIO_COLOMBIA_RELAY_URL` + `TRANSMILENIO_COLOMBIA_RELAY_SECRET` — the main server signs and forwards (spec §3.1). The backend this was built against, the serverless OCI Function relay (§5.2.2a), is **dead and unrecoverable on a free account**, so this mode currently has no working backend: the tier 500s and the cascade falls through to the public proxy pool. The mode itself still works and would serve any CO-egress relay put behind that URL.

#### 5.2.2a OCI Function Relay (serverless CO egress — **DEAD since 2026-08-10, retained as build notes**)

> **Status: gone, and it cannot come back on a free account.** The Oracle free trial ended; **Functions and API Gateway are not Always Free**, so the application and gateway no longer exist. The gateway host still resolves and answers, so the tier does not fail cleanly — it returns **HTTP 500 on every call**, forever, and the cascade falls through to the public CO proxy pool (`source: "public-co-proxy"`). Measured 2026-08-11 against the live gateway: the dead tier costs **60–85 ms warm** (413 ms on a cold TLS handshake) per live request, i.e. ~1% of the ~8 s a live poll takes — so leaving `TRANSMILENIO_COLOMBIA_RELAY_URL` set is nearly free, and unsetting it is cleanliness rather than a latency win. Do not spend time "repairing" this tier; restoring it requires a **paid** OCI account. Everything below is accurate as build documentation and useless until then. The realistic $0 CO-egress tiers are the Live Bridge extension (§5.2.1a), the Android APK's native HTTP (§5.2.1b), and the public proxy pool (§5.2.5).

The reliable Colombia egress backing `TRANSMILENIO_COLOMBIA_RELAY_URL` is an **Oracle Cloud Always-Free Function** in the **Bogotá** region (`sa-bogota-1`), fronted by an **OCI API Gateway** — chosen over an always-on VM because the Always-Free A1.Flex compute pool in Bogotá is chronically capacity-exhausted (`Out of host capacity`), while Functions egress from a Colombian datacenter IP the live host accepts (verified with real bus data). It replaces the flaky free public proxy pool (§5.2.5) as the primary CO egress.

* **Egress path**: the Function runs in a **private subnet** whose only route out is a **NAT gateway**, so its egress IP is Colombian and satisfies the §5.2.1 geofence. The **API Gateway** (public subnet + internet gateway, NSG allowing `443`) is the sole public surface; gateway→Function is authorized by an IAM resource-principal policy.
* **Function** (`scripts/oci-func/func.js`, Node 20 FDK) — a **controlled forwarder, not an open proxy**. Both request shapes are `RELAY_SECRET`-gated and restricted to the fixed live host (§5.2.1) plus an **allowlisted path set** (`/buses`, `/location/ruta`, `/paradero/buses`, `/lectura_tarjeta`, `/puntos_recarga`, `/puntos_personalizacion`) so it cannot be turned into an SSRF pivot. A path is matched **exactly, or exactly plus a query string** — never as a bare `startsWith`, or `/buses` would also authorize `/buses_internal`. The two `puntos_*` entries are the **GET** POI catalogues (§5.5.1): they exist so the offline harvest has a CO egress without a Colombian connection, and callers must pass `method: 'GET'` since the forward shape defaults to `POST`:
  * `POST <gateway>/relay/buses` — buses convenience shape `{action:'zonal'|'troncal', ruta, Nombre}` → `{ruta, action, upstreamStatus, buses}`; backs the live-bus `co-relay` tier (§5.2.1a fallback chain).
  * `POST <gateway>/relay/forward` — generic `{path, method, body}` → `{upstreamStatus, payload}`. The caller inspects `upstreamStatus` (the Function returns HTTP 200 whenever the upstream was *reached*, so a service-window `400` is surfaced as data, not a transport error). The `/relay/buses` shape deliberately does **not** do that: it answers `502` on a non-200 upstream, because its caller (`requestLiveJson`) parses a 200 body as bus data and would read a service-window `400` as a *verified* empty result from a Colombian egress.
  * `extractBuses` must stay behaviourally identical to the other four payload unwrappers (server `normalizeLiveBusesPayload`, client `findBusPayloadArray`, extension `toBusArray`). It was missing their keyed-object fallbacks, so a payload every other tier handled came back empty through this one.
* **Auth**: server→gateway sends `Authorization: Bearer <TRANSMILENIO_COLOMBIA_RELAY_SECRET>`, verified against the Function's `RELAY_SECRET` config (§3.1). Absent the secret the Function refuses (`403`) — it is a *mandatory* gate, not an optional one, or the gateway URL alone is an open proxy. The comparison is constant-time (`crypto.timingSafeEqual`), never `===` on a secret.
* **Server client** (`server/src/services/co_relay.ts` → `relayForward`): **every CO-IP-geofenced endpoint prefers this relay ahead of the public proxy pool** — cascade **direct → CO relay → public CO proxy**: live buses (`fetchLiveBuses`), arrivals (`fetchArrivals`, §5.5.1), and card balance (`fetchCardBalance`, §5.5.1a). Card reads work 24/7; buses/arrivals need the live service window (below).
* **Live service window**: outside ~05:00–23:00 Bogotá the live host answers `400 {"detail":"Service Not Available"}` to *any* CO client (verified by direct in-country request that bypasses the relay), a few night routes aside. Empty overnight bus/arrival results are the upstream being closed, **not** a relay fault. **Both clients say so** (`services/liveWindow.ts` → `closedWindowNotice`, used by the website's live card and the app's live chip + Inicio status): an empty result inside the window reads "Sin buses"; the same empty result at 02:00 reads "Servicio cerrado · opera de 5:00 a.m. a 11:00 p.m.". Rendering the closed feed as a *verified* absence of buses on that route is a certainty violation (§1) — the window is a presentation-layer explanation only, it never gates the request (some night routes do run).
* **CI/CD** (`.github/workflows/deploy-relay.yml`): the maintainer's local Docker is unavailable, so the Function auto-deploys from **GitHub Actions** on any push touching `scripts/oci-func/**` — build the image (`scripts/oci-func/Dockerfile`, base pinned to `fnproject/node:20`; an untagged base is pre-ES2020 and crashes the Function on load → gateway `502`), push to OCIR, update the Function via the OCI CLI (image tagged with the commit SHA). A dedicated **least-privilege** OCI user (`transmi-ci`; group `transmi-ci`; policy `transmi-ci-deploy` = manage repos + functions-family) authenticates via repo secrets: `OCI_PRIVATE_KEY_B64` (base64 so the multi-line PEM survives paste intact), `OCI_USER_OCID`, `OCI_FINGERPRINT`, `OCI_TENANCY_OCID`, `OCIR_USERNAME`, `OCIR_TOKEN`, `OCIR_NAMESPACE`. No Cloud Shell in the loop; server/client changes still deploy via the normal host (e.g. Render), untouched by this workflow.
* **Config**: `TRANSMILENIO_COLOMBIA_RELAY_URL` = the gateway deployment base (`https://<gateway-host>.apigateway.sa-bogota-1.oci.customer-oci.com/relay`; the tiers append `/buses` or `/forward`); `TRANSMILENIO_COLOMBIA_RELAY_SECRET` = the shared Bearer, also set as the Function's `RELAY_SECRET`.

#### 5.2.2b Cold-start budget (first fix of a tracking session)
Steady-state polling is bounded by the 15 s window (§3.4); what the user *feels* is the **first** fix after selecting a route, and every serial step in front of it is dead time. The rule: nothing that can run in parallel with the live request may run before it.

* **Client — request starts at selection** (`prefetchLiveBuses`, `client/src/services/api.ts`): route selection fires the live request immediately, then does the full-trace fetch (`/troncal/route/:code`), the lazy `layers/buses` import and the map work *while it is in flight*. `getLiveBuses` shares an in-flight (or <5 s settled) request for the same route, so `startBusTracking`'s first poll consumes the prefetch instead of starting a second request. The share key includes the **name candidates**: a prefetch made before the detail loaded is only reused when the tracking layer asks for exactly the same candidate set (a missing candidate can be the matching one, §5.2.4). Wired in `main.ts` → `onRouteSelect` and `client/mobile/src/map/mapController.ts` → `showRoute`.
* **Client — bridge probe never blocks**: the live cascade reads Live Bridge availability from cache only (`isLiveBridgeReady`); the content script announces itself at `document_start`, so an installed bridge is already known. Probing on the hot path would have put the 600 ms ping timeout in front of every request made by users without the extension; the probe now runs in the background for the *next* poll.
* **Client — 3D assets preloaded**: the `buses` chunk (three.js) and the Draco-decoded `bus_lod.glb` are warmed once the map is up (`preloadBusModels`), instead of downloading only after the first fix has already arrived.
* **Server — doomed tiers are skipped**: a `401`/`451` from the live host is an egress-wide verdict, so it is memoised (`TM_DIRECT_GEOFENCE_MEMO_MS`, default 10 min) and the direct tier is skipped for live buses and arrivals until it expires — a success clears it immediately.
* **Server — candidate fan-out resolves on first hit**: `runLiveStrategy` settles the moment a candidate returns buses and aborts the stragglers. Waiting for every candidate to settle pinned each response to the slowest one (the live host answers between ~0.3 s and its 9 s timeout). A valid empty result still requires all candidates, since only a non-empty hit proves the name matched. The native app (`nativeLive.ts`) and the extension worker (`extension/background.js`) do the same instead of their old sequential loops.
* **Server — connections and egress kept warm**: keep-alive agents for the live host and the relay (`tm_api.ts`, `co_relay.ts`) remove a TLS handshake per poll, and `startLiveWarmup()` (`TM_LIVE_WARMUP_MS`, default 240 s, `0` disables) probes the CO relay — the OCI Function drops its container when idle (§5.2.2a) — so the first real poll hits a hot Function over an open socket.

#### 5.2.3 Endpoint Requests
* **Troncal**: `POST /buses` with body `{"ruta": "<code-e.g.-B75>", "Nombre": "<name>"}`.
  * Headers: `Appid: 9a2c3b48f0c24ae9bfba38e94f27c3ea` (only required one — §5.2.1), plus `User-Agent: okhttp/4.12.0`, `version: 2.9.5`, `uuid` sent by the server/proxy paths for parity. Browser-based paths (extension/relay-direct) send `Appid` + `Content-Type` only.
* **Zonal**: `POST /location/ruta?ruta=<route_code>` with empty body.

#### 5.2.4 Normalization & Polling
* Normalizes response keys (`data`, `buses`, `vehiculos`, `lat`/`lng`) into unified model.
* Polling triggered in 15s intervals. Overlapping requests avoided via `fetchInFlight` locks.
* **Name Candidates**: Backend tries destination/origin candidate strings for troncal **in parallel**, resolving on the first **non-empty** hit and aborting the rest (a wrong name returns empty, not an error); falls through only when every candidate's transport throws. Every client-side transport (native, extension) races them the same way — see §5.2.2b.
* **Direction filter (client)**: The live API returns **both directions** of a route whenever the requested `Nombre` doesn't exactly match a destination — common for rutas duales/fáciles (number-only codes) whose catalog name differs from the API `destino_limpio` (e.g. "Portal El Dorado" vs "Portal Eldorado"). `buses.ts` → `filterBusesByDirection` keeps only buses whose `destino_limpio` loosely matches the **selected trip's** destination(s), so the opposite trip is not shown. Falls back to all buses if nothing matches (never blanks the map).

#### 5.2.5 Public CO Proxy Resilience (no card / host / install)
When no CO egress is otherwise available, set `TRANSMILENIO_ALLOW_PUBLIC_CO_PROXY=1` and the main server reaches the live API through free public Colombian proxies. Hardened for the inherent flakiness of free proxies:
* **Pool** (`proxy_manager.ts`): scrapes multiple sources (Geonode CO pages, ProxyScrape CO, proxy-list.download CO, + a bounded global top-up). Every candidate is verified against the live API — the **geofence is the filter** (only CO exits return coordinates). Verified proxies are scored by success rate, latency, and recency; the pool is kept warm (10-min full refresh + 90-s top-up below `TARGET_POOL_SIZE`) and failing proxies are evicted.
* **Race**: each live request fires the best `CO_PROXY_RACE_WIDTH` (default 5) proxies in parallel and takes the fastest valid response; slower in-flight proxies are aborted. Per-proxy timeout `LIVE_PROXY_TIMEOUT_MS` (default 14 s; observed proxies 3–14 s).
  * **Do not tune these knobs — measured, and it got worse.** `CO_PROXY_RACE_WIDTH=8` + `LIVE_PROXY_TIMEOUT_MS=8000` + `CO_PROXY_MAX_WAVES=2` — the intuitive "race wider, give up sooner" setting — moved success **94% → 89%** and p50 **4.6 s → 7.2 s**, and was reverted. A wider race burns the good proxies on one request and a shorter timeout discards the ones that were about to answer. The pool's run-to-run variance is larger than any knob's effect, so a probe run that looks like an improvement is usually noise: hold the defaults unless a change is backed by repeated runs on the same proxy snapshot.
* **Wave fallback**: when an entire wave dies (every raced proxy reset/timed out — routine for free proxies), the request falls through to the next-best, non-overlapping wave instead of failing, up to `CO_PROXY_MAX_WAVES` (default 3) waves or until the overall live budget (`LIVE_OVERALL_TIMEOUT_MS`, 14.5 s) is hit. A valid empty result (a working proxy, no buses on that name) resolves immediately and consumes no further waves.
* **Last-known cache** (`/api/buses`): the most recent non-empty fix per `routeType:ruta` is cached (10-min TTL, **bounded to 120 entries**, oldest fix evicted first). If every upstream path is momentarily down, the server serves it tagged `stale: true` + `asOf` instead of a blank map; the client renders it with a "datos de HH:MM" indicator (spec §4.2). The bound is load-bearing: a TTL is only consulted on *read*, so an entry for a route nobody opens again is never freed — with ~1000 route variants each holding a full bus array that is real resident memory on the 512 MB instance (§5.1.3).
* **The transport is untrusted.** A free proxy is a middlebox that can answer with an arbitrarily long body or a gzip bomb, so every upstream read goes through `services/upstream_body.ts` — one bounded reader (`MAX_UPSTREAM_BODY_BYTES`, 8 MB) covering the socket read (`res.destroy()` past the cap), the inflate (`zlib.gunzip`'s `maxOutputLength`) **and** the `error` listener every response stream needs (an aborted response with no listener is an unhandled `'error'` event, i.e. a process-level crash). Used by the live tiers, the catalog loader, the card read, the CO-relay client and the standalone relay; the OCI Function carries its own copy because it is a separate deployable.
* **The pool only dials routable addresses.** Candidate `ip:port` pairs come from third-party scraped lists and each becomes a CONNECT target, so loopback/private/link-local/CGNAT ranges and invalid octets are dropped (`isRoutableIp`) — a poisoned list must not make the server probe hosts inside its own network. Its maintenance timers are `unref`'d so importing the module never holds a CLI process open.
* **Observability**: `GET /api/health` exposes `proxyPool` (verified count, top proxies w/ latency) and `liveCacheEntries` when the fallback is enabled.
* **In practice the *only* server-side tier**: the cascade is still ordered direct → CO relay → public proxy, but since 2026-08-10 the relay above it always 500s (§5.2.2a), so every server-side live request the app serves is answered here. Measured on the pool as it stands: **94% success, p50 ~4.6–6.0 s, p90 ~10–13 s** — availability is adequate, latency is the felt problem, and it is not tunable — see the bullet below.
* **Honest limitation**: free proxies are best-effort; live tracking through them is intermittent. Reliable CO egress comes from the serverless OCI relay (§5.2.2a), a CO device, or a per-user install (extension/native) — see §5.2.1a / §5.2.2 / §5.2.2a.

#### 5.2.6 3D Bus Models
Every live bus renders as a 3D model in a single MapLibre custom WebGL layer (three.js).
* **Asset**: source `buscar.glb` (Draco-compressed geometry + webp texture). `scripts/bake-bus-pivot.mjs` bakes the node translation so the pivot is the **exact bottom-center of the wheels** (world `centerX = 0`, `minY = 0`, `centerZ = 0` — never the front), emitting `client/public/models/bus.glb`. The Draco buffer is never decoded server-side; the mandatory POSITION `min/max` + node TRS give the bbox.
* **Renderer**: `client/src/layers/busModelLayer.ts` — a `CustomLayerInterface` (`type:'custom'`, `renderingMode:'3d'`) that places one clone per bus at its `MercatorCoordinate` (altitude 0 → wheels on ground). **One model family is used for all bus types** (troncal / zonal / alimentador).
* **LOD**: `bus_lod.glb` (also pivot-baked from `busscar_LOD.glb`) loads immediately and renders when zoomed out; the full `bus.glb` is **lazy-loaded** the first time the user zooms in past `LOD_ZOOM` and shown from then on at close range.
* **Motion**: positions tween from the previous fix to the new one across the poll interval (glide, no snapping). Heading uses the telemetry `angulo` (compass bearing; nose is +Z → `rotation.z = angulo`).
* **Opaque**: model materials forced opaque on load (`transparent=false`, `depthWrite=true`) so buses are never see-through; max texture anisotropy.
* **Declump**: buses sharing a spot are fanned out in a small ring (`declump()`) so a cluster doesn't render as one blob.
* **Precision**: rendered relative to a per-frame local origin (map centre) → no mercator float jitter while panning.
* **Pivot rule (non-negotiable)**: bottom-center of the wheels. Placement uses the pivot directly — no front offset.
* **Interaction**: click pixel-picks the nearest bus → info popup. The popup **follows its bus every frame** (`setFollow`) and its route badge is tinted with the route's own color (`getRouteAccentColor`), not a fixed red.
* **Tunables** (`busModelLayer.ts`): `MODEL_SCALE`, `SCALE_REF_ZOOM` + `MAX_ZOOM_BOOST` (stay visible zoomed out), `LOD_ZOOM`, `DECLUMP_RING`, `BASE_TILT` (glTF Y-up → mercator Z-up).
* **Dependency**: `three` (client). Draco decoder files copied to `client/public/draco/`.

### 5.3 ArcGIS FeatureServer Integration

#### 5.3.1 ArcGIS Query Specifications
* **Base URL**: `https://gis.transmilenio.gov.co/arcgis/rest/services`
* **Query Params**: `where=1=1`, `outFields=*`, `outSR=4326`, `f=json`, `returnGeometry=true`.
* Uses cursor pagination based on `exceededTransferLimit === true`.
* **Per-page retries** (`arcgis.ts`): a failed page is retried up to 3 times (600 ms, 1200 ms) before the query gives up, so one blip on one page of a multi-page layer cannot cost the whole layer. Failures ArcGIS attributes to the *caller* — HTTP `4xx`, or its `200`-with-`error.code` envelope in the 400s — are not retried. Exhaustion raises `ArcGISUnavailableError` → `503` (§4.1).
* **Server cache** (10-min TTL, `routes/api.ts`): concurrent first-hits share one in-flight query; on failure the last good payload keeps being served and the next upstream attempt is paced 30 s apart, so a down ArcGIS never puts the full retry budget in front of every request.
* **Boot prewarm**: the two default-on layers (`consulta_estaciones_troncales`, `consulta_trazados_troncales`, ~190 KB combined) are cached right after `listen` (`prewarmArcgisLayers`). The first visitor after a cold start would otherwise trigger five concurrent ArcGIS queries on a 0.1-CPU instance — the burst that made a random layer time out. Deliberately excludes the heavy layers so boot memory is untouched (§5.1.3).

#### 5.3.2 Queried Layers
This list is exactly what `queries` (`arcgis.ts`) implements — nothing aspirational. A layer we do not read does not belong here: `consulta_esquemas_estaciones` (vagón schemas), `consulta_conexiones_troncales` and `consultaEquivalenciaEstaciones` were listed for a long time with no consumer, and the wagon query in particular sat in `queries` unreferenced. Wagon assignments come from the catalog's `stations.wagons` (§5.1.3), not from ArcGIS.
* **Troncal**: `Troncal/consulta_rutas_troncales`, `consulta_estaciones_troncales`, `consulta_trazados_troncales`.
* **Zonal**: `Zonal/consulta_rutas_zonales`, `consulta_paraderos_zonales`, `consulta_paraderos_rutas`.
* **TransMiCable**: `ConsultaSubgerenciaPlanificacionSITP/Consulta_Planificacion_SITP` layers **11** (estaciones) and **14** (trazado); layer **12** backs the TransMiBici POI sync (§5.5.1).
* **Page cap**: cursor pagination stops at `MAX_PAGES` (60). A service that ignores `resultOffset` keeps answering `exceededTransferLimit: true` with the same page forever — an unbounded loop that fills the heap on the 512 MB instance (§5.1.3). The largest layer we read needs 22 pages.

### 5.4 Station & Zonal Stop Intelligence

#### 5.4.1 Station Resolver
Reconciles ArcGIS points with TransMi catalog stops.
* **Match Order**:
  1. Terminal platform clusters (merging fragments within 180m).
  2. Verified platform splits (`VERIFIED_SPLITS`, see below).
  3. Exact ID match.
  4. Name and distance proximity.
* **Verified platform splits**: Avenida Jiménez (`TM0013`) and Ricaurte (`TM0069`) are each physically **two separate stations** — a Caracas/NQS trunk platform and a Calle 13 platform. The official app files each pair under **one merged stop code**, but ArcGIS exposes each platform as its own point. `VERIFIED_SPLITS` (`stationCatalogResolver.ts`) splits the merged catalog stop back into its platforms **by wagon**, so both stations render distinctly with their own name and route set: Av. Jiménez → Caracas (`TM0013` wagons `A,B,C`, node `9110`) + CL 13 (wagons `D,E`, node `14003`); Ricaurte → NQS (`TM0069` wagons `A,B,C`, node `7111`) + CL 13 (wagons `D,E,F`, node `12003`). The two ArcGIS platform points are matched by node id / normalized name; wagon partitions are kept in sync with the catalog.
* **Both-direction route tags** (`groupCatalogRoutesByDirection`, `stations.ts`): A TransMilenio route serves a station in **both directions**, so each direction is shown as its own tag. Wagon route tags are grouped by **código + destination name** — so a ruta fácil like `3` shows `3 → Portal Tunal` AND `3 → Corferias` (both directions; data carries both as distinct ids/nombres), and lettered pairs `B72`/`H72` show as their two codes. Only genuine duplicates (same código **and** destination) collapse into one tag; the tooltip lists the destination(s). Wagons are left exactly as the catalog files them (no merging across platforms).
* **Audit**: Diagnostic output exposed via `window.__tmStationAudit`.

#### 5.4.2 Zonal Stop Resolver
Aggregates route tags from ArcGIS `consulta_paraderos_rutas` and catalog fallbacks. Deduplicates by normalized route code.

#### 5.4.1a Estación vs Paradero split (mobile)
The API serves the **light** catalog, whose `stations` map merges troncal estaciones and zonal paraderos and carries no `sistema`. The mobile app therefore classifies purely by CODE (`client/mobile/src/data.ts` → `catalogPointRecords`): `TM…`-coded nodes (~140) are estaciones (red), everything else is a paradero (~7400, cyan). This drives the map's station/paradero layers + the Cerca kind badges + filters, so the two are never conflated.

#### 5.4.2a SITP Zone Browse (`consulta_rutas_zonales`)
**One module, both clients**: `client/src/data/zones.ts` owns `variantBase`, the `code → zones[]` index and the landmark-derived zone labels; the app imports it via `@shared/data/zones` and only mirrors the presentation lists into its own state. It used to be a ~95-line copy inside `client/mobile/src/data.ts`, including a hand-curated 33-entry landmark list that had to stay byte-identical in two files for the two clients to agree on what "Zona 4" means (spec §1.1 R2).

The zonal-routes layer assigns every zonal route to **numeric SITP zones** (1–13; `0` = portal/troncal terminus) via `zona_origen_ruta_zonal` + `zona_destino_ruta_zonal` — authoritative even for numeric-coded routes that carry no zone letter (e.g. `661`, `139`). The mobile app's "Zonas SITP" browse builds a `code → zones[]` map from this feed (`client/mobile/src/data.ts` → `buildZonalAreas` / `variantBase`, which collapses catalog zero-padding `F019`→`F19` and direction/variant suffixes so both spellings match). This is separate from the troncal "líneas" (corridor letters A–P, a different taxonomy). `/api/zonal/routes` is served **attributes-only** (`returnGeometry=false`) — the route geometries are unused (zonal lines come from catalog trazado) and returning them timed the endpoint out.

#### 5.4.2b Sidebar lookup scope — the rider chooses what to look for
The Explore search reaches **two** universes: the 1000+ route variants and the ~12 500 places (troncal estaciones, zonal paraderos, tullave recharge points §5.5.1, TransMiBici cicloparqueaderos §5.5.1). Blending both into one list serves neither: a query for a recharge point buried it under 200 route rows, and a query for a route pushed it below six paraderos. Worse, only estaciones/paraderos were searchable at all — the two POI catalogues could be reached **only** by GPS proximity in Cerca, never by name.

* **Scope chips** (`#search-scope-chips`, `ui/sidebar.ts` → `renderSearchScopeChips`): `Todo` · `Rutas` · `Estaciones` · `Paraderos` · `Recargas` · `Bici`, each carrying its **hit count for the current query**. The row exists only while a query does — browsing the network needs the type/zone/line filters, not a "what am I searching" question. A scope with zero hits stays visible but `disabled`, so the rider still learns the category is searchable.
* **`Todo`** keeps the mixed view: up to 6 place rows above the routes, filled **round-robin across kinds** so one crowded kind (paraderos) cannot hide the others, each name capped at two rows. The heading reads `Resultados · N` (not `Rutas · 0`) whenever the list mixes both.
* **A single kind** shows that kind only — up to 60 rows, no per-name cap (the rider asked for these), and the route-only controls (type segments, saved views, zone/line rows) are hidden rather than left as switches that do nothing.
* **Never a dead end** (same rule as §5.6.2): a scope carried over from the previous query that matches nothing for this one widens back to `Todo`, so the panel shows where the results actually are instead of an empty state next to a chip reading `419`.
* **Every long list pages; none of them stops dead.** Both clients, both list kinds (routes and places) render in pages with a **`Ver N más`** button — "Mostrando 200 de 1031 · usa la búsqueda para filtrar" was an instruction, not a way out, and refining the query is exactly what a rider *browsing* a zone does not want to do. The page count resets on any query/filter/scope change and only the button grows it.
* **An empty result names the narrowing in effect** (both clients). "Sin rutas · prueba con otro código" read the same whether the rider had a typo or a zone/line/type filter swallowing every result: the state now says which filter is applied (`Ningún resultado para “x” dentro del filtro Troncal`) and carries the button that lifts exactly that one. `de` + a noun phrase is contracted through one shared helper (`utils/text.ts` → `de()`), so no surface ships "de el".
* **One kind vocabulary, one ranking — `client/src/data/pointKinds.ts`, shared by both clients.** It owns the kind list (`POINT_KINDS`, now including **`cable`**), their labels/badges (`POINT_KIND_META`), the accent-folded match ranking (`rankPointsByKind`, memoised per point — this runs over ~12 500 places per debounced keystroke), the per-name de-duplication and the round-robin preview. A kind cannot appear in one lookup surface and not another, and the two clients cannot disagree about what a query finds. `nearRowHtml` (website) / `ui/pointRow.ts` (app) are the row renderers over that vocabulary; the mouse wheel/drag affordance for every horizontal chip row is `ui/chipRow.ts` (Explore **and** Cerca — the Cerca row is wider than a phone sidebar and used to clip `Bici` out of reach with no way to scroll to it — **and** the estación platform plan, §5.5.6: any element that scrolls sideways here gets the same hidden bar, mask fade, wheel and drag by being wired through it).
* **TransMiCable is a lookup kind, not just a map layer.** It renders on both maps and the app listed it under Cerca, but on the website a gondola station was in neither lookup surface — visible on the map and unfindable by name. `showCableStationPopup` (`layers/cable.ts`) is now shared by the map click, Cerca and the Explore search so all three show the same card.
* **App parity (`client/mobile/src/views/rutas.ts`, the "Buscar" tab).** The app used to look up **routes only**: the ~12 500 places were reachable solely by standing next to them with GPS on. It now carries the same scope chips (`Todo · Rutas · Estaciones · Paraderos · Recargas · Bici · Cable`) with per-scope hit counts, the same mixed-`Todo` preview above the routes, the same "a scope that matches nothing widens back to `Todo`" rule, and the same hiding of route-only controls under a place scope. Route rows page with a **`Ver más`** button instead of stopping dead at a cap ("Mostrando 140 de 419" with no way to reach the other 279). The planner's endpoint suggestions use the same shared ranking, ordered station → cable → paradero → POI, since a trip endpoint is usually a station.
* **Locating is not choosing (website Cerca, `ui/cerca.ts` + `placeUserMarker`, `main.ts`).** Dropping the user marker used to also open the popup of the nearest troncal estación. The rider asked "what is near me", got the ranked list they asked for **and** a card for one station they never picked, over the map — and since the drag handler re-enters the same function, every nudge of the location dot re-opened it. `placeUserMarker` now places, recentres and re-ranks, and opens nothing; picking a point stays the list's job (`focusNearbyPoint`) and the map's.
* **A POI popup carries a pin, because the POI has no layer.** Estaciones, paraderos and cable stations are drawn on the map; the tullave counters (§5.5.1) and the cicloparqueaderos (§5.3) are catalog places with no symbol, so opening one from Cerca floated a card over blank street — the popup tip is 14 px of transparent CSS triangle. `showPopup(…, { pinColor })` (`layers/popup.ts`) owns the pin next to the single-popup state, so it cannot outlive or duplicate its card. The card itself is one renderer for all three kinds (`showPoiPopup`) and states what the row promised: address + localidad, the distance and walking time **from the same origin the ranking used**, the tullave counter's **three** windows each under the day it covers (`hds`/`exs`/`wks`, §5.5.1 — one unlabelled range cannot answer "is it open Saturday?"), and the `Desde aquí / Hasta aquí` actions every other place popup has.
* **The Cerca results scroll, not the panel** (`.cerca-panel > .near-list`, the split `.explore-panel` already used with `.route-list`). With the panel as the scroller every header row was a shrinkable flex item, and a row with `overflow-x:auto` is a scroll container whose automatic minimum size is **0**: the kind-chip row collapsed from 37 px to 8 px and its chips painted over the status line and the first results. The header rows are additionally `flex: 0 0 auto`, so a short viewport cannot re-open it.
* **`Consultar saldo` follows the Explore tab**, like the route detail does (`initTabs`, `ui/planner.ts`). As a permanent sidebar footer it sat under the Cerca results and under the planner's own sticky `Buscar ruta` on every tab — a second call-to-action, for an unrelated errand, competing with the one the rider is using.
* **A place row opens a sheet, in place.** Estaciones/paraderos always did; the POIs (recarga, bici, cable) instead jumped the rider to the Map tab and threw a 2.6 s toast, discarding the address and hours they were looking for. `openPoiSheet` gives them a real detail sheet with "Ver en el mapa" and planner seeding ("Desde aquí" / "Hasta aquí"), like every other place.

* **Trunk Corridors**:
  * `A`: `#0C3A95` | `B`: `#75C347` | `C`: `#FFB741` | `D`: `#6867B4`
  * `E`: `#B76416` | `F`: `#FB2C17` | `G`: `#00B0E8` | `H`: `#FF8525`
  * `J`: `#E49DAA` | `K`: `#D3AA78` | `L`: `#00B0A9` | `M`: `#852D89`
  * `P`: `#25206F` | `T`: `#808000` | `RF`: `#000000` | `Z`: `#EAB308`
* **Special Cases**: Alimentador `#009944`. Zonal default `#00608B`. Troncal default `#FB2C17`.
* **`RF` is a troncal service family, so the código alone never proves one.** The catalog files four variants under código `7`: the two rutas fáciles (`7 Portal Suba` / `7 Polo FINCOMERCIO`, `TransMilenio/TRONCAL`) **and** two SITP zonal services (`7 Palmitas` / `7 Consuelo`, `TransMiZonal/URBANO`). A code-only test called all four rutas fáciles — the zonal pair wore the black `RF` badge, answered the "Fácil" filter and read `Ruta fácil` in the app's route rows. `isRutaFacilCode(code, network)` / `isRutaFacilRoute(route)` / `getStopTagColor(code, color, network)` / `getRouteZoneLetters(code, network)` (`routeColors.ts`) all take the network, and every caller that has one passes it: a route item its own `type`, a wagon or catalog tag its own `sistema`/`tipoServicio` (`catalogRouteNetwork`, `routeType.ts`), an arrivals board the `TM…`-ness of its stop code. Only `RF` is gated this way — every other letter is deliberately shared by both networks (a zonal `T25` and a troncal `T…` are the same colour, above).
* **The letter class and this table are one thing.** Colour is keyed off the code's leading corridor/zone letters (`ROUTE_ZONE_PREFIX_RE`, `routeColors.ts`), and both systems draw from the same alphabet — a zonal `T25` and a troncal `T…` are both the `T` colour. `Z` was declared here and in `TRONCAL_COLORS` but missing from that character class, so Z-coded routes could never reach `#EAB308` and the entry was unreachable config. Adding a colour here without adding its letter there is a silent no-op.
* **The table colours corridors, not only route codes.** An estación page takes its accent from the letter of the troncal the station sits on (§5.5.6), resolved through `station_corridors.json`'s `letters` map — corridor name → letter, joined once from ArcGIS `letra_trazado_troncal`. Adding a corridor to this palette therefore means adding it there too, or the stations on it fall back to red.
* Every colour reaching an inline `style` attribute goes through `safeColor()` (`utils/html.ts`), never `escapeHTML()` — escaping does not neutralise `;`/`:`, so it does not make an untrusted catalog `color` safe as a CSS value (§3.3).

### 5.5 Backend API Contract & Local Dev Configuration

#### 5.5.1 API Endpoints
All mounted on `/api`. These serve the **browser client**; the native app does not call them — it hits the official hosts directly and reads the catalog/POIs from bundled assets (§5.2.1b).
* `GET /api/health`: Exposes catalog status (`catalogStale`, `syncInProgress`, `catalogStations`), ArcGIS + live cache entry counts (`cacheEntries`, `liveCacheEntries`), `liveTrackingVersion`, uptime, and — when the public-proxy fallback is enabled — `proxyPool` stats (§5.2.5).
* `GET /api/debug-buses`: Test payload endpoint (tests route `1` / `Universidades`).
* `GET /api/geoip`: Approximate client location from IP (fallback when native geolocation is blocked; zero PII stored — §3.3).
* `GET /api/troncal/routes`, `/api/troncal/stations`, `/api/troncal/corridors`, `/api/troncal/master-catalog`, `/api/troncal/route/:code`, `/api/troncal/station/:code`, `POST /api/troncal/sync`, `/api/zonal/routes`, `/api/zonal/stops`, `/api/zonal/stop-routes`, `/api/cable/stations`, `/api/cable/trazado`, `POST /api/buses`, `POST /api/card/read`.
* `GET /api/geocode?q=`: Bogotá-bounded address/place lookup (local catalog + Photon + Nominatim + ArcGIS geocoder, queried **in parallel**), backing the planner's origin/destination autocomplete. Returns `{candidates:[{name,lat,lon,type,code?}]}` with `type ∈ {station, stop, address, place}` — and nothing else: `aliases` is an internal matching aid for the verified-split entries and must not reach the client. The local scan is an **autocomplete hot path** (one call per debounced keystroke), so both sides of the scoring are canonicalised exactly once: the query per lookup, and every catalog station into a `localIndex` built once per `getCatalogLoadedAt()`. Re-deriving either inside the ~7 500-station loop cost ~163 ms of synchronous string work per lookup on a 0.1-CPU instance (spec §1.1 R2 — measured, not estimated).
* **One Bogotá bounding box** (`services/bogota.ts`): it was written out four times, and two of the copies disagreed (`south: 4.45` in the geocoder vs `4.4` for walking-route validation), so latitude 4.42 was inside the city for one endpoint and outside it for the next. The Nominatim `viewbox` and Photon `bbox` are derived from it too, never re-typed. The app's direct-host client had a fifth copy (`officialApi.ts`, gating its own walking-route and geocode calls); it reads the client's single box (`utils/geo.ts`) now, so a coordinate the website will plan for is never one the app silently refuses to route.
* `POST /api/stop-arrivals`: per-route ETA for **any** stop code (troncal `TM…` or zonal cenefa), computed from live bus positions projected onto each serving route's trace — the "Próximos a llegar" block in both the estación and the paradero popup (`layers/arrivals.ts`). Distinct from `/api/arrivals`, which forwards the official app's own `/paradero/buses` board. Never hard-fails.
* **The `GET /api` index must list all of them.** It is the only machine-readable inventory of this surface and had drifted eleven endpoints behind; a route added without a line there is undocumented twice over (here and at runtime).
* `POST /api/arrivals`: real-time arrivals/ETAs at a paradero (`{paradero:"<cenefa>"}` → `{arrivals:[...]}`), reusing the live-bus transport cascade (direct → CO relay §5.2.2a → public CO proxy). Never hard-fails — empty list on outage (§5.8 Host 2), and that outage answers `source: null`, **never** `source: 'direct'`: naming a transport that never answered would claim a Colombian egress had verified an empty arrivals board (§1 certainty).
* `GET /api/walking-route`: real pedestrian route geometry between two points (OSRM foot profile), consumed by the planner's `resolveWalkingLegs()` to replace straight-line walk-leg estimates with real distance/time/path (§5.6). `distance` is the **honest walked total** — the routed path *plus* both of OSRM's snap legs, which are also returned individually (`snapFrom`/`snapTo`) because the geometry runs between the snapped points, not the ones asked about (§5.6.4). Cacheable (`max-age=86400`): a walk between two fixed points never changes, and the previous `no-store` sent every repeat of an identical leg back to the public router.
* `GET /api/recarga-points`, `GET /api/personalizacion-points`: the two static tullave POI catalogs (name/address/hours) — where a rider tops up a card, and where they register/personalize one. Both are committed from a Colombian egress like the master catalog; **one** sync serves both (`server/src/sync_tullave_points.ts`, §5.8 Host 2), because upstream returns the identical `TuLlave` shape for each. It runs from anywhere via the standard cascade (direct → CO relay → public CO proxy) and **refuses to write an empty harvest** — silently emptying a committed catalog would read downstream as "this kind has no points" rather than as the failure it is (§1).
  * **The three hour fields are not named after what they contain.** As the official app labels them (v2.9.6 `MapTagActivity`): `hds` = *Horario entre semana* (Mon–Fri), `exs` = *Horario Sabados*, `wks` = *Horario Domingos y Festivos*. Both clients had been showing `wks` as **the** opening hours, so a counter open on a Tuesday could display its Sunday `"No Opera"` and read as permanently closed. The rendered value is `hds`.
* `GET /api/station-demand`: mean weekday entry/exit (validation) counts per troncal station, aggregated offline from the open **Salidas** dataset and committed — see `server/src/sync_demand.ts` (§5.8 Validaciones). Auto-refreshed daily by `.github/workflows/sync-demand.yml` (22:00 UTC): regenerates the JSON and commits it only when the data window advanced, so the host redeploys on real data only. A downloaded day that parses to **zero rows** is skipped rather than counted: `daysUsed` is the divisor for every mean, so an upstream CSV-format change would otherwise deflate the whole dataset silently instead of failing (§1 certainty). Powers the "Demanda" heat overlay on both clients (website `client/src/layers/demandLayer.ts`; app `tm-demand` layer in `client/mobile/src/map/mapController.ts`, tap → toast) — an independent graduated-circle layer keyed on its own coordinates so it never couples to the station resolver.
* `GET /api/transmibici`: static TransMiBici bike-parking POI catalog (name/capacity/occupancy) from ArcGIS `Consulta_Planificacion_SITP` layer 12 — see `server/src/sync_transmibici.ts` (§5.3). Surfaced as the Cerca "Bici" kind on both clients.

#### 5.5.1a Lectura de saldo
* **Upstream host**: `https://tmsa-transmiapp-shvpc.uc.r.appspot.com`.
* **Endpoint**: `POST /lectura_tarjeta`.
* **Request body**: `{"numero_tarjeta":"<digits>","consultar":"false"}`. `consultar` is a string (`"true"` / `"false"`), not a boolean.
* **Required observed headers**:
  ```text
  Accept-Encoding: gzip
  Appid: 9a2c3b48f0c24ae9bfba38e94f27c3ea
  Connection: Keep-Alive
  Content-Type: application/json; charset=UTF-8
  Host: tmsa-transmiapp-shvpc.uc.r.appspot.com
  User-Agent: okhttp/4.12.0
  uuid: fd1be953-d85e-4c63-8c23-234f143f445d
  version: 2.9.5
  ```
  `Content-Length` must be computed from the exact JSON body bytes.
* **Server contract**: `/api/card/read` validates the card number, sends the exact upstream shape, decodes gzip, does not cache, and never logs or stores the full card number. Because the host is CO-IP geofenced, the read follows the same egress cascade as live buses — **direct → CO relay (§5.2.2a, forwards `/lectura_tarjeta`) → public CO proxy** (`fetchCardRowsViaColombianEgress`, `card_balance.ts`); unlike live buses the card endpoint is not service-window-gated, so it resolves 24/7 given any working CO egress.
* **Source separation**: `/lectura_tarjeta` returns the server ledger only. The official mobile UI can show newer balance and multiple movements after a phone tap because it reads NFC card memory locally. Web/server code must not infer or fabricate those hidden card movements from the server response. Any future NFC/native bridge must merge as `source:"card"` with provenance distinct from `source:"server"`.
* **App NFC read (`client/mobile/src/services/nfc.ts`)**: three runtime-detected backends, so the web bundle keeps no hard dependency and needs no code import — detection is runtime-only. Android's System WebView **disables Web NFC** (`NDEFReader` → "NFC permission request denied"), so inside the APK a **native plugin is mandatory**; the app tries them in order: (1) **`phonegap-nfc`** (free/MIT, `window.nfc`) — a declared `mobile/` dependency, so it registers automatically on `npm install` + `npm run apk` (which runs `cap sync`), no manual plugin install (patched for Android 12+/14 — see [[apk-nfc-beam-api34]]); (2) **`@capawesome-team/capacitor-nfc`** (`Capacitor.Plugins.Nfc`, sponsorware); (3) **Web NFC** (`NDEFReader`) only outside the APK. With no plugin present in the APK the read fails with an explicit "install the NFC plugin and rebuild" message. **Correction (verified §5.5.1b):** the tullave chip is a **Calypso** card, NOT an unreadable encrypted DESFire. Its balance + last 10 movements + 16-digit card number are readable with **plain, unauthenticated ISO-7816 APDUs (no keys)** via `phonegap-nfc` `transceive()`. NFC therefore yields a real `source:"card"` balance and movement history on-device — the earlier "UID only, balance is server-only" claim was wrong.

#### 5.5.1b tullave Calypso NFC protocol (reverse-engineered, validated)
Decoded from the official app **v2.9.6** (`com.nexura.transmilenio`, `MainActivity.ndefReadTag`) and **validated live on-device** (Frida hook on `IsoDep.transceive`, real card). All reads are **unauthenticated** — no DESFire/Calypso session, no keys. Use `IsoDep` (tech `IsoDep`/`NfcA`/`NfcB`), `setTimeout(20000)`, then transceive in order (hex):

```text
1. SELECT AID     00 A4 04 00 07 D4 10 00 00 03 00 01   → FCI 6F31…  (Calypso transit app)
2. GET balance    90 4C 00 00 04                         → respA  (e.g. 0000 98EE 9000)
3. READ BINARY    00 B0 86 00 42                         → respB  (66 B; debt record, all-zero when none)
4. SELECT EF 4200 00 A4 00 00 02 42 00                   → respC  (FCI; card # inside)
5. READ RECORD    00 B2 <rec> 24 2E    rec = 0x01..0x0A  → 46-byte movement records
```

**The official app reads one of the card's four populated files.** A full sweep (`research/sweep.src.js`, READ RECORD and READ BINARY over SFI 1–30, three cards, 2026-08-22) maps the transit application as:

| SFI | Access | Contents |
|---|---|---|
| 2 | READ RECORD, 1 rec | Byte-identical copy of the FCI |
| **3** | READ RECORD, ≤10 recs of **51 B** | **Parallel transaction log, undocumented format** (below) |
| 4 | READ RECORD, ≤10 recs of 46 B | The movement log the app reads (step 5) |
| **5** | READ RECORD, ≤5 recs of 46 B | **Recharge-only log** — same format as SFI 4, `type` always `02` |
| 6 | READ BINARY, 66 B | `respB`, the *mora* record (step 3) |
| 13 | READ BINARY, 100 B | Constant `10` + zeroes — **byte-identical on all three cards**, not card data |
| 17–25 | — | Files **exist but hold no records** (`6A83`, not `6A82`) on all three cards |

Read a record file with `00 B2 <rec> <(SFI<<3)|4> 00` and a transparent one with `00 B0 <0x80|SFI> 00 00`; a `6C XX` reply carries the length to retry with. SFI 1, 7–12, 14–16 and 26–30 answer `6A82` (no such file).

Parsing (all multi-byte fields **big-endian**; strip the trailing `9000` SW before indexing):
* **Balance (COP)** = `BE(respA[0:4])`. **Correction (verified 2026-08-22):** an earlier revision gave this as `BE(respA[0:4]) + BE(respA[5:8])`, which cannot ever have run — `respA` is **4 bytes** before the `9000` SW (observed `00005CC6`; that revision's own worked example, `0000 98EE 9000`, is 4 bytes too), so `respA[5:8]` indexes past the end of the buffer. The 4-byte value alone is correct: on a live read it reconciled to the peso against the newest movement's `saldoFinal`, and against a 10-record balance chain that closes exactly (below). The `respB[0:4]` starts-with-`01` adjustment is **retained but unexercised and probably misstated** — see the `respB` bullet below: on the one captured card carrying a debt, `respB` begins `02` and its `[4:8]` field holds the debt exactly, so the branch is about *mora*, not about a second balance term. Do not implement it from the `01` formula as written.
* **Card number** (16-digit BCD) = `hex(respC[8:16])`.
* **Movement** (per 46-byte record; `rec = 0x01` is the **newest** — SFI 4 is written newest-first): `type = rec[0]` (`01`=Viaje en bus, `02`=Recarga, `04`=Cancelación recarga); `saldoFinal = BE(rec[3:6])`; **`tripCounter = BE(rec[8:10])`**; `monto = BE(rec[11:14])`; **`deviceClass = hex(rec[14:18])`** and **`deviceId = hex(rec[18:22])`**, both BCD; **`deviceCounter = BE(rec[22:26])`**; datetime = `DD/MM/YYYY HH:MM:SS` from `rec[29] rec[28] rec[26]rec[27] rec[30] rec[31] rec[32]` (hex-as-decimal). `rec[1]` is always `2C` (= 44, the payload length in bytes); `rec[2]`, `rec[6:8]`, `rec[10]` and `rec[33:46]` are zero on every record observed. Records with no valid response end the loop.
* **`tripCounter` counts paid trips, not transactions** (`rec[8:10]`). It advances by exactly 1 per successful debit and **does not move** for a recarga or for a refused tap — a recarga and the refusal preceding it both carried `047E`, and the next paid trip took `047F`. It is a lifetime ridership odometer for the card, not a log sequence number: the captured card read **1158 paid trips**. Do not use it to detect gaps in the log.
* **`deviceId` is the individual validator, and the record never encodes the place.** `rec[18:22]` is an 8-digit BCD id in one flat, system-wide registry (observed range `10000736`–`10014375`). Seven taps at **Nariño** — three ordinary gates plus one accessible gate the rider never uses — produced **exactly three ids**, one per ordinary gate. `rec[14:18]` looks like a station field and is not: it is the **device class**, `08200200` for a fare validator and `08200100` for a recharge point, byte-identical across every station observed. **A card records which machine, never which place.** Resolving `deviceId` → place needs a registry this project must build; it cannot be read off the chip.
  * **`08200200` is not "turnstile" — it is any fare validator, vehicles included.** One captured tap under that class resolved to an **SITP bus**, not a station (Sunday 09/08, 17:44). Its `deviceCounter` was 321 328 against 5.2 M and 8.3 M for two Nariño gates, so counter magnitude separates a vehicle validator from a station turnstile in practice, but nothing in the record *declares* which it is. A bus id maps to a **vehicle**, not a location, so `deviceId` → station is undefined for that part of the registry.
  * **Ids are NOT allocated in per-station blocks — falsified.** CDS Carrera 32 turned up as `10012270` and `10012271` on two different cards five weeks apart, which looked like block allocation; but **Nariño's three gates are `10000804`, `10003425` and `10012674`**, spread across the whole range. Consecutive ids indicate a shared installation batch, nothing more. The registry must be built one device at a time; a station's other gates cannot be inferred from a known one.
  * **Resolved so far — 8 validators + 4 recharge points, from 3 cards.** Nariño `10000804` / `10003425` / `10012674`; CDS Carrera 32 `10012270` / `10012271`; Biblioteca Tintal `10001272`; Las Nieves `10001073`; SITP bus `10010330`. Recharge points `10000736`, `10001925`, `10010355`, `10013869`. Still unplaced: `10014375`.
* **A refused tap is written as a zeroed record, not as a zero balance.** `monto` and `saldoFinal` both `000000`, `tripCounter` unchanged, `deviceId` and datetime populated as normal. The captured card holds one (10/08 15:12:42, gate `10014375`): the card stood at **−$1.400**, and a further $3.550 would have breached the one-fare debt floor of a *tarjeta personalizada*, so the gate declined. Reading those zeros as "the balance was $0" is wrong — no transaction occurred.
* **Negative balance is real, settles on the next recharge, and is never stored directly.** A personalizada may go negative by at most one fare. Observed: card at −$1.400 → recarga posts **gross** (`monto` $50.000, `saldoFinal` $50.000) → a second record **at the same device in the same second**, typed `01` (Viaje en bus) rather than as a fee, debits exactly $1.400 → $48.600. The debt is inferable only from the pair; no field carries a signed balance. A client that renders those two records independently shows the rider a $50.000 recharge plus a phantom $1.400 "trip".
* **`deviceCounter` (`rec[22:26]`) is that turnstile's cumulative validation count.** For a fixed `deviceId` it rises monotonically with time; across gates the values are unrelated. Measured on gate `10003425`: **+1536** (12→13 Aug), **+5286 across five days** spanning Sat/Sun and the 17 Aug festivo (≈1057/day), **+1753** (18→19 Aug), **+1426** (19→20 Aug) — roughly 1400–1750 validations per weekday at one gate, with the expected weekend/holiday dip. This is **per-gate demand at a granularity the `validaciones_tmsa` station-demand feed (§5.5.1) does not publish**, readable from any rider's own card. Unresolved for class `08200100`: the recharge point returned `0000425B` and `0000F59A` from the same device in the same second, so that class carries something other than a single counter.
* **`respB` (READ BINARY, 66 B) is the *mora* record, not padding.** All-zero on the two captured cards that have never gone negative; populated on the one that has. Its content there: an `02` prefix, **`0578` = the $1.400 debt to the peso**, the BCD timestamp **`20260810150540`**, counter `047B`, ten `FF` bytes, then a second dated block — **`20260812112900`**, matching the settlement record in the event log to the second — the field `2B33`, counter `047E`, and ten more `FF`. The card therefore carries debt state **outside** the SFI 4 circular buffer, with its own timestamps. The counter `047B` it cites is **not** in SFI 4 — the sweep found that transaction in **SFI 3 record 9**, which carries the same `0D1D0D3C` field, so the two files corroborate each other. **Unresolved:** the two blocks' exact boundaries and the fields `0000D040` / `00002B33`; and note that `0D1D…` is *not* debt-specific — see the marked-transaction bullet below.
* **The FCI carries an issue date and a profile block.** The FCI returned by SELECT AID (step 1) and by SELECT EF 4200 (step 4) is byte-identical in all three captures. Beyond the card number at `[8:16]`: `[16:21]` is a second BCD number, `[21:25]` a BCD date — `20240223`, `20240308`, `20250430` on the three cards — and `[25:31]` is a six-byte block that reads **`3C9264926512` on the *personalizada* and `000000000111` on both *anónimas*** — card type confirmed by the holder for all three. That block is the card profile, and therefore the likeliest place for a subsidised tier (adulto mayor, estudiante, discapacidad) — the entitlement signal no upstream API exposes. **Untested:** the sweep found SFI 17–25 (where Calypso conventionally keeps contracts and counters) present but **empty on all three cards**, personalizada and anónima alike, so nothing here distinguishes a subsidised card. Settling it needs a tap from an actual subsidised card; do not assume the profile block is the only place a tier could live. It is also the only field that predicts whether the card may go into *mora*: the personalizada carries a debt record (`respB` below), neither anónima can. `0F4240` (= 1 000 000) follows on all three and is constant; plausibly the balance ceiling, unverified.
* **`tripCounter` gaps led to SFI 3 and SFI 5 — sweep done, partly resolved.** Two cards skipped counter values with record slots still free, which could only mean transactions written outside SFI 4. The sweep found them. **SFI 5** is a recharge-only log in the SFI 4 format (`type` always `02`), reaching back **two and a half months** where SFI 4 covered eleven days — one card holds recharges from 10 Jun, 18 Jun, 1 Jul, 6 Jul and 30 Jul. **SFI 3** is a parallel log in a different 51-byte format whose **newest record sits exactly one transaction behind SFI 4's on all three cards** (1157 vs 1158, 69 vs 70, 5 vs 6) — too consistent to be chance. It is **not uniformly deeper**: it recovers counters SFI 4 had already overwritten (1146–1148 on one card, 59 on another) yet holds only 3 records against SFI 4's 6 on the least-used card. Reading SFI 3 + 4 + 5 together yields **13–15 transactions per card**, not the full lifetime count. Still unexplained: counter `1149`, absent from every file on that card.
* **SFI 3 record layout (partial).** 51 bytes. `monto = BE(rec[14:17])` (`000DDE` = $3.550, same fare as SFI 4) and `tripCounter = BE(rec[36:38])`, matching SFI 4's counter for the same transaction — those two anchor the record. `rec[0:2]` is always `0132`; `rec[2:4]` is a second descending sequence. `rec[17:21]` and `rec[21:25]` are two 4-byte fields differing by a constant `0x2140` in every record on every card; they are **not** a timestamp — their inter-record deltas do not track elapsed time (129 326 across 25 h, 558 003 across 24 h on the same card). Unresolved, and SFI 3 carries **no decoded date**, so SFI 4 remains the only source of transaction timestamps.
* **A marked transaction class exists in SFI 3, and it is not (only) debt.** Records where `rec[2]` is `10` rather than `14` also carry `rec[7]` = `82` (vs `C9`), `rec[8:10]` = `0202` (vs `0101`) and `rec[10:12]` = `0D1D` (vs `0098`). **Correction:** an earlier revision read the one such record on the *personalizada* — counter `047B`, the `0D1D0D3C` field it shares with `respB` — as "the trip that created the debt". One of the **anónimas carries the same marker** (counter 67) while its `respB` is all-zero and it cannot go into *mora* at all, so the marker denotes a broader transaction class of which debt is at most a subset. Do not treat `rec[2] = 10` as a debt flag.
* **A card's first record is an issuance record under a third device class.** The least-used captured card carries as its oldest entry a record with `monto` and `saldoFinal` zero, **an all-zero datetime**, and `deviceClass` **`07200900`** / `deviceId` `20000052` — outside both the `08200200` turnstile and `08200100` recharge-point classes, and the only observed device id not beginning `1000`/`1001`. Clients must tolerate a dateless record rather than rendering the epoch.
* **Evidence base and scope.** Decoded from **three cards captured 2026-08-22** with the `research/` Frida rig (§5.8 provenance) — first the app's own read (26 records), then a full SFI 1–30 sweep of all three (`research/sweep.src.js` + `sweep-run.py`, hooking `IsoDep.connect` to drive the card directly instead of observing the app; all probes read-only). All three balance chains reconcile to the peso with no unexplained movement, which pins `type`, `saldoFinal`, `monto` and the datetime decode. `deviceCounter` is confirmed **across cards**: two different cards read the same Nariño turnstile on nine days between 3 and 20 August and their readings form one monotonic series (≈1400–1950 validations per weekday, falling to ≈1050/day across a weekend-plus-festivo stretch). `deviceId` → place is **partially solved**: 12 of 13 observed devices are now named (list above), one gate remains unplaced, and the per-station block hypothesis is falsified. The profile block is confirmed across all three cards against holder-stated card type; the `respB` internals and the issuance record each still rest on a single card. `rec[19]` varies only with `deviceId` and is treated here as its second BCD byte; if a second station shows it moving independently, that reading is wrong.
* Provenance stays `source:"card"`; the server ledger (`/lectura_tarjeta`, §5.5.1a) remains `source:"server"`. The card read is authoritative for live balance since it is the chip itself.

#### 5.5.2 Caching & Timeouts
* **Caching**:
  * ArcGIS endpoints cached in-memory with 10-minute TTL.
  * **Master catalog (memory-critical)**: `/api/troncal/master-catalog` is served from a **precomputed gzip buffer** built once per catalog version (`getCatalogLightGzip`, `tm_api.ts`) and streamed verbatim (`Content-Encoding: gzip`) — never re-`JSON.stringify`d or re-gzipped per request. The light catalog is NOT retained as a live object; only the ~5 MB buffer + the full catalog stay resident. This removes the transient per-request allocations that OOM-killed the 512 MB host under concurrency (§4.3). ETag `W/"catalog-<loadedAt>"` → `304`; concurrent first-hits share one build; identity fallback for clients that refuse gzip.
  * **Static assets** (`server/src/index.ts`): fingerprinted `/assets/*` served `Cache-Control: public, max-age=31536000, immutable`; `index.html` `no-cache` (so new asset hashes are picked up on deploy); other public files (models, draco, icons) `max-age=86400`.
  * **Service worker** (`client/public/sw.js`, registered in `main.ts`): cache-first for hashed assets + models/draco/fonts, **network-first** for `/api/troncal/master-catalog`, network-first for the HTML shell. Live `/api/*` is never cached. Versioned cache (`tm-cache-v5`); old versions purged on `activate`. The catalog is deliberately **not** stale-while-revalidate: SWR served the cached copy first and revalidated behind it, which pinned a stale catalog across a deploy (the app kept rendering phantom route mappings while the server was already fixed). Network-first with `cache: 'no-cache'` forces an ETag revalidation (fast `304` when unchanged) and falls back to the cache only when offline. **Bump `VERSION` whenever the cached surface changes**, and keep this line in step with it.
* **Timeouts**:
  * Catalog API request: 15s.
  * Official live API request (direct): 9s.
  * Colombia relay query: 12s.
  * Public live proxy request: 14s (`LIVE_PROXY_TIMEOUT_MS`), raced across the best `CO_PROXY_RACE_WIDTH` (5) proxies.
  * Public proxy pool readiness wait: 18s; per-proxy verification test: 12s.
  * Relay health checks: 5s.

#### 5.5.4 SEO & Crawler Surface
Canonical public origin: **`https://transmilenio.onrender.com`** (same origin allow-listed in `RELAY_CLIENT_ORIGINS`, §5.2.2).
* **Dedicated folder**: the hand-maintained crawler-facing root files live in **`seo/`** — `robots.txt` and the Google Search Console ownership token `googlebb8cb92194ccf198.html` (Google fetches that exact root path; it must never be renamed or nested). They are **not** client build output, so they are not copied into `client/public`; `server/src/index.ts` mounts the folder with `express.static` (`index:false`, `Cache-Control: public, max-age=3600`) after the `client/dist` mount, which puts them at `/robots.txt` and `/googlebb8cb92194ccf198.html` with one source of truth and no build step. Consequence: they are served by the Express server only — `vite dev` (5173) proxies just `/api` and 404s them. **Nothing in `seo/` is generated** — the sitemaps are build output and live in `client/dist` (below).
* **Prerendered pages (`server/src/prerender_seo.ts`)**: in-app deep links are hash fragments (`#/r/<code>`, `#/plan?…`, §5.6), and crawlers discard fragments — so a hash-only site is one indexable URL competing for one generic query. The troncal network is therefore written out as static HTML after `vite build` (wired into the root `npm run build`, standalone via `npm --prefix server run seo:prerender`):
  * `/ruta/<code>/` — **213 pages**, one per troncal código, covering *both* directions on a single page. Body carries the ordered stop list with cumulative distances, per-direction origin→destination, and horarios; JSON-LD `BusTrip` + `BreadcrumbList`.
  * `/estacion/<slug>-<codigo>/` — **139 pages**, one per troncal estación (`/^TM\d+$/`, the same test `buildCatalogLight` uses). Body carries the street `direccion` and a **platform diagram** (below); JSON-LD `BusStop` + `BreadcrumbList`.
  * **Platform diagram (`buildPlatform`)**: what an official "plano de ubicación" encodes is which services board from which vagón, and which way each faces. Both halves come from the catalog. `station.wagons` already groups services by platform — verified against the official planos for General Santander, Calle 40 Sur, Sevillana, León XIII, Bosa, San Mateo, Granja-Carrera 77 and Suba-TV 91, where the catalog's wagon groups reproduce the printed vagones **exactly**. Direction comes from each service's own bearing to its next stop, matched through the wagon entry's route **variant id** (the same código runs both ways, so the código alone is ambiguous).
  * **Wagon key `0` is a mixed pool, so it is classified by `tipoServicio` and never by the key itself.** It is the platform letter the catalog *doesn't* assign, and what lands there is both the station's alimentador/zonal pool **and** troncal services: P85/M85 at Centro Memoria, L81/D81 along Avenida 68, **61 troncal services across 22 stations** (4 of which hold both kinds at once). Reading the key as a class printed those troncales under "Alimentadores y servicios zonales" on the estación page and its social card — telling a rider a troncal padrón is a feeder — while the app's station popup labelled the same set **"Vagón único" next to a Vagón A and a Vagón B**, because it named the section from the pool's dominant content. Both surfaces now split the pool on `isZonalService`: the zonal half keeps the alimentador heading, the troncal half gets its own block headed *Otros servicios troncales* ("Vagón único" survives only where there is no lettered platform beside it) with the note that the catalog assigns it no vagón. That block is deliberately kept **out** of `vagones`: it must take neither a vagón number nor a `Plataforma N` ordinal — the catalog names no platform for these, only the station's signage can — and `wagonCount`, the plate comparison behind `vagonLabel`, must keep counting lettered platforms only. A zonal route filed on a *lettered* troncal platform is the opposite case and is still **dropped**, not repooled (A537 "Palermo" merely parallels the corridor — a phantom stop, currently 0 of 139 stations); the server's `isZonalService` is a deliberate copy of the client's, since the two packages compile separately (`rootDir: ./src`) — change both together.
  * **Split the directions, don't average them (`splitDirections`).** A vagón is usually an *island platform* serving both ways, so its services' bearings are supposed to disagree — Calle 85 has badges above and below the same vagón. An earlier version averaged them, found they cancelled, and concluded vagones had no direction; that was backwards and printed a wrong direction for **107 of 139** stations. The fix is to split on the principal axis of travel (doubled angles, so opposite headings reinforce instead of cancelling) and label each group from its own mean. Verified against the planos for Calle 40 Sur and General Santander: **every vagón, both directions, sets identical to the printed diagram**.
    * **The direction names are answered, not computed (`data/corridor_directions.json`).** A bearing cannot name a direction in Bogotá. The grid is not square to true north, and — the part no amount of geometry recovers — **a corridor keeps one name for its axis along its whole length, even where the road bends**: Calle 26 is *oriente/occidente* where its bearing swings to 145°, and the NQS stays *norte/sur* through the Soacha stretch that physically runs east–west. Deriving names from the compass printed "nororiente" for the Caracas and, once checked corridor by corridor, disagreed with the street on **8 of the 12 corridors**. So the compass no longer names anything: it only decides *which end* of a corridor a platform serves. The names come from `corridor_directions.json`, answered station-pair by station-pair by the maintainer as the deciding authority ("Bus de Calle 76 - Héroes → norte"); **24 answers cover all 1 444 boardable services at the 140 troncal stations**. Two were corrected on review because a corridor came back with two ends whose names were not opposites — the check worth repeating if the table is ever re-answered.
    * **Group by the name, not by the geometry (`splitDirections`).** Services on a platform are bucketed by the label their heading earns, not split on the vagón's principal axis and named from each half's mean. The axis split forced every service into one of two buckets, so at Museo Nacional the bus that turns west onto Calle 26 was averaged in with the ones climbing Carrera 7 and inherited their *norte*; it now reads *occidente*, which is what the maintainer answered for that bus. A platform can genuinely send buses three ways — 35 vagones do, 3 send four — and the name is what a rider reads off the sign.
  * **Vagón numbering is gated on evidence, and resolved once for every surface (`printedVagonLabels`, `services/plano_vagones.ts` + `data/plano_vagones.json`).** The catalog keys wagons `A`/`B`/`C` while signage reads "Vagón 1/2/3"; A→1, B→2, C→3, D→4 was confirmed on 8 of 10 planos spot-checked. It fails where the catalog groups platforms differently from the signage — Calle 161 (catalog 2 wagons, plano prints **4**, so catalog `A` mixes printed vagones 1 and 3) and Av. Jiménez (catalog 5, plano prints 3). Both are caught by comparing the catalog's wagon count with the plate count counted off each plano and committed to `data/plano_vagones.json`; that predicate agreed with ground truth on 9 of 10, and its one miss errs toward silence. Where the counts disagree the platform renders as "Plataforma N" with no number: **93 of 139** stations get a real vagón number, 46 get the neutral label. Directing a rider to "Vagón 1" when the sign reads 3 is a real-world wrong answer, so the numbering is withheld rather than guessed. `plano_vagones.json` stores **only the count** — no plano image is copied, cached or re-served.
    * **The decision is made where the evidence lives and shipped as data**, `station.vagonLabels` on the light catalog (§5.1.4) — wagon key → the number printed on that sign, absent where it can't be trusted. The prerendered page and the app's station popup both *read* it; neither re-derives it. They did not use to agree at all: the popup printed the catalog's raw key, "Vagón A" — a letter that appears on no sign in any station, so a rider sent to it has nothing to look for — while the page printed the gated number for the same platform. A number is display data here, not presentation logic: the client cannot derive it (the plate counts are a server-side dataset) and a second copy of the rule is a second answer waiting to happen.
    * **The client re-checks the evidence against what it actually renders (`resolveVagonLabels`).** The map's stations are not one-to-one with catalog stops: four ArcGIS fragments cluster onto Terminal (TM0031) and Av. Jiménez / Ricaurte each split one catalog stop into two stations. A plate count measured over a stop's five platforms cannot be inherited by a station showing three of them, so labels are published only when the platforms on screen are exactly the platforms one labelled stop was measured on. Terminal keeps its numbers (the fragments contribute no wagons); the four verified-split halves fall back to "Plataforma N" — which is where they already were, both stops having failed the plate predicate outright.
  * Content comes from the same light catalog the API serves (`getCatalogLightGzip`, §5.1.4), so a page can never describe a network the app does not render. Output is written **into `client/dist`**, inheriting the built shell's fingerprinted asset tags and served by the existing `express.static(clientDist)` mount — no extra route, and `/ruta/g47` 301s to the trailing-slash form automatically.
  * Pages cross-link **both ways** (route → its estaciones, estación → its rutas). Without both directions the pages are discovered but orphaned, and a crawl graph is what gets a 352-page batch indexed.
  * The static body lives in `<main id="seo-prerender">` and is the page until the bundle boots, so it doubles as the no-JS fallback. **Both kinds hand over to their interactive twin** once the bundle is here — the route page (§5.5.5) and the estación page (§5.5.6) say everything the static body says and add what only a running app can: the live bus card, the arrivals board, the ridership strip, working links. The estación body used to survive instead, because the map's popup could not answer "which vagón do I stand on" and the static plan could; now the page can, so the reason is gone. `revealPrerenderedPanel()` (`main.ts`) still injects the "Ver en el mapa" dismiss bar for the case where no page opens — a station the catalog cannot describe — and never for a body a page has already replaced.
  * **The static bodies are drawn as the same page the bundle draws** (§5.5.5, §5.5.6): accent rail, hero plate, hairline ficha strip, sections separated by rules, the stop list as a numbered line diagram, the estación plan in the app's own neutral. The prerender's stylesheet is a deliberate copy rather than a token import — this body ships before any stylesheet of ours is guaranteed to have loaded, which is the whole point of prerendering it — so where the two must agree (the accent, the surfaces, the rutero bezel, the plan's plate) they are the same values on purpose, and a change to one is a change to both.
  * Route pages carry **el rutero** — the bus's own LED destination sign, drawn from the same dot-matrix font the app uses (§5.5.5). It is content, not decoration: the destination is spelled exactly as the panel spells it, which is often not how the catalog does.
  * **Zonal routes (684) and paraderos (7 387) are deliberately excluded.** At this domain's authority, thousands of near-identical thin pages read as a doorway pattern and risk demoting the whole site rather than merely being ignored. They ship only once Search Console shows this batch indexing — which is why the sitemaps are split by type.
* **Path deep links**: a prerendered page carries no hash, so the hash router never fires for a visitor arriving from a search result. `parseRoutePath()` (`client/src/ui/sidebar.ts`) resolves `/ruta/<code>/` case-insensitively against the código, and `main.ts` resolves `/estacion/<slug>-<codigo>/` through the same `focusNearbyPoint` flow as Cerca/Explore. On the first in-app navigation both `pushRouteHash` and the planner's `syncPlannerHash` normalize the pathname back to `/`, so a hash link can never name a different route than the path it sits on.
* **Per-page social cards (`server/src/seo_og.ts`)**: 1200×630 PNGs at `/og/ruta/<code>.png` and `/og/estacion/<slug>.png`, one per prerendered page, overriding `og:image`/`twitter:image`. Rationale: these pages spread by **WhatsApp forward**, not by Twitter, so the preview is a distribution surface — one generic logo on every link reads as spam. Route cards draw the route's own `trazado` with a bead per stop, beside its código badge, name, origin→destination and horarios; estación cards pin the station and list its services as colour-coded chips. Both sit over a **backdrop of the 88 `TRONCAL` traces** — the city network, dimmed and clipped to the panel. That backdrop is deliberately *not* a basemap: tiles would mean 352× external requests at build time, tile-provider attribution, and a build that breaks when someone else's CDN does; the network is already in the catalog, is free, and reads as a transit diagram. Alimentadores are excluded from it (100+ more traces draw a hairball, not a recognisable city) and every other point is dropped — invisible at 540 px wide, and roughly halves the SVG each card parses. Terminal rings mark the **origin and destination stops**, not the ends of the drawn trace: capping the trace looks tidier on a straight route but collapses on the many loop alimentadores whose trazado starts and ends at one coordinate (`6-1`: first === last exactly), stacking both rings on a single pixel. Three constraints the layout is built around, each found by rendering and looking:
  * **Fonts**: the site ships Inter as **woff2**, which fontdb cannot read, and the Linux build image is not guaranteed to have any system font — text would render as *nothing*. The woff2 is decompressed back to a TTF (`wawoff2`) and passed to resvg explicitly. It is a *variable* font that fontdb collapses to one weight, so hierarchy comes from **size and colour only**, never `font-weight`.
  * **Glyph coverage**: the subset is latin-only and has no `→` (U+2192) — it renders as tofu. Arrows are drawn as **paths**; no glyph outside the subset may be used.
  * **Badge contrast**: chip/badge text picks black or white by relative luminance against a **0.179** threshold (the white/black crossover). A higher threshold silently produced white-on-pale badges for the many mid-bright route colours (`#38BDF8`, `#E1A2AC`).
  * `trazado` in the light catalog is a **flat** polyline (`[[lon, lat], …]`) while the full catalog may carry multiple paths; `toPaths()` detects both. Assuming the nested shape silently emitted every card with no trace at all.
  * Build-time only — nothing here is imported by `index.ts`, so the native resvg binary costs the 512 MB instance no runtime memory. Whole prerender step (352 pages + 352 cards) runs in ~20 s.
* **Sitemaps** are generated into `client/dist` as an index (`/sitemap.xml`) over `sitemap-paginas.xml`, `sitemap-rutas.xml` and `sitemap-estaciones.xml`. Split by type on purpose: Search Console reports an indexed-ratio per sitemap, which is the only signal that says whether the next phase is safe to ship.
* **Canonical tag**: `client/index.html` carries `<link rel="canonical" href="https://transmilenio.onrender.com/">` so any shell served for an unknown path consolidates onto `/` (the SPA fallback still answers unknown paths with the shell at `200`, i.e. a soft 404 — nothing links to those and no sitemap lists them). **Every prerendered page overrides it with a self-referencing canonical**, along with its own `og:url`/title/description and JSON-LD graph — leaving the shell's `/` canonical in place would have Google discover all 352 pages and index none of them.
* **`robots.txt` disallows** `/api/` (JSON for the app, and `/api/troncal/master-catalog` is a multi-MB payload — crawling it burns the 512 MB instance, §5.1.3) plus `/models/` and `/draco/` (binary 3D assets, not needed to render the page).
* **Domain change checklist** (`seo/README.md`): the `ORIGIN` constant in `server/src/prerender_seo.ts` (it stamps every canonical, `og:url`, JSON-LD `url` and sitemap `<loc>`), the `robots.txt` `Sitemap:` line, and the `canonical`/`og:url`/`og:image`/JSON-LD `url` in `client/index.html` — then re-verify in Search Console and resubmit the sitemap.

#### 5.5.5 The route page (`/ruta/<code>/`) and el rutero

A route is bigger than the sidebar panel that used to be the only place to read it. The panel is 360 px wide, it describes the **one** direction currently drawn, and it exists to be read beside the trace. So a route now also has **its own page** at the URL the prerender already publishes — one address for a search result and an in-app navigation alike.

* **One page, one route.** The page draws the route the reader chose and infers no others. It used to gather every list item filed under the same código and render a sign and a stop list for each; the catalog's list items are not a clean partition by código, so a page could end up showing a *different* service's rutero and paradas beside its own. Even where the siblings were genuinely the two sentidos, a page reached from one direction is about that direction — and dropping the shared-panel-width machinery let each sign size itself, so a route whose sibling had a long destination stopped being drawn small to match it. The **prerendered** page is the exception and keeps both sentidos: it is the static page for a *código*, read straight from `catalog.routes[codigo]`, so every variant on it carries that código by construction.
* **Layout — the page is ordered the way a rider reads a route, not the way a database lists one.** A sticky three-column masthead (back · brand · share) under a full-bleed rail in the route's own colour, the crumbs, then a hero: the código as a **plate** at the size it is painted on the bus, the name beside it, the family tag and sistema under it. Then **the rutero**, high on the page, because it is the object a rider on the andén is trying to match — not a section two screens down. Then origen→destino **drawn as the line it is** (two labelled ends with the route's colour running between them; it used to be a sentence with an arrow in the middle, which said the same words and showed nothing), the ficha técnica as one hairline-divided strip read across, and finally the things that change through the day — en vivo, horario — with the paradas last, because that is the long list you scroll to.
  * **Sections are rules and labels, not cards.** Every block used to be the same rounded box, which gave a three-row schedule the same weight as an 80-stop timeline and read as a template rather than as a page. A hairline says "next thing" for the price of one pixel, and it lets the things that genuinely *are* boxes — the trip rail, the live card, a vagón's services — stand out for being boxed. The section label keeps the panel's small uppercase idiom (`.detail-section-title`) with an accent tick in front of it.
  * **The ficha técnica is one strip, not a grid of tiles**: paradas, longitud, servicio, operador, divided by the container's own background showing through a 1 px gap, so a row that wraps on a phone still divides cleanly instead of leaving a border hanging on the first cell of the second row. Cells with no value are dropped, since routes carry different subsets of these facts (many have no operator, zonal ones no length).
  * **The stop list is a line diagram**: numbered down the margin, its spine in the route's colour, the estación links underlined. It drops the sidebar's 320 px cap — that cap exists so a 60-parada route cannot push the sidebar's own controls off screen, and a scroll box nested inside a scrolling page is a trackpad trap.
* **It is a page of *this* site, and it is built from the shell's own parts.** Everything but the rutero was once styled from scratch — a centred hero under a glowing pill badge, bold sentence-case headings, cards on a cyan-tinted wash, a solid `--tm-blue` fill for the primary action that appears nowhere else in the app — and read next to the sidebar it looked like a different product. There is no second design system here: the masthead is the sidebar's brand lockup over the same glass (`.sidebar-header`), section titles are `.detail-section-title`, the count chip is `.route-list-count`, the ficha cells and every action are the shell's `--bg-secondary` + `--border-card` box with its red hover (`.footer-action`), and the hero is ranged left like every other surface. Tokens, not a second palette: every size, radius and colour is a `:root` variable, the few literal `rgba()` values being the ones the panel itself uses for its glass and its chip fill — so the page follows the theme instead of freezing a copy of it. The rutero is the one thing that is *not* borrowed, because it is drawn hardware rather than UI.
* **The subject's own colour carries the page** — `--page-accent`, set on the page root by the shell from the route's línea (`getRouteAccentColor`) or from the estación's red. It paints the rail under the masthead, the código plate, the tick beside every section title, the trip rail and the spine of the stop list, and it is the reason the L-línea's page does not look like the H-línea's. A page never hard-codes a hue; a colour reaching an inline `style` goes through `safeColor()` first (§5.4.3), and the top-of-page wash is a `color-mix` gradient, so a browser without it drops the declaration and gets the same page minus one flourish.
* **One shell, two pages** (`client/src/ui/pageShell.ts`). The route page and the estación page are the same *object* — a real URL rendered over the live map, the shell behind it `inert` + `aria-hidden`, Escape and "Ver en el mapa" to leave, Back/Forward driving it, one masthead, one share action, one `--page-accent`. That plumbing is written once and each page supplies only its path, its accent and its body (spec §1.1 R2); a second copy would be a second answer to "is a page open", "who holds the focus", "does Back close or navigate". The shell also owns **in-app link interception**: an anchor to `/ruta/…` or `/estacion/…` anywhere in the app is a real `<a href>` — it middle-clicks, it copies, a crawler follows it — and only the plain left click becomes a `pushState` navigation between two views that are already on screen. That is what makes a parada on a route page open the estación's page, and a service chip on an estación page open the route's.
* **The page is the interactive twin of the prerendered one** (`client/src/ui/routePage.ts`). It renders *over* the map, not instead of the shell: the map behind keeps the route highlighted and live tracking running, so **Ver en el mapa** is a dismissal, not a reload. Arriving on `/ruta/<code>/` from a search result, the client selects the route from the same path the sidebar's deep-link restore already parses, then replaces the static `#seo-prerender` body — once the bundle is here that body is strictly the worse copy of the same page, so it hands over rather than stacking behind (§5.5.4). While the page is up the map, sidebar and FAB are `inert` + `aria-hidden`, and Escape leaves (§1.1 R5). Opened from an estación page's service chip, the route is selected on the map *after* the page opens: `pushRouteHash` leaves a `/ruta/<code>/` path that already names the selected route alone, so the selection costs no second history entry — and it is what starts the live tracking the page's card is about to show.
* **A deep link opens the page on the catalog, not on the end of boot** (same rule as §5.5.6, and the reason the catalog request is issued before the map is waited on). The page needs *one* route, so the early build is scoped to that código (`buildCatalogRouteList(catalog, { onlyCode })`, matched on the URL slug) rather than walking the whole catalog — the full list build is the boot's heaviest synchronous step. Measured on the deployed instance: the page arrived at ~12 s, and now opens as soon as the catalog does. When the merged list finally exists — ArcGIS geometry folded in, `setRoutes` having selected the route from the same path, live tracking started — the page **adopts** that item in place (`adoptRoutePage` → `refreshOverlayPage`), which keeps a reader who has already scrolled into the paradas where they were. `openRoutePage` still covers the case the early build found nothing, e.g. a código only ArcGIS knows.
* **Reached from the panel, not instead of it.** The sidebar detail keeps today's behaviour and gains one **Ver página de la ruta** link — a real `<a href>`, so it middle-clicks and copies, with the left-click intercepted for a `pushState` navigation. Browser Back closes the page and restores the map's own `#/r/<code>` deep link; opening the page from a URL that already names it does **not** push, or Back would hit a duplicate entry instead of leaving.
* **One renderer per fact, across three surfaces.** `ui/routeDetail.ts` holds what the panel and the page both show — the horarios table (parsed windows, §5.6.2), the service-status chip, the stop timeline, the live card, the family/system labels. `updateLiveBusStatus` paints **every** `.live-tracking-status` on the page from one fix, so the panel and the page can never report different bus counts (§1.1 R2).
* **El rutero — the LED destination sign, drawn as LEDs** (`shared/rutero.js`). The sign above a TransMilenio windscreen is how a rider on the andén decides whether the bus pulling in is theirs, and no other surface here could show it. It is **not** text in a condensed typeface: it is ~1 300 discrete LEDs, and a web font gets the words right and the object wrong.
  * **The grid is measured, on a photograph that resolves individual LEDs** — including the *unlit* ones, which is what makes the lattice fittable instead of inferred from lit strokes: *"2019 Bogotá – Estación Parque Tercer Milenio…"*, Felipe Restrepo Acosta, CC BY-SA 4.0, Wikimedia Commons, 5006×3338, near-frontal, sign reading "Hola TransMiCable". Autocorrelation of the column profile peaked at lags 9/17/26, a comb fit pinned pitch and phase, and each letter was sampled on its own vertical phase so the sign's tilt could not smear a row:
    * dot pitch **8.68 px horizontal, 8.70 px vertical** — a square lattice;
    * **cap height 11 rows** — the stems of H, M, C and T span 96–98 px, i.e. 11.05–11.28 pitches;
    * **strokes are 2 dots** — every stem 2 columns, every bar 2 rows;
    * **caps are 6 columns** (H, C) on a **7-column advance** (H→o and o→l both measure 7). M is 7 columns and `l` is 2 on a 3-advance: the real face is **proportional**, and we render fixed at 6, the dominant cap width. M and W are the two letters that costs.
    * This corrected the first pass, which read the 2-dot stems as 1-dot and landed on 5×11 on a 6 advance — too light and too narrow. The reconciliation is exact: the "3 px stem at 9.3 px character pitch" measured off the low-res catalogue *is* a 2-dot stem at 1.33 px/dot on a 7-column advance.
  * **`TmRuteroCatalog/` — six 130–195 px crops of screenshots of photographs** — cannot resolve a lattice, but it is the record of the fleet this app describes and it settles what the reference photo cannot: **ALL CAPS with no diacritics** (the F23 unit reads "PORTAL AMERICAS" — legible at any blur, and it *contradicts* the manual below, so it is an observation rather than an inherited assumption); **white** LEDs ≈ `rgb(200,220,228)` on a panel near `rgb(8,15,25)`, which the manual also mandates — though **amber units are in service too**, including articulated troncales, so white is what we draw rather than the only colour that exists; a panel of about **20 characters**, a character *count* rather than a measurement; and the layout rule below, which is a ratio *inside one image* and so immune to scale and perspective. A second Commons photo (*"Bog - Bus TransMileni dando la curva Avenida 30"*, CC BY-SA 3.0) shows a live route display reading `J16 CC SANTAFE`, confirming casing and layout on hardware other than the catalogued units.
  * **H, C, T and M are transcribed off the reference photograph; the rest of the table is drawn to match their construction** — one promotional message does not contain the alphabet. A photograph of a *route* display at that quality is what would let the remaining glyphs be re-cut against ground truth.
  * **Four elements draw the whole sign.** Two-dot strokes put ~720 lit LEDs on a full panel; as `<use>` pairs, plus ~1 900 dark dots as elements, that is more nodes than the rest of the route view combined for something the eye reads as texture. The unlit lattice is a one-tile `<pattern>`, and the lit lattice is a single path of zero-length subpaths (`M<x> <y>h0`) that a round line cap renders as discs — stroked twice, wide and faint for the bloom, narrow and bright for the cores. Six characters per dot against the ~55 an arc pair costs: **5.9 kB** per sign versus 85 kB drawn with real circles (§1 priority 2).
  * **The front panel only.** A side/rear sign was drawn here for a while, from the manual's rule that it carries the código alone, always centred (`ManualDeIdentidad.pdf` p. 49). It was removed on the maintainer's reading of the real fleet: **the side signs are not one thing** — different buses carry visibly different ones, so any single drawing of "the" lateral rutero asserts something about a bus that isn't true (§1, Certainty). The front panel is consistent enough across the fleet to draw; that one is not. Do not reintroduce it from the manual alone.
  * **Layout rule, also read off the photos**: código flush left, destination centred on the **whole** panel, shifted right only far enough to leave one blank column after the código. That reproduces both the single space measured in "M83 MUSEO NACIONAL" (4 px) and the ~2.5 in "D21 PORTAL 80" (25 px) with no special-casing. A pair too long for 20 characters **widens** the panel rather than truncating — a rutero that drops the tail of a destination is a wrong answer, and no real one does it; they scroll. Every sign on one page then takes that same width: a rutero is fixed hardware, and per-direction sizing drew ruta 1's two sentidos at visibly different scales.
  * **The sign words a destination shorter than the catalog does** (`ruteroDestination`, `SIGN_DESTINATIONS`). A terminus carries its sponsor or its qualifier in the catalog — `Toberín- Foundever`, `Héroes - Colmena Seguros`, `Polo - FINCOMERCIO`, `Universidades CityU`, `Alcalá - Colegio S. Tomás Dominicos`, `Pradera - Plaza Central`, `Tibanica - Primavera` — and none of it reaches the panel: the bus is signed `TOBERIN`, `HEROES`, `POLO`, `UNIVERSIDADES`, `ALCALA`, `PRADERA`, `TIBANICA`. Applied inside `ruteroLayout`, so the two surfaces that draw a sign (route page, prerendered twin) and the shared panel width are all measured on what actually lights. Keyed on the folded, punctuation-free name — a catalog that adds or drops a space still matches — and deliberately a **list of answered cases rather than a rule that strips after a dash**: `Guatoque - Veraguas` and `AK 68 - CL 12A` are whole names, and shortening them would be exactly the invented answer this file exists to avoid (§1). The figcaption and the `aria-label` keep the catalog's full name, which is the station's real one.
  * **The signs print no diacritics.** The photographed F23 reads "PORTAL AMERICAS" for a destination the catalog spells "Portal Américas", so `normalizeRuteroText` folds the accents — keeping only the tilde that makes Ñ, which is a letter with its own glyph — and maps anything with no glyph to a blank cell (then re-collapses, so a dropped `·` leaves no hole).
  * **The brand manual is a source, not the authority** (`ManualDeIdentidad.pdf`, TRANSMILENIO S.A. 2016, *Vehículos* volume, pp. 48–49 "Información exterior · Páneles Electrónicos"). It confirms three things and contradicts two, and the contradictions are deliberate:
    * **Confirms**: content is "la nomenclatura de la ruta y el destino final de la misma"; "se debe mostrar en leds de color blanco sobre fondo negro"; no transitions or fragmentation (the panel is static, never scrolling). Front unit minimum **1750 × 250 mm**, legible from 100 m day and night.
    * **Contradicts, and reality wins**: the manual mandates text **aligned left** and in **"mayúscula inicial"** (Title Case), and lists centring among the prohibited uses. Every photographed unit is ALL CAPS with the destination offset from the código. The manual is from 2016 and the buses do not follow it; this surface exists so a rider can match the page against the bus in front of them, so it follows the bus. Do not "correct" the casing or the layout to the manual.
    * **Names no typeface** for these panels. Its two mockup faces are not the hardware's: `DotMatrixBold` is referenced by name and **not even embedded** in the PDF, and its metrics (avg cap 623 / cap height 697 = 0.89) are wider than the photographed letterforms, as is `Advanced_LED_Board-7`. `InfoDisp Bold` — the obvious candidate — is assigned to the *interior printed* esquemas de ruta (105/54/42 pt, `InfoDisp Medium` 42/31 pt), not to the ruteros, and at avg cap 507 / cap height 670 = **0.76** against the photographed ≈0.45 cell it is about twice as wide relative to its height, with stems ~2.2 dots where the photos show 1. It is also a commercial FontFont present here only as a 7.3 KB subset. Hence the hand-authored bitmap: nothing to inherit, and nothing licensable to ship.
    * Also useful from the same volume, should any of it ever be needed: printed ruteros are Helvetica Neue LT Std 77 Bold Condensed at 500×500 mm (urbano/complementario) and 500×350 mm (especial); service-level names on the flank are Futura Bold Condensed; body paint is Pantone 186 C / RAL 3028 (troncal, with a 116 C top stripe), 7469 C / RAL 5017 (urbano), 349 C / RAL 6029 (alimentador), 165 C / RAL 2004 (complementario), 202 C (especial).
  * **Only the fleets that carry one get one** (`carriesRutero`, on the catalog's `tipoServicio`): `TRONCAL` (including the number-coded rutas fáciles) and `PADRON`. Alimentadores and the SITP zonal fleet carry a different sign and get none — drawing this one for them states something untrue about a bus (§1 Certainty). The predicate is gated **per variant, never on `variants[0]`**: a código can exist in both networks at once (`7` is a ruta fácil *and* a zonal service) and which lands first in the catalog is not a fact about the fleet.
  * **Cost**: the ~1 400 *unlit* dots are one `<pattern>` tile, not 1 400 nodes; each lit LED is a single `<use>` of a halo+core group (~360 per sign).
* **`shared/rutero.js` + `shared/rutero.d.ts` — plain ESM with a declaration sidecar, deliberately.** The website (Vite) and the prerender (tsx, `server/`) both draw this sign, and their tsconfigs each pin `rootDir` to their own `src`; a `.ts` file outside both fails **TS6059** on both sides. A declaration file is never emitted and so is not bound by `rootDir`, which leaves every call site fully type-checked while one implementation serves both. This is the pattern to reach for the next time the two packages must share logic — prefer it to the copy `isZonalService` still lives with (§5.5.4).
* **Alimentador is not a padrón** (`buildCatalogRouteList`, `main.ts` → `onRouteSelect`, `routeDetail.ts`). `isDual` is partly a heuristic — a route touching both estaciones and paraderos (`routeHasDualStops`) — and a feeder that runs to a portal trips it. Resolved in the old order, alimentador `1-1` came out `subType: 'dual'` and every surface reading it called the feeder a padrón ("Ruta Dual" in the panel, "TransMilenio Dual · PADRÓN" on the page). A service the catalog *names* `ALIMENTADOR` is one, whatever stops it happens to serve, so alimentador now wins over the dual test in all three places — and it is named **TransMilenio Alimentador**, not "SITP Zonal": they are TransMilenio's own buses, and naming the wrong operator tells a rider the wrong door to wait at.

#### 5.5.6 The estación page (`/estacion/<slug>-<codigo>/`)

The map popup is a card *over* a station: 340 px wide, floating on the thing the reader is looking at, gone on the next click. It has to abbreviate — the plan scrolls sideways inside it, the services are a wall of chips, and there is no room at all for the two facts that describe an estación beyond its routes. So an estación has **its own page**, at the URL the prerender already publishes (§5.5.4), built on the same shell as the route page (§5.5.5) and reached the same three ways: a search result, a shared link, and the popup's own button.

* **Reached from the popup, not instead of it** (`stationPageLinkHtml`, `layers/stations.ts`). The card gains one **Ver página de la estación** link, rendered **inside** the popup's sticky footer (`planActionsHtml`'s `lead`), above `Desde aquí / Hasta aquí`. Inside, not beside: a station popup carrying a platform plan is about 2.5× the height of its scroller at every portal — which is why the planner buttons are pinned there in the first place — so a link left in the flow sat below the fold on exactly the stations that most need a page of their own. It is built from the **catalog** stop, never from the rendered ArcGIS station: the URL is the one the prerender publishes and its slug is the catalog's own name and code, so a verified-split platform (Av. Jiménez, Ricaurte) links to the page for the stop both of its platforms belong to, which is the page that exists (§5.4.1). Opening the page closes the popup — two copies of one station on screen would also mean two live-arrivals slots for one stop code, and the shared renderer fills the first it finds (`layers/arrivals.ts`). Leaving the page re-opens it, so the round trip is where the reader was.
* **The page is coloured by the troncal the station sits on** — Autonorte green, Caracas navy, Carrera 7 purple (`TRONCAL_COLORS`, §5.4.3) — feeding the same `--page-accent` a route page fills with its own línea. It is not decoration: it is the fact a rider already reads off the corridor's signage and off every código serving the platform, and it is what stops 139 estación pages from being one page with the name swapped.
  * **The corridor is answered, not derived** (`stationCorridor`, `services/station_plan.ts`; `data/station_corridors.json`). ArcGIS's own `troncal_estacion` is a station label that does not always name one corridor — Museo Nacional reads `CR 7-10`, which is two of them — and the nearest corridor centreline is wrong exactly where it matters most, since three of them pass within metres at Av. Jiménez. The file already carried the official station-maps corridor per station (it is what names each platform's sentido, §5.5.4); it now also carries **corridor name → troncal letter**, joined from ArcGIS `letra_trazado_troncal` on `consulta_trazados_troncales` (20 trazados, 12 distinct corridors). Every name matched, accent- and case-folded, with one alias — `Autonorte` = `AUTOPISTA NORTE` — and TransMiCable matched nothing because it is not a troncal and has no letter.
  * **Shipped as data on the light catalog** (`station.corridor = { nombre, letra }`), like `vagonLabels` and `wagonPlan`: the page, the prerendered twin and any future surface read one answer instead of each re-deriving a corridor. A station with no corridor on file falls back to the red the station layer is drawn in rather than being assigned one.
  * **A corridor the station-maps API has not published yet is filed by hand** (`_meta.manual` in `station_corridors.json`). Those markers still number 153 and carry nothing for the Bosa–Tibanica stations, so `Av. Ciudad de Cali` is entered directly for `90009`/`90010`/`90011` with letter **Z** — the letter its services carry, which shares the Américas red (§5.4.3). Without it the three newest pages were the only ones in the set with no corridor line under the título. The entries are listed in `_meta` precisely so they can be removed once the API carries them.
* **Which nodes are estaciones is answered by the register** (`npm run sync:stations` → `data/troncal_stations.json`; `station_registry.ts`). The file joins every station in ArcGIS `consulta_estaciones_troncales` to the catalog stop that carries its routes, recording *how* each pairing was made (`node-id` 137, `name-and-distance` 7 within 450 m, `distanceM` per row) so a wrong pairing is visible in the file rather than shipped silently. Three gates keep a street stop from being promoted: a TM-coded candidate always outranks a zonal-coded one at the same station; a non-TM candidate must be within **150 m**, because SITP paraderos are named after the station they stand at ("SENA - NQS" sits 342 m from the SENA platform, "Estación Calle 63" is the paradero outside it); and it must actually be served by a `TransMilenio` route. Nine register stations pair with nothing — the catalog has no counterpart for them — and are listed in `_meta.unmatched` rather than matched to something nearby. **A new station is therefore a data refresh, not a code change**: `npm run sync:stations` + `npm run sync` and it has a pin, a popup, a page, an OG card and a place in the app's `Cerca`. Calle 72 is the worked example: it sat in `_meta.unmatched` as `09122` for as long as the Metro works kept it shut, and reopening it on **2026-08-25** took one sync and one `sync:stations` — node `9122` paired with the catalog's new `TM0002` at 23 m, three vagones, Caracas, no code touched. The three `TZ022` stations have no corridor and no plano yet (that corridor is absent from `consulta_trazados_troncales`, and the station-maps API still lists 153 markers without them), so they take the red fallback above and no vagón numbers — neither is invented (§1).
  * **Marked with the colour, never set in it.** Half this palette is dark (Caracas `#0C3A95`, Carrera 7 `#852D89`), so a corridor name printed in its own colour on this page's near-black is a name nobody can read. The name keeps `--text-secondary` and takes a dot in the corridor's colour beside it; the rail, the accent ticks and the código chip's border carry the rest.
* **The URL's código is whatever follows the last hyphen, never a `TM…` shape** (`parseStationPathname`). The slug is built as name + `-` + código, so the shape test that used to parse it returned *nothing* for `/estacion/laureles-90010/` — the three estaciones whose codes are not TM-coded (§5.5.6) therefore never opened their interactive page at all. What the reader got instead was the prerendered body left in place, with the fallback "Ver en el mapa" bar that exists for a station this catalog cannot describe — a black bar no other estación page shows, and none of the live sections (llegadas, demanda, the route links) ever reached. An unknown código still resolves to null one step later in `getStationPageData`, which is where "no such station" belongs.
* **The map joins an ArcGIS station to its catalog stop by the register's node id first** (`resolveByRegistryNode`, `station.nodo` on the light catalog). The heuristics behind it — same id, then same name within 450 m — cannot pair a station the two sources spell differently: the register says `Los Laureles`, the catalog says `Laureles`, their ids live in different spaces and the points sit 98 m apart, so that pin opened an empty popup while its two services sat in the catalog one word away. The registry already computes that pairing offline, so it travels on the catalog instead of being guessed at a second time in the browser.
* **A deep link opens the page on the catalog, not on the end of boot.** A visitor arriving from a search result is the reason these pages exist, and they used to wait for the whole boot — every ArcGIS layer, the route list, four GeoJSON sources and the map style — before the interactive page replaced the static body: ~12 s on a warm free-tier instance and worse on a cold one, spent looking at the copy without the live board. Everything this page draws is catalog data, so the catalog request is now issued **before the map is even waited on** (its promise is reused by the parallel boot fetch, so nothing is requested twice) and the page opens the moment it lands — 0.8 s locally against 3.7 s for full boot. The three facts that do come from ArcGIS (WiFi, biciestación, and the node id the ridership dataset is keyed on) are patched in by `refreshStationPage()` once the station layer resolves, so nothing is lost by opening early. The map underneath still recentres on the station at its first idle, which is what makes dismissing the page an arrival rather than a search.
* **Catalog-first, exactly like its prerendered twin** (`getStationPageData`). Wagons, plan and plate numbers all come from the catalog stop, so the page a crawler reads and the page the bundle draws describe the same platform; the rendered ArcGIS station only *enriches* it (corridor name, WiFi, biciestación) and can never subtract from it — a station whose ArcGIS point failed to load still has a complete page (§4.2).
* **The plan scrolls like every other horizontal row in this app** — hidden scrollbar, a mask fade at whichever edge still has content behind it, wheel and mouse drag, all from the shared `initChipRowScroll` (`ui/chipRow.ts`, §5.4.2b), wired on both the popup and the page. A native scrollbar under a drawn platform diagram reads as a browser widget resting on the drawing, and the four background gradients that faked the cue before it had to be re-pointed at every surface the plan was ever placed on (popup `#121212`, page `--bg-primary`); a mask needs no background at all. The container keeps `role="group"` + `tabindex`, so arrow-key scrolling is unaffected.
* **One renderer for the plan, at two sizes** (`buildStationWagonView`). The popup and the page draw the same platform diagram and the same wagon sections from one function, returned in parts so each surface can frame them its own way — the popup stacks them in one card, the page gives the plan and the service list a section each. Every dimension in that drawing is a multiple of `--tm-scale` (the map's own popup scale), so the page raises **one variable** to 1.3 instead of restating the diagram (§1.1 R2). Two renderers would be two answers to which vagón a service boards from.
* **What only the running app can add.** The live **Próximos a llegar** board (`/api/stop-arrivals`, §5.5.1) and a **Demanda** strip: mean weekday validaciones with entradas/salidas and the station's rank, from the open Salidas dataset (`/api/station-demand`, §5.8). The dataset is fetched at most once per session and filled into the page in place rather than by re-rendering it — a re-render would reset the arrivals slot to its placeholder and ask for a board the reader is already reading.
  * **The figure carries its own window.** A ridership number is a measurement *of some days*, and which days is part of the number: the dataset is a rolling mean regenerated whenever the upstream Salidas window advances (§5.5.1), so the note under the strip reads "Promedio de 15 días hábiles entre el 23 jul 2026 y el 13 ago 2026" from the endpoint's own `days` and `window`, never a bare "promedio de días hábiles". The dates are formatted **by parts**, never through `new Date('2026-08-13')` — that is read as UTC midnight and printed in the reader's zone, so the same string renders as the 12th for everyone west of Greenwich, which is the entire audience.
  * **Matched on the node id, or not at all.** That is the only identifier the Salidas dataset shares with this app: its `codigo` is the operator's own numbering (`05000`), not the catalog's `TM…`, and the names differ between the sources ("Portal Norte – Unicervantes"). No node match, no section — an approximate name match would print another station's ridership under this one's name (§1 Certainty), and an empty "Demanda" heading would read as "this station has no ridership" rather than as the missing row it is.
* **A service chip is the way out to a route.** The chips are the same tags the popup draws, so they carry the código already; here they open that route's page rather than selecting it on a map the reader cannot see. On a page they are also the *only* way out, so they are promoted to something a keyboard can reach and a screen reader can name (`role="link"`, `tabindex`, Enter/Space — §1.1 R5). That promotion lives on this surface, not in the shared renderer: in a popup the tag is a click target inside a card the pointer is already on.
* **Planner actions dismiss without handing the station back to the map**: re-opening its popup on the way out would fight the planner panel the reader just asked for (`dismissOverlayPage`, §5.5.5).

#### 5.6.2 Service schedules (not every route runs at every hour)

Journeys are planned **for a moment in time**. Every route carries its own operating windows, and the planner uses them for everything it can: the trip's real clock times, the wait for the first bus, the "this route is closed now" label, and — the point below — a ranking preference for services that run most of the day.

What it does **not** do by default is delete connections. Schedule enforcement is **opt-in** (`enforceSchedules`, "Solo en servicio" in both UIs): a rider planning tomorrow's trip, or reading a `horarios` row we parsed from an imperfect upstream feed, is better served by a labelled itinerary than by an empty panel. The counterweight, so that "optional" does not mean "ignored", is that **long-running services outrank short ones in every search** — a route open 4:30 a.m.–11 p.m. is a usable answer if the rider is slow, misses a bus or comes back later; a 2 h peak-only shuttle is a trap even while it is open.

* **Source** (`horarios` from `infoRuta`, §5.1.2 — carried through `getCatalogLight()`, so both clients already have it, no API change): every one of the catalog's 1054 route variants ships `horarios.data` (2333 rows). `convención ∈ {L-V, L-S, S, D, D-F, L-D}`; hours are 12-hour strings, some zero-padded (`04:00 AM`), some lowercase (`2:00 pm`); **168 rows close after midnight** (`12:30 AM`).
* **Parser** (`parseServiceSpans`, `client/src/services/schedule.ts` — shared by both clients and the router): each row becomes `{ mask, start, end }` in minutes from midnight. A row whose end is **not after** its start closes the next day (`end += 1440`), never a zero-length window. Duplicate rows collapse (182 in the catalog). A route whose hours cannot be read at all yields `undefined` = **unknown schedule = always operating**: a parse gap must never hide a real service (spec §1 certainty, §4.2 degradation).
* **Day masks**: one bit per weekday plus a dedicated `FESTIVO` bit. On a holiday the weekday bit is deliberately **not** set — Bogotá runs holiday service on a holiday, so an `L-V` window must not apply on a Monday festivo. A route that files no `D-F`/`L-D` row but does run Sundays falls back to its **Sunday** window on holidays (the local convention), so holidays never read as "the whole city is closed".
* **Festivo calendar** (`isFestivo` / `festivoName`): computed, not tabulated, so it never expires — six fixed dates, the seven Ley 51 de 1983 ("Emiliani") dates observed the following Monday, and five Easter-relative dates (Jueves/Viernes Santo, and Ascensión/Corpus/Sagrado Corazón at Easter +43/+64/+71, already Mondays). Easter via Meeus/Jones/Butcher. Verified against the published 2026 calendar (18 festivos, exact dates).
* **Clock**: schedules are Bogotá local time, and the device may be anywhere, so the planning moment is resolved in `America/Bogota` (`Intl`, fixed −05:00 fallback) and carried as plain wall-clock fields (`PlanTime`) — never a `Date` a host time zone could shift.
* **Router** (`services/router.ts`): `RouteSearchParams.departAt` (default **now**) makes the search time-dependent. Windows are evaluated over three days (−1/0/+1) so a 00:20 departure still sees the previous day's `…–12:30 AM` window.
  * Every boarding is timed against the route's own window at the moment the traveller *reaches* that stop. Arriving shortly before the first bus is normal, so a wait of up to **30 min** (`SCHEDULE_OPENING_WAIT_MAX_MINUTES`) is allowed and charged as real time in both the cost and the displayed total. A boarding the window cannot cover at all is tagged `outsideService` — and **dropped only when `enforceSchedules` is set**. The two modes annotate identically; enforcement changes what is offered, never what the rider is told about it.
  * **Long-service preference** (`FULL_SERVICE_DAY_MINUTES` 18 h, `SERVICE_COVERAGE_PENALTY_MINUTES` 8): each boarding pays a penalty of `8 · (1 − coverage/18 h)` minutes, where *coverage* is the route's operating minutes clipped to the plan day (`serviceMinutesOnPlanDay`, resolved once per route per search). It is charged in **cost, never in the reported time** — the itinerary duration on screen stays a real estimate; only the ordering changes. Bounded by construction (≤ 8 min × 4 boardings = 32) so it stays strictly inside the secondary term of every §5.6.1 criterion and cannot overturn a transfer or walked-meter optimum. An unknown schedule counts as a full day, so a parse gap never demotes a route. `sortJourneyPlans` ranks on `totalTime + servicePenalty` for the same reason — otherwise each re-rank (walking enrichment) would silently undo the preference.
  * Continuing a ride is never re-checked — only boardings are, since a bus already boarded finishes its run.
  * **Performance**: a route already running and open through a **150 min** horizon (`SCHEDULE_FAST_PATH_HORIZON_MINUTES`) is marked once per search and skips the interval scan entirely; boardings past that horizon are always checked exactly, so the shortcut cannot wave a rider onto a bus after its last service. Measured on the committed catalog: the schedule work costs ~5–15 ms over a schedule-blind search (20–30 ms without the shortcut), keeping typical trips inside the §1 sub-100 ms budget. Coverage adds one memoised value per route touched, i.e. an array read per boarding.
  * **Annotations** per ride step: `startMinute`, `boardMinute`, `serviceWait`, `serviceEndMinute`, `outsideService`, `serviceDayMinutes`; per plan: `departMinute`, `arriveMinute`, `serviceWait`, `outsideService`, `lastServiceRisk` (a boarding within **20 min** of that route's last service), `servicePenalty`, `shortService` (some ride runs ≤ `SHORT_SERVICE_DAY_MINUTES` = 10 h). `resolveWalkingLegs(plans, sortBy, departAt)` (§5.6.4) re-runs them after real OSRM walking times land, so a card can never show a clock time the route's own window no longer covers.
  * **Never a dead end**: an *enforced* search that finds nothing re-runs with the filter off and returns those itineraries **tagged** `outsideService`, each ride carrying its real window, instead of an empty result. The default search cannot hit this — it never filtered.
  * **Known modelling limit**: labels are kept per (node, arriving route) by *cost*, so under the `transfers`/`walk` preferences the window check uses the cost-optimal label's arrival time; a strictly earlier but costlier label is not retained. Exactness there would need full Pareto labels. Under `time` (cost = time) the search stays exact.
* **UI/UX** — website (`ui/planner.ts`, `index.html`) and app (`client/mobile/src/views/planner.ts`):
  * A **Salida** control: `Ahora` (default, no input) / `Otra hora`. Behind `Otra hora` the moment is set by **tapping, not typing** — a day row (`Hoy · Mañana · sáb 8 ago …`, a week ahead, horizontally scrollable) over a clock flanked by **−15 / +15** steppers that roll the calendar day when they cross midnight. A native `<input type="date">` stays as the source of truth for the date and is revealed only by the trailing **`Otra fecha…`** chip, so a day outside the week (or a restored deep link) is still reachable and still gets its own chip. Reaching a departure two days out used to mean typing a full `dd/mm/yyyy` into a native field, and nudging a trip half an hour meant editing it again.
    * **Festivos are marked in the row itself** (dot + `Festivo · <nombre>` tooltip): a holiday runs a different service (§5.6.2 day masks), and that is the most common reason an expected itinerary does not exist — the rider sees it before planning, not after an empty result.
    * The hint line always resolves the moment to a day, **how far away it is**, and **which service applies** ("mié 5 ago, 4:30 p.m. · en 2 h 10 min · servicio de día hábil", or `servicio de festivo (Batalla de Boyacá)`). A moment already behind the Bogotá clock is planned as asked but flagged `ya pasó` in amber — never answered silently as if it were the trip the rider meant (§1).
    * The day options, the offsets, the service-day label and the hint string are one shared module (`client/src/services/departure.ts`, imported by the app as `@shared/services/departure`) — both clients had their own `serviceDayLabel` copy, so the same instant could be described two ways (spec §1.1 R2).
  * A schedule-filter control: off by default (every connection, each labelled with its own schedule); on = the hard filter. Website: a single **Solo rutas en servicio** toggle chip folded into the Salida block — it filters *by* the departure moment, so the two are one control group — mirrored into the deep link as `s=1` (the default stays out of the URL). App: a `Todas las rutas` / `Solo en servicio` chip pair in the same options block.
  * Each result card shows the real **clock range** (`4:30 a.m. → 6:22 a.m.`, marked `(mañana)` past midnight) plus chips: `Espera N min por apertura`, `Último servicio`, `Fuera de servicio`, `Servicio limitado` (the ride the long-service preference penalised).
  * The expanded timeline shows a clock per step, the window in effect (`Último servicio 10:55 p.m.`), the opening wait, `Opera N h ese día` for a short service, or — for an out-of-service ride — the route's full schedule in red.
  * When everything is closed, a banner explains why and offers **one concrete recovery**: "Ver opciones desde 4:30 a.m.", computed as the earliest departure that puts every ride of some plan inside its own window (referenced to stop arrival, so it introduces no residual wait). Clicking it re-plans at that moment.
  * **An empty search names its own cause and hands over the undo** (both clients). "No se pudo encontrar una conexión … con los filtros actuales" named no filter and offered no way out. A search comes back empty for exactly one of three reasons, and each is stated with its own action: a **mode filter** (`Solo TransMilenio` / `Solo SITP`) → `Buscar en toda la red`; **`Solo rutas en servicio`** → `Incluir rutas fuera de servicio`; otherwise neither endpoint has a stop inside the router's `ACCESS_SEARCH_RADIUS_M` (1.5 km) or no itinerary exists under `MAX_TRANSFERS` — stated as such, with the map-pick suggested. The button lifts the constraint (flipping the real control, not a hidden copy of it) and re-plans. A failed calculation likewise ends in a **`Intentar de nuevo`** button, not the sentence "inténtalo de nuevo".
  * Route detail (both clients) shows an **En servicio / Fuera de servicio** chip with the next boundary, and the schedule table is rendered from the parsed windows — the same data the planner enforces, so the panel can never contradict the itineraries.
  * Deep link: `#/plan?…&t=YYYY-MM-DDTHH:mm` restores a trip planned for a specific moment; `Ahora` stays out of the URL so a shared link is always current.
* **Tests**: `tests/schedule.spec.ts` (parser shapes incl. post-midnight, the 2026 festivo calendar, holiday vs weekday service, plan-day coverage, and the router's wait / last-service / out-of-service / unknown-schedule behaviours, the optional filter, and the long-service ranking).

#### 5.6.3 The trace is the network (a bus drives its `trazado`, not a straight line)

Every route variant ships `trazado` — the polyline it is actually driven along — and **99.0%** of the 1031 presented routes have one. The planner used to ignore it in both places it mattered, and both showed.

* **What was wrong.**
  * *Cost.* A ride leg was charged the straight-line distance between two consecutive stops. Against the trace that under-counts the driven metres by a mean **8%** (troncal) / **11%** (zonal) — but not by a constant: per leg the ratio runs 1.00×–1.36× at p90 and past 2× in the tail. The cruise speeds had been calibrated to absorb the average, so a winding SITP loop was priced exactly like a straight avenue and won rankings it should have lost. No single constant can fix a spread like that.
  * *Geometry.* `sliceRouteGeometry` cut the drawn leg out of the trace by **nearest vertex**, scanning every vertex of every path per step, choosing between paths by summed endpoint distance, and forcing direction by comparing vertex indexes and reversing the slice. On the browser's transport-capped traces (§5.1.4) vertices are hundreds of metres apart, so the drawn ride began a mean **305 m** — p90 861 m, worst **1.4 km** — from the station the rider boards at. That is the "horrible merge with the walking paths": each step is drawn as its own `LineString` (`layers/journeyLayer.ts`), so the walk leg ended at the station and the bus leg started most of a kilometre away, as two disconnected pieces.

* **The fix** (`client/src/services/trace.ts`, one index per route, built once in `initRouter`): project the route's stops **onto its own trace, in order**, and let everything downstream read that index — ride distance is a difference of along-the-line positions, ride geometry is a slice between two projected points, and both are O(1) per leg instead of a scan per step. Graph edges carry `fromOrd`/`toOrd` (the stop's position in its route's list) rather than being matched back by coordinate, so a loop route that visits one code twice can no longer slice an arbitrary pass.
  * **Monotone by construction.** Stop *k+1* may not land before stop *k* (30 m of tolerance for opposite kerbs). Independent nearest-point snapping is exactly what breaks on the loop routes that are most of SITP, where the outbound and return legs run down the same street metres apart.
  * **Loops are rotated to the first stop.** The catalog does not promise the polyline starts where the stop list does: route 97's first stop sits 26.2 km into its own 45.3 km trace, route 91's 30.3 km into 60.8 km. Read forwards from vertex zero, every stop before the wrap looks like a backtrack. A trace whose ends meet within 400 m is re-cut to begin at the first stop.
  * **Direction comes from the stops.** One `trazado` per variant, with no promise it points the way the variant is ridden — so a dozen sampled stops are projected and the line is reversed if they descend it.
  * **Multi-path traces keep the catalog's order** (8.9% of traced routes ship several pieces); only each following piece's orientation is chosen, by whichever end continues from the last. Choosing pieces by proximity to the first stop instead reordered the trace into a journey nobody drives and cost four in ten multi-path routes their trace.
    * **A wide joint is not a joint.** 31 of the 109 joints in the catalog are over 200 m and five are over a kilometre: those pieces are disjoint branches, not one line cut in two. Welding them invents a straight segment kilometres long — and since ride distance is read off this line, that fiction is charged to any leg spanning it *and* drawn across the map. Pieces are therefore split into runs at every joint over `MAX_JOINT_GAP_M` (200 m) and the **longest run wins**; stops on the discarded branches fail the per-stop gate and their legs fall back. Part of a route's trace beats all of it plus a fiction.
  * **Gating is per leg, not per route.** One stop that does not sit on its trace is ordinary catalog noise; rejecting the whole route for it threw away every other leg too and cost 183 routes their trace outright. A stop past `MAX_SNAP_ERROR_M` disables only the two legs touching it; a trace matching under 60% of the stops is refused entirely. A route with no usable index falls back to the straight line and the stop chain — i.e. exactly the old behaviour, never worse.
    * A **leg** is refused by its **detour** — how far the trace runs beyond the straight line (`TRACE_EDGE_MAX_DETOUR_M`, 5 km) — with a loose ratio arm (`TRACE_EDGE_MAX_RATIO`, 12×) behind it. A ratio bound cannot tell a real detour from a broken projection, because it depends on how close the two stops happen to be: it condemns a feeder looping 2 km between neighbours while waving through an express leg wrong by kilometres. Across the 39 830 trace-measured legs the detour is 20 m at the median, 758 m at p99 and 3.2 km at p99.9, then jumps to 13.8 km — a clean separation between "the bus went round the block" and "the projection jumped".
    * A ride is **drawn leg by leg, exactly as it was charged**: a traced leg contributes its slice of the trace, a refused one the straight line the search paid for it, appended from wherever the previous leg ended so the ride stays one continuous polyline. Drawing *through* a refused leg is what puts metres on the map the itinerary does not charge — that gap reached 55% of a ride's reported distance before the trace work — but refusing the whole ride for one blemished leg overcorrected: measured over 260 planned trips, **11.7%** of ride steps and **11.6%** of all ride metres came out as a straight chain between stations, and the median one of those had **71%** of its own legs individually traced. A trunk ride down a curved busway drawn as a ruler line across the city is the defect the rider actually sees. Per leg: **4.3%** of ride steps and **2.8%** of ride metres, and what remains is a route with no usable trace at all rather than one whose trace was thrown away. Drawn-over-charged distance per ride step stays 1.000 at p50/p90 (worst 1.026 — the ≤ `MAX_SNAP_ERROR_M` connector where a traced leg hands over to a straight one).
    * `MAX_SNAP_ERROR_M` is **100 m**, and it is set by what can appear on the map rather than by coverage: trace coverage is flat at 93.1% of ride legs anywhere in 80–220 m (the per-leg gating absorbs the difference), while the worst drawn gap tracks the tolerance one-for-one — 160 m admitted a 158 m gap, 100 m admits 99 m. The headroom over the 17 m 99th percentile still covers a platform whose pin sits off the busway.
  * **The rider is told when the shape is not the route's** (`JourneyStep.traceSource` = `trace` / `partial` / `estimate`, `JourneyPlan.traceEstimated`) — the exact analogue of §5.6.4's `walkSource`, and **per step**, because a ride drawn leg by leg can genuinely be part real trace and part straight line. The website shows a `Trazado aproximado` chip on the card and names the case under the step (`Trazado parcial · algunos tramos se dibujan en línea recta entre paradas` / `Sin trazado oficial · …`); the app shows the same chip and step note. A straight line across the city was otherwise indistinguishable from the route's real shape, which §5.7 #8 already forbids and only the walks were honouring. The cable carries no flag: its straight span between stations **is** its shape.
  * **What the remaining fallbacks are, measured.** 972 of the 1031 presented routes index cleanly. Of the 59 that do not — every one zonal — 10 ship no `trazado` at all, 1 fails the span gate, 1 has a single stop, and 47 fail the per-stop gate. Those 47 break down as: **27** whose `trazado` is shared with a sibling variant it fits *exactly* (route 669's "Camelia" indexes at 18.5 m max error while "Gran Granada" misses 41% of its stops — the catalog files one polyline per route code and the return direction rides different streets); **14** whose shared polyline fits *neither* variant; **6** with a unique `trazado` that misses their own stops. Ruled out as causes, not assumed: orientation (reversing the line rescues **0** of 47), the wide-joint run discard (only 2 lose a run, both already class 1), and §5.1.4 simplification (identical failures at full catalog resolution). Relaxing `MIN_MATCHED_FRACTION` from 0.6 to 0.5, 0.4 or 0.3 rescues the *same* 3 routes / 93 legs — 4% of the 2385 ride legs on the refused routes — so the gate is not the lever; the disagreement is upstream. Closing it needs a per-variant `trazado` from `infoRuta`, or an offline harvest of driven geometry (§5.8's pattern), not a client-side threshold.
  * **One upstream cause fixed at the source** (`data/routeCatalog.ts`): when two route variants merge into one presented route, the stop list and the trace must come from the **same** variant. Pairing variant A's stops with variant B's `trazado` put stops hundreds of metres off "their" trace; that alone accounted for most of the per-route rejections.
    * Audited on the zonal side too: `applyZonalStopEnrichment` fills a stop list only where the route has none, and **0 of 939** zonal catalog variants ship without stops — so ArcGIS paraderos are never paired with a catalog `trazado`. Re-running the planner bench with the real 7623 stops + 42601 mappings applied produces a byte-identical graph (42 755 edges, 39 830 trace-measured), confirming it rather than assuming it.
    * The same rule binds **ArcGIS**, which enriches a troncal route and never re-draws it (§4.2). `consulta_rutas_troncales` publishes a survey centreline — a different source from the variant that supplied the stops — and adopting it over the catalog `trazado` for 115 of 126 matched routes was the same defect one level up: troncal ride legs measured from the trace fell from **96.2%** to 95.4% of 1599, and the route panel had to re-hydrate the real `trazado` behind the rider's back on every selection to draw the line the catalog already had. ArcGIS geometry is now used only where the catalog variant ships no trace, and the panel's re-hydration is a resolution upgrade (light 320-point → full) rather than a correction.

* **Validated against a source that touches neither the catalog nor our geometry.** ArcGIS `consulta_rutas_troncales` publishes `longitud_ruta_troncal` — the official length of each troncal route. Over the 83 routes that match a catalog variant, measured against that published figure:

  | model | mean ratio | mean \|error\| |
  |---|---|---|
  | straight-line stop chain (before) | 0.908 | **9.6%** |
  | trace-measured legs (now) | 0.983 | **2.6%** |
  | whole stitched trace, unclipped | 1.056 | 8.4% |

  The old model was short by 9% because that is roughly what a bus drives beyond the straight lines between its stops — the error this change was aimed at, confirmed from outside. The third row is why the projection is clipped to the stop span and gated per leg rather than simply measuring the polyline: the raw trace overshoots by 5.6% on average, carrying tails the service does not run in revenue.

* **Measured, on the committed catalog and the trip set in the bench.** Trace-measured ride legs **93.2%** (39 830 of 42 755). Drawn path start → boarding stop: mean **305 m → 18 m** (p50 133 m → 7 m, max **1401 m → 98 m**); end → alighting stop mean 179 m → 8 m. Step-to-step seam gap on the map — what decides whether the itinerary reads as one line — p50 **3 m**, p90 18 m, and **none over 100 m** (before: a single trip carried a 525 m break). Stop-to-trace projection error p50 4.2 m, p99 16.9 m. Graph build +≈80 ms and **+7.2 MB of heap** (15.1 → 22.3 MB for the whole graph), traces indexed once — the phone runs this too, so `tracePaths` hands back a path that needs no normalising *as it came* instead of copying it; copying by default duplicated 156 000 coordinate pairs the map layer already holds and cost 15.7 MB instead.
  * **Residual, known:** a ride's reported distance is the sum of its graph edges, while its drawn path is one slice of the trace, so the two can differ by the per-leg floor (no leg is charged less than its straight line) — p50 0.0%, p90 0.1%, worst 19% over 860 ride steps, always with the itinerary reporting the larger figure. Closing it entirely would mean charging metres the search did not.
  * **Search cost is unchanged.** A/B over 300 random OD pairs, same process, cost model patched at bundle time: p50 35 → 39 ms, p90 116 → 118 ms. The §1 sub-100 ms budget holds at the median but not at p90 on that distribution, and did not before this change either — the modelled buses are slightly faster, which shrinks the admissible A\* bound and prunes marginally less.

* **Speeds** (`TRONCAL_SPEED_M_PER_MINUTE` 533→**570**, `ZONAL_SPEED_M_PER_MINUTE` 300→**333**) are the old ones scaled by their own median trace/straight ratio, so the median trip time is held exactly where it was while the per-route bias goes: implied commercial speed stays 29.0 km/h troncal and 15.2 km/h zonal, but its spread narrows from 24.8–32.5 to 25.5–30.6 and from 14.4–18.5 to 14.7–16.5.
  * **Known gap, deliberately unchanged:** those medians are ~8% faster than the published commercial speeds (troncal 26–27 km/h, SITP 13–15 km/h). The old constants were already optimistic; re-centring them would move every reported trip time for reasons unrelated to the trace work. §5.8 records the real fix — harvest `consultar_programacion` (the theoretical per-stop timetable) offline over a bounded route sample and calibrate against it.

#### 5.6.4 Walking is part of the answer, not a coat of paint on it

Real pavement runs **1.25 × straight-line + 50 m** (fitted below). The planner used to search on the raw straight line, cut to four itineraries, and only *then* ask OSRM what the walking really was.

* **The routed answer was not the walk.** OSRM routes between the points it **snaps** onto the pedestrian network, and reports neither the snap legs in `distance` nor the requested points in the geometry. Taking the response at face value — which both transports did — broke the two things a walk leg is for:
  * **The metres were short, always in the same direction.** Measured over the walk legs this planner actually produces (97 distinct legs across 10 cross-city trips, both preferences): a mean **24 m** per leg uncharged, p90 42 m, worst **94 m**. A rider's origin dropped mid-block and a station set back from the kerb are each 20–90 m off the network, and every leg pays it twice. On **2 of 97** legs the card showed a walk *shorter than the straight line between its own endpoints* — a distance no rider can walk. It also biased the `walk` preference, which is a lexicographic optimum on exactly this number.
  * **The drawn walk did not touch anything.** `layers/journeyLayer.ts` renders `step.path` verbatim as one `LineString`, so the dashed leg started a mean **19 m** (p90 35 m, worst **91 m**) from the origin pin and ended that far from the station the next leg boards at — the same disconnected-pieces defect §5.6.3 fixed for rides, left standing on the walks that join them.
  * Both are fixed at the source: the transports charge `route.distance + snapFrom + snapTo` and hand the snap legs back individually, and `fetchWalkingPath` stitches the requested endpoints onto the geometry (`stitchWalkGeometry`, 2 m threshold) and floors the charge at the straight line. Re-measured over 179 walk legs: **0** detached endpoints (worst residual 1.7 m, i.e. already touching) and **0** legs charged under their own straight line.

* **What was wrong.** The refinement could reorder four plans but never recover the one it should have kept, and every limit it re-crossed went unchecked.
  * The `walk` preference is a **lexicographic optimum on walked metres**. Optimising it on straight lines makes it provably optimal for a metric nobody walks: on a real trip a 396 m straight-line leg (798 m of pavement) outranked a 490 m one (493 m of pavement).
  * `WALK_ONLY_FALLBACK_MAX_M` (2.5 km) and the walking-only-plan comparison were applied to the estimates and never re-applied to the truth, so a plan whose "2.2 km" turned out to be 3.4 km stayed on screen. That limit now means **walked** metres at both stages — and because those are ~25% more than the straight lines it used to see, it is applied the way the schedule filter is (§5.6.2 "never a dead end"): a plan over the limit is **held back, not dropped**, and offered anyway when nothing else survives. Enforcing it unconditionally turned trips that previously had an answer into empty panels — 5 of 142 in the 2.4 km+ band of a 400-trip sweep, where the honest count is 0.
  * Every leg fired at once in a single `Promise.all` — 53 requests to one public routing service for ten trips — and 92 walk steps were only 53 distinct routes, so ~39 of them were **duplicate requests in flight**, because the cache is written when a request resolves, not when it starts.
  * A failed lookup silently fell back to the raw straight line, mixing two metrics inside one itinerary with nothing on screen to say so.

* **The fix.** `findRoutes(params, out?)` returns the four itineraries to show **now** and hands `out.candidates` the pool of **8** they were cut from. `resolveWalkingLegs(pool, sortBy, departAt)` then routes every walk leg for real, recomputes totals and the §5.6.2 clock annotations from them, re-applies the walking limit, re-ranks, and only then cuts to four. Both clients call it (spec §1.1 R2).
  * **The estimate is unbiased so the refinement is small.** `walkMeters(d) = max(d, 1.25·d + 50)`, fitted against the same OSRM foot router over 150 stop pairs from this graph stratified across 120 m–1.5 km: mean error **−1 m**, mean |error| 77 m (10.7% relative), where the raw straight line is short by **227 m** on average. The fixed 50 m is a crossing: every leg has to reach one, so it is charged per leg rather than folded into the multiplier. It was **40 m** while the target it was fitted against still dropped the snap legs; against the honest distance that constant left the estimate 11 m short per leg, one-directionally — the exact bias the fit exists to remove, so the term was re-fitted rather than left to cancel out by luck. Least squares over the same sample puts the unconstrained line at `1.239·d + 59`, within noise of the kept form.
  * **What the correction does *not* do — measured, because the opposite is the intuitive guess.** It barely changes *which* itinerary is offered. A/B over 40 trips under the `walk` preference, cost model patched at bundle time: the first card shown before any lookup is still the genuinely shortest walk **74%** of the time either way (raw 25/34, corrected 26/35), and a rider acting on it before the lookups land walks a mean 48 m further either way. That is arithmetic, not luck — scaling every leg by one factor cannot reorder plans at all, and the per-leg term only separates plans with *different* leg counts, which the top candidates rarely have. **The ranking is fixed by routing the walking for real over the wider pool before the cut, not by estimating it better** — that is what changes the first card on the other 26% of trips. The correction's job is that the number on the card is honest while that happens.
  * Search radii and nearest-N cuts stay straight-line (they mean "is this stop next door"); only the metres charged are corrected. Hand-surveyed tunnel paths (§5.6.1 `TUNNEL_PATHS`) are already real distances and are not corrected twice.
  * **Requests**: deduplicated, coalesced while in flight, capped at **6** concurrent, and persisted in `localStorage` (`tm.walkroutes.v2`) — a walk between two fixed points never changes, so the second visit walks for free. A blocked or full store degrades to the in-memory cache. The 250-entry cap is a *write-cost* budget rather than a quota one: the store is rewritten whole, synchronously, after any search that added to it, and real pedestrian geometries average ~820 bytes each, so 250 is ~200 KB per write and still holds roughly 40 trips of history at the ~6 distinct legs a search resolves.
    * **The key is the unordered pair.** A foot route is the same walk both ways — measured against this router over the graph's own legs, worst asymmetry 4.1 m (0.48%) — so the entry is stored in one canonical direction and reversed on the way out. Keying on the ordered pair made the return trip, and every transfer leg a later search happens to traverse backwards, pay for a lookup it already had; it also let two opposite in-flight requests for the same walk both go out.
    * `v2`, not a migration: `v1` entries were keyed by ordered pair and held the raw OSRM route — snap legs uncharged, geometry stopping short of both endpoints. Reading them back would have kept both defects alive for exactly the riders who use the planner most, so the old store is dropped on load.
    * A persisted entry is **validated, not trusted**: a non-finite or negative distance/time, or a coordinate list that does not survive a finite check, is dropped rather than repaired. One bad value read back into `plan.walkDistance` makes it `NaN`, which sorts arbitrarily against every other plan and prints as "NaN m" on the card — a corrupt store must cost a lookup, not the ranking.
  * **A superseded pass stops queueing.** The two clients already track a search sequence; they hand it to `resolveWalkingLegs` as `stillWanted`, and the bounded runner checks it before dispatching each remaining leg. Otherwise a search the rider has already replaced keeps six connections busy on the same public router the new search is waiting for — the discarded results were thrown away by the staleness guard anyway.
  * **A failed lookup is labelled, not hidden**: the leg keeps the corrected estimate (never the raw straight line, which would shrink one leg to a distance nobody can walk), `step.walkSource` stays `'estimate'`, and `plan.walkEstimated` is set so a card can say so instead of passing a guess off as a measurement (spec §1).

* **How the numbers in §5.6.3 and §5.6.4 were obtained.** Not from a fixture: the committed catalog is loaded, `buildCatalogRouteList` + `initRouter` are run exactly as the browser runs them (with the traces first simplified to the §5.1.4 cap), and a fixed set of real cross-city trips is planned. Ride geometry is scored by the distance from each drawn leg's endpoints to the stops it serves and by the seam between consecutive steps; walking is fitted and scored against live calls to the same OSRM foot router the planner uses. Walk legs are scored the same way rides are — the gap from each drawn leg's endpoints to the two points it was asked to join — and the distance fit is scored against the honest walked total (routed path + both snap legs), which is what a rider covers and what the card now says. `tests/schedule.spec.ts` continues to cover the schedule behaviour these numbers must not disturb.

### 5.7 Acceptance Criteria

System aligns with spec when:
1. **Catalog Fallback**: Client loads and initiates search from local master catalog.
2. **Interactive Search**: Users search/select routes, showing correct traces, schedules, timelines — and choose **what** the query looks for (routes, estaciones, paraderos, recargas, bici) instead of scrolling a blended list, with every place catalogue reachable by name, not only by GPS proximity (§5.4.2b).
3. **Layer Integration**: Station popups render wagon assignments. Zonal stops map correct routes.
4. **Live Operations**: Live tracking resolves through the cascade (Live Bridge extension → CO relay direct → server `/api/buses` → public CO proxy), showing loading/tracking/empty/error/stale states.
5. **Card Balance**: Lectura de saldo reproduces the observed `/lectura_tarjeta` request, labels server-only data as such, and never presents missing NFC card-memory movements as verified data.
6. **Stability Guidelines**: App loads properly even when live relay or ArcGIS endpoints fail.
7. **Schedule Constraints**: The planner times every boarding against its route's own window (§5.6.2) — real clock times, opening waits, out-of-service tags, and a ranking that prefers services running most of the day. Filtering by those windows is the rider's choice ("Solo en servicio"), never the default, and even then a search that finds nothing returns tagged out-of-service options plus the next departure that works, never an empty result.
8. **Real geometry, both modes of travel**: a ride is charged and drawn along the route's own `trazado` (§5.6.3) and every walk leg of every candidate is routed on the real pedestrian network before the itineraries are ranked and cut (§5.6.4), never after. **Both** kinds of leg start and end on the points they join — the walk reaches the rider's origin and the door the bus leaves from, not the pavement OSRM happened to snap to — so the itinerary is one continuous line on the map rather than disconnected pieces, and the metres on the card include the walk to the network that the routed path leaves out. Where a trace or a lookup is unavailable the leg falls back to the labelled straight-line estimate, and the rider is told which one they are looking at.

### 5.9 Voice — the app you can use without looking at it

A rider who has just unlocked their phone should be able to say one thing and hear one sentence back.

**What it answers.** One question is a demo; a day of questions is a feature. The flow reads an **intent** off the utterance (`voiceMatch.parseVoiceRequest`) and each one is a different engine and a different sentence — everything but the first used to come back as "no encontré una ruta que se llame…", which taught riders the thing only did one trick:

| Intent | Said as | Answered from | Needs network? |
|---|---|---|---|
| `eta` | "¿qué tan cerca está el F19?" | route index + one geometry shard + one live call | live buses only |
| `horario` | "¿a qué hora abre el K86?", "¿pasa los domingos?" | route index alone | no |
| `paradas` | "¿qué buses pasan por aquí?", "¿dónde estoy?" | stop index + horarios | no |
| `viaje` | "¿cómo llego a la Calle 100?" | stop index / geocoder → the planner tab | only for street addresses |
| `saldo` | "¿cuánto saldo tengo?" | remembered card → tullave ledger (§5.5.1a) | yes |
| `ayuda` | "¿qué puedes hacer?" | the example list itself | no |

Four of the six are answerable **with the phone in airplane mode**, which is the point: the data is in the APK (§5.2.1b), so the questions a rider asks while standing at a paradero with one bar of signal are the ones that do not need it.

**The loop, not the answer.** A stop question ends in a row of route chips, each of which is the ETA for that route *at that stop* — breadth offline, then depth on the one route the rider cares about, instead of a 27-way live fan-out nobody can wait for. The stop carries over as the `anchor`, so "¿qué buses pasan por Banderas?" → tap `F19` answers **at Banderas** rather than asking where the rider is. That two-step is the daily shape of the feature; the single spoken ETA is only its fastest case.

 Bare `"Hey Google, how close is the F19?"` does **not** reach a third-party app: Assistant's App Actions voice shortcuts do not survive the Gemini transition, and their successor — AppFunctions (`androidx.appfunctions`) — needs Android 16 (API 36, our `compileSdk` is 34, pinned by the phonegap-nfc patch) *and* an allowlist that is still private preview. So the shipped entry point is the stock `"Hey Google, abre <app>"` launch into a hot mic, and the app's own shortcuts/widgets; AppFunctions is a wrapper to add over the same engine when it opens up.

That budget — a spoken answer ~1.5 s after the rider stops talking — is what shapes the data layer, because the ETA must be computed **on the phone**: the APK talks to no web server of ours (§5.2.1b), so the server's `/stop-arrivals` engine is not available to it.

**Bundled assets** (`bundle_mobile_data.ts`, alongside the §5.2.1b offline datasets). The 13.6 MB light catalog is too slow to parse on a cold launch, so it is split in two:
* `voice_index.json` (**367 KB**, always loaded, ~15 ms): per route `nombre`, `tipo` (`t`/`z` → cruising speed), `color`, and per direction `origin` / `destination` / `horarios` (native shape, so `parseServiceSpans` needs no conversion) / `live` (destination-first live-query names, §5.2.4, precomputed because the voice path never builds the full route list). All **783** routes are present, including the 7 with no usable trace — "el F19 no presta servicio los domingos" is answerable with zero geometry, and dropping those routes would turn a real answer into "no conozco esa ruta" (§1).
* `voice_stops.json` (**565 KB / 166 KB gzip, 7415 stops, lazily loaded, ~10 ms parse**): `[codigo, nombre, lng, lat, "F19,B12,…"]` — the inverse index, and the whole reason the `paradas` question exists. Built in the **same bundler pass** as the shards, from the same stop rows, so the two cannot disagree about what serves what (§1.1 R2). Loaded only when a stop question is actually asked: it is worth nothing to the route questions, which are the ones on the ~1.5 s budget. A sixth field, `1`, marks an **estación** (from the register, §5.5.6) and is written only for the ~140 that are one. It is what makes a named stop resolve to the place the rider meant: names here belong to the station and are inherited by the SITP paraderos around it, so "Islandia" matched `Br. Islandia` — more routes filed, so it won the tie — and answered about the stop across the road. `findStopByName` now breaks ties **estación first**, then shortest name, then most routes. In the same pass `nameTokens` drops `los`/`las`/`del` (the one- and two-letter connectors already fell out of its length rule): a rider says "los laureles" for the station the catalog files as `Laureles`, and requiring that word sent them to the paradero. Symmetric — the same function tokenises the rider's words and the stop's name — so `Las Aguas` and `Portal Las Américas` still resolve to themselves. Its consumer (`services/voiceStops.ts`) ranks a stop's routes **troncal first** — códigos sort alphabetically, so the first four at Banderas used to be whichever alimentadores began with a digit — and reports **which are running now**, off the route index's own horarios: a station with 27 routes filed and 6 running at 23:40 presented as 27 options is how a rider waits for a bus that stopped hours ago (§1).
* `voice/<CODE>.json` (**776 shards, avg 5.8 KB**): per direction, `stops` as `[codigo, nombre, lng, lat, posicion]` and the `trazado`, coordinates rounded to 5 dp (~1.1 m). Fetched only for the ONE route that matched. Route codes are all `[A-Za-z0-9_-]+`, asserted at bundle time, so a code is its own filename. Shards are **not** placed in a Vite `public/` dir — the mobile client's `publicDir` points at the *website's* `client/public`, so anything left there would ship in the website bundle too; `mobile/scripts/build-web.mjs` copies them to `www/voice/` after the build instead.

**Engine** (`client/src/services/routeEta.ts`, pure — buses, position and the Bogotá wall clock are all inputs). The inverse of §5.8's `stop_arrivals.ts`: *this route, where is it relative to me*, one route and one live call instead of a 24-way fan-out. The cruising speeds, the 160 m on-route tolerance and the 40 m passed-stop epsilon are **the same numbers as the server's** — the same bus must not be "4 min away" in the app and "6 min away" on the website (§1.1 R2) — and the projection is duplicated rather than shared only because the two live in different packages. Both are annotated to change together.
* `checkRouteService()` runs **first**, off the index alone: a closed route is answered without waiting on the live host. `fuera-de-servicio` (opens later today) and `cerrado-hoy` (no more service today) are separate verdicts because they are different sentences.
* Bus and stop are projected onto the **same** simplified trace, so the shard's RDP corner-cutting largely cancels in their difference. Measured on F19 against the operator's own chainage: 6012 m computed vs **6083 m** filed (−1.2%); on a zonal MultiLineString, −2.8%/−3.4% — all well inside the whole-minute rounding. The stop's `posicion` is deliberately *not* used as the along-track anchor: it is chainage on the full trace, and mixing scales would bias every ETA instead of cancelling.
* The rider's walk is folded in, so the verdict is actionable rather than a bare number: `sal-ya` / `alcanzas` / `no-alcanzas` / `llega` / `sin-buses` per direction, and `ok` / `lejos` / `sin-geometria` / `sin-ubicacion` / `fuera-de-servicio` / `cerrado-hoy` for the route. Nothing beyond `ACCESS_MAX_M` (1500 m, the router's access radius) is offered as an ETA off a *position* — the honest answer there is the distance.
* **A position is not required, because a rider can name the stop.** `userPos` is `[lng,lat] | null` and `stopHint` anchors the answer instead (`matchStopByName`, strict: every word of the hint must appear in the stop's name, shortest name wins). This is what makes the feature work indoors, with location denied, or on a phone whose newest system fix is hours old — the cases where it used to answer "no sé dónde estás" and stop. The access radius deliberately does **not** apply to a named stop: a rider who says "Banderas" has answered the "are you near it?" question themselves, and refusing because the phone thinks they are 4 km away is the app overruling them with worse information. With neither anchor the verdict is `sin-ubicacion` — distinct from `lejos`, because only one of the two is fixable by the rider, and the sentence for it now says how ("Dime en qué parada estás y te lo calculo").
* **The walk clause is dropped, not invented, when there is no fix.** `walkMeters`/`walkMinutes` are nullable and every sentence that mentions the walk is built around that (`verdict: 'llega'` = a bus is inbound, no walk to race it against). A walk past the access radius is also dropped rather than reported — "estás a 178 minutos caminando" is not a walk, it is a rider asking about somewhere they are not.
* **`describeRouteDay()` answers the timetable question** off the index alone: today's windows clipped to the plan day, first opening, last service, and how long a service it is. Separate from `checkRouteService` because the two answer different questions — "can I board now" versus "when does this thing run".
* **Both directions are returned, never guessed between.** 249 of 783 routes file two sentidos, and a bare route code cannot disambiguate them; answering the wrong one is worse than answering both in one extra clause.

**Utterance → request** (`client/src/services/voiceMatch.ts` → `parseVoiceRequest`, tables in `voiceSpanish.ts`). A recognizer never returns "F19"; it returns "efe diecinueve", "la efe 19", "ef 19", or the destination. No NLU — the search space is 783 códigos, so a letter/number table plus edit distance beats a model on accuracy *and* on the budget (measured **0.8 ms** per utterance over the whole index, warm, scoring up to five recognizer readings, §1 sub-100 ms). Two things make that number hold while doing five times the matching: the index is swept **once** and split by threshold (matching separately for the answers and for the shortlist doubled the hot path for nothing), and each route's searchable words are derived **once per index** and memoised in a `WeakMap` — re-tokenising 783 route names per reading per question was the module's entire cost.
* **Every reading the recognizer offers is scored, not just its favourite.** `EXTRA_MAX_RESULTS` is 5 and the plugin hands back the whole list (`resolveListen` → `alternatives`); the matcher takes `string | string[]`. A códigos table is a far better judge of "F19" vs "fe 19" than the recognizer's own ranking, and the exact match is regularly the second alternative — reading only the first threw it away. The hints and the intent, though, come from the **best** reading alone: the alternatives exist to rescue a código, and mixing clauses from two transcriptions would build a question nobody asked.
* **The kind of question is parsed too, because a rider asks more than one** (the table above). Order is the design, and it is resolved *against* what matched: the three command intents (`ayuda`, `saldo`, `viaje`) outrank everything, because "llévame a Suba" is unambiguous however many route names contain "Suba"; a **strong** código (≥0.85) then means the rider is asking about that route; and only below that does a stop question win. That last rule is load-bearing — "¿cuáles rutas hay en la Calle 100?" produces a one-edit match on route **B100** (from the número 100), which was enough to hijack a question that never named a route at all. A `viaje` or `paradas` reading also **discards** its route matches, so the same accident cannot leak an ETA into the answer. A schedule word (`abre`/`cierra`/`opera`/`domingos`/…) beside a código makes it `horario`; "¿a qué hora pasa?" deliberately stays an ETA, since it asks about a bus rather than a timetable.
* **A named stop, a named direction and a destination are carried as hints.** `stopHint` (after `en`/`por`/`desde`/`estación`/`parada`/`portal`), `dirHint` (after `hacia`/`sentido`/`rumbo`) and `destinationHint` (after `a`/`al`/`hasta`/`para`, `viaje` only) are read from the raw tokens, since the markers are themselves stopwords for name matching. All are *hints*: the engines use one only when it matches real data, so a mis-parse ("por el F19" → stopHint "f19") degrades to the plain nearest-stop answer rather than to a wrong one. A **deictic** hint is dropped rather than looked up — "¿qué buses pasan por **aquí**?" is the likeliest phrasing of the stop question, and taking `aquí` as a stop name answered "no encontré una parada que se llame aquí", a parody of the feature.
* **A letter word is only read as a letter when a number follows it.** Half the Spanish letter names are ordinary words — `de`, `se`, `a`, `ese` — so requiring the letter+número shape of a real código is what stops "cuánto falta **de** mi casa" resolving to route D. Clipped ("ef" → F, when exactly one letter name starts with it) and bare glyphs ("f 19") are also accepted, but never from a stopword: `el`/`la`/`de` precede a route far more often than they name a letter, and reading "el treinta y siete" as *E37* swallows route **37**. Those weak readings therefore also offer the número on its own.
* Numbers parse as words or digits, 0–999 ("ochenta y seis" → 86), and a run of single digits is additionally read as a digit string — riders spell zonal códigos both ways ("a seis dos ocho" → A628). A consumed número is **not** re-read as a bare código, or "ka ochenta y seis" would also propose route 86 and tie with the real match.
* Scores: 1.0 exact código, 0.85 base código (§5.4.3 Ciclovía suffix), 0.6 one edit away, 0.5–0.75 by name/origin/destination token overlap. A lone shared word only counts at ≥6 characters ("banderas" yes, "casa" no). Nothing below **`MIN_VOICE_CONFIDENCE` = 0.5** is *answered*: answering the wrong route costs a bus.
* **But a weak reading is asked about, never discarded.** Anything from **`SUGGEST_VOICE_CONFIDENCE` = 0.3** up to that floor comes back as `suggestions`, which the overlay renders as tappable códigos and the composer says out loud ("No estoy seguro. ¿Preguntas por el F19 o el F60?", `composeSuggestions`). The certainty rule is intact — nothing is answered on the strength of a 0.3 reading — while a dead end becomes one tap. "No te entendí" with nothing after it leaves the rider guessing what the app can even hear.
* **An ambiguous place is a question, not a coin toss.** "El bus en la Calle 100" name-matches every route serving Calle 100, all with the *same* score, and returning the alphabetically-first one would be a guess presented as a fact (§1). When the whole shortlist is name matches tied at one score, it is demoted wholesale to `suggestions` — so the rider is asked which of the three, instead of told about one of them.

**The sentence** (`client/src/services/voiceAnswer.ts`). Every verdict composes a line a rider can act on, so the flow never falls back to a generic failure (§4.2). All output is **plain text** — it goes to TTS as-is and must reach the DOM through `textContent`/`escapeHTML`, since stop and route names are upstream data (§3.3).
* **The walk is part of the answer**: *"El efe 19 llega a Suba Calle 100 en 2 minutos y estás a 3 minutos caminando. Sal ya."* An ETA said without the walk is unusable to whoever is 12 minutes away.
* **Never promise a bus we cannot see**: "Hay 2 buses en camino" is only said when a second vehicle actually projected onto the trace (§1).
* **The stop answer says what is *running*, and how many there are** (`composeStopRoutes`): *"Estás en Banderas. Ahora pasan 25 rutas, entre ellas el F19, el B26, la 5 y el A60."* The count leads because it is the useful number; four códigos follow because a spoken list longer than that is not an answer anyone can hold; and they are one per **variant family** (`variantBase`), so the four are four services rather than four spellings of one. Never a collapsed stand-in, though — the rider has to be able to match what they hear against what is painted on the bus (§1). Nothing running at this hour is said as exactly that, with the filed count, rather than as an empty list.
* **The trip answer is a handoff, and says so.** The router needs the full catalog and its answer is four itineraries with legs and transfers — a screen, not a sentence. What voice removes is the part that made the planner a chore: typing two endpoints the rider just said out loud. With no fix it seeds the destination alone and names the missing half ("Dime desde dónde sales") instead of searching with a hole in it.
* **The saldo answer never reads the card number out loud** — only the last four digits, and only the amount is spoken ("5.400 pesos" for the ear, "$ 5.400" for the eye). The number is the rider's, and saying it on a bus is not something this app does (§3.3).
* **The timetable answer states the window *and* where now sits in it** (`composeSchedule`): *"El F19 opera hoy de 4:30 a.m. a 10:00 p.m. Ahora está en servicio."* — the hours without that second clause leave the rider doing the arithmetic they asked us for. A route closed for the day says which kind of closed it is (§5.9 `runsToday`), a peak-only route reads its several windows ("de 5:00 a 9:00 de la mañana y de 4:00 a 8:00 de la tarde", collapsed to first–last "en varios turnos" past three), and the closing hour is not repeated when it is the same one the range just ended on.
* **Every answer is composed twice** — `VoiceAnswer` carries both `spoken` and `written`, built by running the same sentence templates through a `Phrasing` (`SPOKEN` / `WRITTEN`). They are not interchangeable and neither may be substituted for the other: es-CO TTS reads a bare `F` as English so the speaker must be told **"efe 19"**, while a rider looking at their phone must see the código they know, **"F19"**. Same for the clock ("4:30 de la mañana" spoken, "4:30 a.m." written), the distance ("4,5 kilómetros" / "4,5 km") and the catalog's dashed place names ("Portal El Dorado – C.C Nuestro Bogotá" → a comma, spoken only). Composing once and reusing the string is exactly the defect this shape exists to prevent — it shipped that way first and put "El efe 19" on screen. Upstream abbreviations are never expanded in either form: guessing at them would put words in the operator's mouth. `service.detail` (with its " (mañana)" chip suffix) is never spoken; the composer formats from `boundaryMinute` instead.

**Native glue** (`mobile/android/.../VoicePlugin.java`, registered in `MainActivity` *before* `super.onCreate`). The plugin is plumbing only — no route knowledge, no catalog, no network — because the answer must stay in TypeScript for both clients (§1.1 R2). What it buys is timing: on a `transmigo://voice` launch, recognition starts in `load()`, during bridge init, and the transcript is **buffered** until the web layer asks. The rider talking and the WebView booting then overlap instead of queueing.
* **One recognition attempt owns the microphone, and it is the newest one** (`recognitionGeneration`). This is the defect that made the whole feature read as *"it doesn't let you talk at all"*. `SpeechRecognizer.cancel()`/`destroy()` delivers one last callback on many OEM implementations — typically `onError(ERROR_CLIENT)` — and that callback ran the same `deliver()` path as a real result: it took whichever call was pending *now* (the brand-new `listen()` the rider was waiting on), rejected it as `RECOGNITION_FAILED`, and then destroyed the recognizer that had just been created for it. The mic closed milliseconds after opening and the overlay read "no te entendí" before a word was said — on the main path, because the hot-mic pre-warm is *always* torn down by the overlay's `listen()`. Every listener and watchdog now carries the generation it was created for and is inert once stale, the listener is detached before `destroy()`, and `startListening` re-checks the generation after its `post` so two recognizers can never be open at once.
* **A cancel may never answer for a listen that came after it.** `cancelListening` takes the state down **synchronously**, on the caller's thread (only the recognizer teardown is posted), and the web layer serialises the two calls (`micIdle` in `views/voz.ts`). Capacitor dispatches plugin methods on a thread pool, so close-and-immediately-reask — which is exactly what "Preguntar otra vez" and a re-fired shortcut do — could otherwise land the cancel on the *new* call and reject it as `CANCELLED`: a dead microphone under a screen that said "Escuchando…".
* **The watchdog is for a recognizer that went quiet, not for a rider mid-sentence.** It is re-armed from `onBeginningOfSpeech` (`SPEAKING_TIMEOUT_MS` 20 s, ceiling `LISTEN_TIMEOUT_MS` 15 s). A 12 s ceiling that started while the splash was still up used to expire *over someone audibly speaking* and hand back "no escuché nada".
* **A partial is not a draft — it is what the rider said, and it is already on their screen** (`lastPartial`). Google's recognizer routinely streams "efe diecinueve" through `onPartialResults` and then finalises with an empty result or `ERROR_NO_MATCH`; the transcript was echoed to the overlay and then thrown away, so the app answered "no te entendí" about words it had just displayed back. That is the whole of "it has problems recognizing your voice". Every ending that means *heard something, transcribed nothing* — empty final, `ERROR_NO_MATCH`, `ERROR_SPEECH_TIMEOUT`, and the went-quiet watchdog — now answers with the last partial instead (`deliverOrFallBackToPartial`). Nothing is *answered* below `MIN_VOICE_CONFIDENCE` regardless, so a junk partial still lands on "no te entendí" while a good one is rescued; the partial is cleared at the start of every window so one question's words can never answer the next.
* **The rider ends their own sentence** (`finishListening` → `SpeechRecognizer.stopListening()`, the overlay's **"Ya terminé"**). Endpointing is a guess the recognizer makes in both directions — it cuts off someone who pauses mid-código and holds the mic open through a bus — and this is the half of it the rider can settle. It is `stopListening`, never `cancel`: the audio already captured is transcribed, so the question is answered rather than abandoned. The button appears only once `voiceReady` says the mic is actually open, and disables rather than hides itself on tap so the row does not jump under a thumb.
* **The silence windows are generous because of that button** — `MIN_INPUT_MS` 3000, complete-silence 2600, possibly-complete 2000 (from 2500/1500/1200). 1.2 s of silence is a breath, not a full stop, and the cost of the longer window (roughly a second before the recognizer decides on its own) is one the rider can skip whenever they want by saying they are done.
* **Spanish is a ladder, not one locale** (`LANGUAGES` = `es-CO`, `es-419`, `es-US`, `es-ES`, `es`). A language failure steps down it before the flow ever says "este teléfono no tiene español" — most phones have *some* Spanish pack, just not the Colombian one, and giving up at `es-CO` told riders they had none. The offline→network retry above still happens first, at whichever language the attempt was using.
* **Ten alternatives, not five** (`EXTRA_MAX_RESULTS`). The matcher scores all of them against a códigos table and is a better judge than the recognizer's own ranking, so extra readings are close to free and the exact código is regularly not the first one.
* **"Heard nothing" and "couldn't make it out" are different sentences.** `ERROR_NO_MATCH` is its own code (`NO_MATCH` → outcome `no-entendi`), neither of them terminal, and the second window says "No te entendí. Dime la ruta otra vez…" instead of accusing someone who just spoke of silence. A `no-entendi` retry is offered even when a habit exists (`predict.ts`) — the rider plainly wants to ask about something else.
* **`ERROR_SERVER` is not a missing language pack from API 33 on.** Three codes say that precisely there (`LANGUAGE_UNAVAILABLE`, `LANGUAGE_NOT_SUPPORTED`, `CANNOT_CHECK_SUPPORT`); reading a plain server error as "this phone has no Spanish" sent riders to install a language pack they already had. Pre-33 the heuristic stays, because there is genuinely no way to tell. The *retry* is deliberately wider than the classification: any of those plus `ERROR_SERVER`/`ERROR_CLIENT`/`ERROR_NETWORK` on an `EXTRA_PREFER_OFFLINE` attempt is worth one network attempt before telling the rider we cannot hear them.
* **A pre-warm never answers for the rider.** The hot mic races the WebView, so it routinely reaches its silence timeout *before the overlay is on screen* — and handing that timeout back as the result is exactly "the app said it didn't hear me before I could speak". Only a real transcript (≤60 s old) and genuinely terminal failures (no recognizer, no permission, no network, no Spanish model) survive to the web layer; a pre-warm that heard nothing is discarded and the mic is **re-armed** when `listen()` arrives, so the rider's window starts when they can see that it has. Recognition already running is taken over only while `onBeginningOfSpeech` says the rider is mid-sentence; an open-but-silent mic is restarted instead. The endpointing hints go with it (`EXTRA_SPEECH_INPUT_MINIMUM_LENGTH_MILLIS` 2500, complete-silence 1500, possibly-complete 1200, sent as `int`) because the platform defaults cut off a rider who pauses for breath, and a **12 s watchdog** ends any recognition that neither returns nor errors — some OEM recognizers simply go quiet, and without it the mic stays open under a screen that reads "Escuchando…" forever.
* **Every failure mode is its own code, and its own sentence.** The plugin rejects with `NO_SPEECH` / `PERMISSION_DENIED` / `NO_RECOGNIZER` / `NETWORK` / `LANGUAGE_UNAVAILABLE` / `RECOGNITION_FAILED` (mirrored from the Web Speech error strings in the browser fallback), `listenOnce` maps them to an outcome and **never rejects**, and `composeListenFailure` answers the four that are about the microphone rather than the rider. Collapsing them into "no te escuché" told someone whose mic permission was denied to repeat themselves into a device that was never listening.
* **The plugin is threaded, so it is locked.** Capacitor invokes plugin methods on a background executor while every `RecognitionListener` / `UtteranceProgressListener` callback arrives on the main thread; the buffered transcript, the pending call and the listening flag are shared by both sides and are guarded (`recognitionLock` / `speechLock`), with the recognizer's whole lifecycle posted to the main thread — which is both what `SpeechRecognizer` requires and what serialises a start against a cancel.
* **Recognition uses the platform recognizer with `EXTRA_PREFER_OFFLINE`, never `createOnDeviceSpeechRecognizer`.** That constructor reports itself available whenever the on-device *service* exists, regardless of whether the locale's language pack is installed — measured on a Pixel 6 / Android 16, where every attempt died instantly with `SodaSpeechRecognizer: Failed to get language pack of required locale: error 12` and no fallback was possible. The platform recognizer uses the offline model when present and the network otherwise; a language error on the offline attempt retries **once** without the hint, which is what actually opens the mic on that phone.
* **The `transmigo://voice` filter is `DEFAULT` only, never `BROWSABLE`.** That category exists so a link inside a web page can fire the intent, and this intent opens a live microphone. Nothing that legitimately uses the link needs it — a launcher shortcut names the component explicitly, and an automation's implicit `VIEW` gets `DEFAULT` — so the only thing it would add is letting any page open the app straight into recording.
* `<queries>` for `android.speech.RecognitionService` / `TTS_SERVICE` is required: without it Android 11+ package visibility hides the speech services and `isRecognitionAvailable()` answers false on a device that can hear perfectly well.
* **A held sentence is always released.** An init that *fails* used to leave the held call un-settled, so the JS promise the overlay awaited never resolved and the answer was never even shown — worse than not speaking it. Failure rejects the held sentence (`TTS_UNAVAILABLE`), a bind that never completes times out at 4 s, `stopSpeaking` drops it (closing the overlay must not have the answer read out to an empty screen a second later), and `handleOnDestroy` settles everything outstanding.
* **Nothing inside the `TextToSpeech` init callback may touch the engine field.** `onInit` can fire *before* the constructor has returned and assigned it; the resulting `NullPointerException` is swallowed by the TTS framework, so the engine is silently never marked ready and every answer is shown but never spoken — intermittently, since it is a race. Measured on a Pixel 6. The callback therefore sets a flag only, and the language is resolved lazily on the first sentence. A sentence handed over while the service is still binding is **held and flushed on init**, never rejected: dropping it is what "the answer appeared but nothing was said" looks like from the rider's side. Audio goes out as `USAGE_ASSISTANT` / `CONTENT_TYPE_SPEECH` so it ducks the rider's music instead of mixing under it.
* **Position is the last known fix, never a fresh one** — `navigator.geolocation` with high accuracy is what the map uses and can take ten seconds, which is the whole voice budget several times over. The accepted age is **30 minutes**, not the five it started at: a phone in a pocket indoors has nothing refreshing its location, and a strict window turned a real answer ("estás a 2,4 km de Ricaurte") into "no sé dónde estás" on a stationary device whose newest system fix was ~20 minutes old. The question is which stop is nearest, and that does not change while the rider stands still.
* `app_name` is **TransMi Go**, matching what the app calls itself everywhere else. The launcher label is what a rider says out loud — the entry point is the stock "Hey Google, abre \<app\>" — and "TransMilenio Explorer" is eight syllables and gets misrecognised.
* **The feature asks for everything it needs, from inside itself.** `RECORD_AUDIO` on the first question, never at boot; **location on the first `lastLocation`**, because only the map used to request it and a rider who only ever asks out loud was told "no sé dónde estás" forever with nothing in the feature able to fix it — the permission had to be granted from Android settings, which is not an answer for someone standing at a paradero. A permanent denial is not re-prompted; it answers with the schedule half instead (§4.2). Verified from a fully revoked state: mic prompt → location prompt → spoken answer, no developer tooling in the path.
* **The speech engines are the OS's and cannot be bundled.** `SpeechRecognizer` and the TTS voices are Android system services; there is no supported way to ship or side-load Google's models inside a third-party APK, and every device with Play services already has both. What that costs the rider is bounded: the *recognition* step falls back to the network when the optional offline Spanish pack is absent (the rest of the answer — catalog, schedule, geometry — is already APK-local, §5.2.1b), and a device with no Spanish **voice** gets an `Instalar voz en español` button wired to `ACTION_INSTALL_TTS_DATA` rather than silence. Full independence from Google would mean bundling our own recognizer (a Vosk es model is ~40–50 MB of APK) — a deliberate size/accuracy trade, not something to adopt by default.

**The flow** (`client/mobile/src/voice/`, overlay in `views/voz.ts`). Ordering is the design: the position fix starts *before* listening finishes (it does not depend on the route), the geometry shard and the live call start the moment a código exists — **in parallel with the fix**, since neither depends on where the rider is and a serial step in front of the live request is dead time the rider feels (§5.2.2b) — the schedule is checked *before* the live call (a closed route is answered offline in milliseconds instead of after a Colombian round trip, and skips the live request entirely), and nothing waits on `loadCore`. Shards load from `/src/generated/voice/` in dev and `/voice/` in the APK; a failed *read* is un-cached exactly like the index (a 404 is a fact about the route, a network blip is not — pinning it would answer "no tengo su recorrido" all session about geometry sitting in the APK).
* **Closed outranks `lejos`.** Both can be true; being 2 km away does not matter when nothing is running, so the rider gets the hour it opens rather than a walk to a stop no bus will reach.
* **A broken microphone is never masked by the habit.** The prediction exists for a rider who *said* nothing; someone whose mic is denied, missing or offline said nothing because they could not, and answering their usual route as though the question had been heard leaves them with no idea why nothing else is askable — the very defect the four separate mic sentences exist to prevent. So the mic failure is named first, and the habit comes back as a **tap** (one chip) instead of being thrown away. The overlay also offers **"Buscar la ruta en la app"** on those four outcomes: "búscala en la app" is a sentence, not a way out, and the rider should not have to follow it by hand.
* **Only `Instalar voz en español` waits for the speaker.** Every other post-answer affordance is wired at `listo`, off the progress event, because the session promise does not settle until TTS has finished or given up — a rider whose mic was denied should not have to wait out a sentence being read aloud before the fix for it appears. The web fallback's `speechSynthesis` is also bounded (20 s): a browser with no installed voice accepts `speak()` and then fires neither `end` nor `error`, which hung that promise forever and with it everything gated on it.
* **A voice surface has no menu, so it says what it can do.** `VOICE_EXAMPLES` (five real utterances, one per intent) is shown on "¿qué puedes hacer?", on anything that resolved to nothing, **and on every microphone failure** — and each example is a *button* that runs the same pipeline speech feeds (`VoiceSessionOptions.utterance`). That is what makes them documentation rather than a picture of a feature: on a phone whose recognizer will never open, or with the mic permission denied, the whole thing is still usable by hand (§4.2, §1.1 R5). A rider who hears "no encontré una ruta" twice with nothing after it stops opening the mic at all.
* **A command navigates behind the overlay, and the overlay leaves when the sentence ends.** `viaje` and a card-less `saldo` return a `VoiceAction`; the session never touches `AppContext` (it computes and composes — the navigation belongs to the view that owns the sheet, §1.1 R2). The order matters both ways: closing first would cut the speech off mid-word (`onClose` owns `stopSpeaking`), and waiting for the speech first left the rider staring at a finished answer for the seconds it takes to say. So the planner is seeded and searching *while* the sentence plays, and the sheet closes itself once it is done.
* **Only the question on screen may write to the screen.** The overlay stamps every `ask()` with a round and ignores progress and results from any other (`views/voz.ts`), and the session itself stops reporting and stops speaking once its `AbortSignal` fires. Without both, a superseded question settled *after* the new one had started listening and painted its "no te entendí" over the live "Escuchando…" — indistinguishable, from the rider's side, from an app that refuses to listen.
* **Silence is answered, not refused.** A rider who says nothing gets the route they ask about at this hour (`predict.ts`: a count per código × part of day, requiring **two** prior asks — treating a one-off as a habit is worse than asking; the parts of day are **Bogotá's** hours, like every other clock in the flow, or a phone left on another timezone files the morning commute under "tarde" and never matches the bucket it reads back). A prediction is **not** recorded as a question: letting the model count its own guesses turns one lucky answer into the only route the device ever offers. And when there is no habit to fall back on, a first attempt that heard silence gets exactly **one more** — refusing the question before the rider has spoken into a screen that says the app is listening is the worst thing this flow can do.
* **The answer is on screen before it is spoken.** The composed answer is handed to the overlay at `listo` and only then read aloud; awaiting the speaker first left the rider watching a spinner for the several seconds the sentence takes, on a screen whose whole point is carrying the words TTS may never manage to say. Closing the overlay aborts the question (`AbortSignal`), so an answer the rider walked away from is never spoken to an empty screen.
* **The status line tracks the microphone, not the intention.** `onVoiceState` (`voiceReady` / `voiceSpeaking` / `voiceEnd`) drives it: "Abriendo el micrófono…" until the recognizer says it is open, "Escuchando…"/"Te escucho…" while it is, "Un momento…" once it has closed. A screen that claims to be listening while the service is still binding is how a rider ends up talking into a closed mic.
* **The overlay outranks the boot splash** (`sheet-host` z-index 110 > `boot` 100 > `net-banner`; toasts above at 120). A `transmigo://voice` launch answers off the 367 KB index while `loadCore` is still parsing 13.6 MB — underneath the splash it listened, answered and spoke from behind "Encendiendo motores…", which the rider reads as the app ignoring them. For the same reason "Ver en el mapa" re-checks itself on `routes:ready`: the catalog usually lands *after* the answer on exactly the path the feature exists for.
* **The mic owns a lane, and everything anchored to that corner respects it** (`--voz-lane`, 74 px). The FAB floats over every screen at the bottom right, which is where the map's "Mi ubicación" sat (they overlapped pixel for pixel and the mic won) and where Planear's sticky full-width "Buscar ruta" ends. The map's locate button and route banner offset by the lane; the planner's action bar reserves it as `padding-right`, because that bar sits mid-screen with a short trip and pins above the tab bar with a long one — moving the mic only ever clears one of the two.
* The overlay is built on `openSheet`, so `role=dialog`/`aria-modal`/Tab-trap/Escape/focus-restore/inert-shell are the app's one implementation (§1.1 R2/R5), and it always shows the spoken sentence verbatim — a device with no Spanish TTS voice, a loud bus, or a rider who cannot hear still gets the answer (§4.2). The pulse honours `prefers-reduced-motion`.

**Deliberately not built yet** (in rough order of what a daily rider would feel next): **dynamic launcher shortcuts** off the habit model, so a long-press on the icon offers "F19 ahora" with no speech at all — the cheapest remaining entry point, and the one that would make the feature reachable in one gesture; a **spoken itinerary** for `viaje`, which needs the router's answer summarised into one sentence rather than handed over as a screen; **"¿dónde recargo?"** off the bundled recarga POIs (§5.5.1), which is a weekly question rather than a daily one; and the **AppFunctions** wrapper (above) whenever the allowlist opens, which would remove the "abre TransMi Go" step entirely. None of these need new data — the assets and the engines are already in the APK.

**Verified offline for the capture changes above** (2026-08-17, no handset): the 33-utterance matcher battery passes against the real bundled index — including the new `F63`/`Z63` pair spoken as "efe/zeta/seta sesenta y tres" and the seseante variants — and the stop lookup resolves "tibanica", "islandia", "los laureles", "laureles" to the three new estaciones rather than to their paradero twins, with `banderas`, `calle 100`, `ricaurte`, `las aguas`, `portal las americas` and `el tunal` unchanged. The APK builds green with the plugin changes (`assembleDebug`, 16 MB). The partial-rescue, the "Ya terminé" button and the language ladder are reasoned from the `SpeechRecognizer` contract and compile-verified; **they are the next thing to confirm on a handset**.

**Pending**: on-device confirmation of Spanish transcription and of the live-bus ETA path — both need a rider speaking during service hours (the F19 test ran at 00:55, outside the route's 4:30 a.m.–10 p.m. window and outside the live API's ~05:00–23:00 one). The matcher, the six intents, the stop anchor, the ETA and every composed sentence are verified offline against the real bundled indexes and real shards (a 34-utterance battery incl. "en Banderas", "hacia Banderas", "a qué hora abre", "qué buses pasan por aquí", "cuáles rutas hay en la calle 100", "llévame al Portal Suba", "cuánto tiene mi tarjeta"; ETA with a fix, with no fix, with a named stop; stop answers at 08:00 and 23:40; closed-route / no-service-today / multi-window schedules), and in the browser build the tappable examples, the stop→chip→anchored-ETA loop and the planner handoff (destination seeded from the offline stop index, overlay closing itself afterwards) were driven end to end with **no backend, no GPS and no microphone**. The APK builds green; the recognizer is verified to open the mic and report `NO_SPEECH_DETECTED` correctly. **The mic-lifecycle fixes above are reasoned from the `SpeechRecognizer` contract and compile-verified, not yet re-confirmed on a handset** — the next device session should check, in order: hot-mic launch → overlay opens → "Escuchando…" appears and stays until spoken to; "Preguntar otra vez" twice in a row; and a mid-sentence pause of ~2 s not being cut off.

### 5.10 In-journey guidance — the plan does not end when the rider boards

The planner draws an itinerary and then goes quiet. A rider standing in an articulado with no signal and a phone in their pocket still has the only question that matters unanswered — *was that my stop?* — and the answer used to require surfacing the phone, finding the tab, and re-reading a map. Guidance turns the rendered plan into a **running** one: given where the rider is, it says what, if anything, should be announced right now.

Two rules shape the whole design. **Silence is the default** — a 40-minute trip produces roughly six utterances, `advanceGuide` returns `cue: null` on the overwhelming majority of fixes, and every cue is emitted at most once (`GuideState.emitted`). And the engine is **pure and synchronous** — no GPS, no clock, no network, no DOM; position comes in as a `RiderFix` and everything else is derived, which is what makes it drivable over synthetic positions along a real `trazado` and what lets both clients share it (§1.1 R2).

**The engine** (`client/src/services/journeyGuide.ts`). `buildGuideJourney` turns a `JourneyPlan` into a guidable one, `prepareGuide` precomputes each leg's cumulative path distances and projects every intermediate stop onto it once, and `advanceGuide(prepared, fix, state)` advances the journey by one position fix. The projection is a plain point-to-polyline one over an already-cut leg: `trace.ts` projects onto a route's whole `trazado` through an ordinal-keyed index built for *drawing* rides (§5.6.3), and that index does not expose what this needs.

| Cue | Fires when | Says |
|---|---|---|
| `walk` | start of a walking leg | "Camina 300 m hasta Portal Suba, vagón 1." |
| `board` | within 80 m along a ride's boarding point | "Sube al F19 en Portal Suba, vagón 1." |
| `prepare` | the alighting stop is genuinely next **and** ≤1200 m out | "Próxima: Av. Chile. Prepárate para bajar." |
| `alight` / `transfer` | within 150 m of the alighting point | "Bájate aquí. Transbordo al B74, vagón 2." |
| `arrived` | within 40 m of the end of the last leg | "Bájate aquí. Llegaste a Calle 45." |
| `offRoute` | three consecutive fixes >400 m from the plan | "Parece que te saliste de la ruta." |

* **The thresholds are the feature**, so they are named rather than inlined: `ALIGHT_RADIUS_M` 150, `ARRIVE_RADIUS_M` 40 (a bus needs warning before the doors; announcing "llegaste" 150 m from a front door is simply wrong), `BOARD_RADIUS_M` 80, `PREPARE_LEAD_STOPS` 1, `PREPARE_MAX_REMAINING_M` 1200, `STRAY_M` 400, `STRAY_FIXES_BEFORE_OFF_ROUTE` 3, `MAX_USABLE_ACCURACY_M` 100. They are the first thing to tune once this has been ridden in the real city.
* **`prepare` needs both a stop count and a distance.** At `PREPARE_LEAD_STOPS` 2 the cue names the alighting stop while a *different* stop comes first, which is a lie; at 1 it is a true sentence. But stop counting alone is not enough either — a ride with no intermediate stops has the alighting stop "next" from the moment it starts, so on a long direct hop the cue would fire the instant the rider boarded. Hence the 1200 m ceiling, roughly one troncal inter-station gap.
* **Boarding is checked before preparing to alight.** On a short leg one fix satisfies both, and being told to get ready to get off before being told to get on is nonsense.
* **Step selection only ever moves forward, and only by one.** Two legs of one trip often run within metres of each other, and a rider whose fix lands near a later leg must not be teleported past a transfer they have not made. Advancing also requires the current leg to be nearly done, so proximity to a parallel corridor is not enough on its own.
* **A fix too vague to place the rider advances nothing, and reports the progress that still holds.** Anything worse than `MAX_USABLE_ACCURACY_M` is held rather than acted on (§1), and `GuideState.along` carries the last usable position forward — reporting zero instead would jump the banner from "faltan 2 paradas" back to the boarding stop every time the phone lost sky.
* **A leg with no usable geometry ends the guidable journey rather than being skipped.** Splicing one out of the middle silently rewrites the trip: drop the walk between two rides and the engine announces a transfer where the rider was meant to get off and walk two blocks. Guiding as far as the geometry reaches and then falling silent is the honest form of the same limitation (§1).
* **Every cue is composed twice**, through the *same* `Phrasing` tables the voice answers use (`voiceAnswer.ts`, §5.9): `spoken` for the speaker ("Sube al **efe 19**", "300 **metros**", dashes voiced as pauses) and `written` for the screen ("Sube al **F19**", "300 **m**", the catalog's name untouched). A second set of tables would drift, and one string for both is the exact defect that shape exists to prevent — it is what puts "el efe 19" in front of a rider's eyes.

**What the router had to keep** (`router.ts`). `JourneyStep.stops` is stop *names* alone, and a name is not an identity — dozens of paraderos share one — so nothing downstream could turn it back into a place. The step now also carries `stopPoints` (name + código + coordinate, pushed in lockstep with `stops` so the two cannot drift out of order) and `fromCoord` / `toCoord`, because `path[0]` is the drawn shape and not the stop. All three are additive: `stops` is unchanged and every existing reader of it is untouched.

**The vagón is the thing no general-purpose transit app can say**, and it is also the easiest thing here to get wrong. `StationRecord.wagonByRoute` inverts the catalog's `wagons` map (wagon key → services) into route código → **the number printed on that platform's sign**, read from `station.vagonLabels` (§5.5.4). Two keys are dropped and both for the same reason — a rider sent to a platform must have something to look for: key `0`, the pool the catalog assigns to no vagón (§5.4.1), and every key the plano's plate count does not back. That leaves **92 of 142** stations able to name a vagón; on the rest the cue simply drops its vagón clause. The raw key is a letter that appears on no sign in any station, and "vagón 1" where the sign reads 3 is a real-world wrong answer (§1).

**The wiring** (`client/mobile/src/services/guidance.ts`). The engine is pure; this is the part that is not — it owns the GPS watch, the speech and the one piece of state a rider would lose if the app were killed mid-trip.
* **`watchPosition`, not a timer.** The OS already coalesces fixes; polling on top of it burns battery to learn nothing new.
* **Speech is fire-and-forget.** `speak()` resolves when the utterance *ends*, which can be seconds; awaiting it inside the fix handler would queue cues behind each other and announce a stop after the rider had passed it.
* **The journey survives being killed.** `GuideState` is plain JSON and is persisted whenever it actually moves — a cue, or a leg completed — never on every fix, which would rewrite localStorage a few times a minute for nothing. `resumeGuidance()` runs once `loadCore` has landed (the vagón lookup reads the catalog's station records) and restores a stored trip up to `MAX_RESUME_AGE_MS` **3 h** old: longer than any itinerary the router produces, short enough that opening the app next morning does not resume yesterday's commute. The read happens *before* the teardown, because `stopGuidance` clears the store — loading afterwards found nothing every time and every resume silently restarted the trip from its first instruction.
* **A denied position is terminal; a missing one is not.** `PERMISSION_DENIED` ends the journey and says so, because the watch will never produce a fix and a banner reading "guiando el viaje" over a trip that can never advance is the failure this branch exists to prevent. Everything else — indoors, in a tunnel, no sky — keeps the watch running and tells the rider why the instructions stopped rather than that the trip ended.
* **A fix's own timestamp is sanitised.** The Geolocation API specifies epoch milliseconds and Android WebViews have shipped builds that report uptime instead; taken at face value every fix then fails the 30 s freshness check and guidance sits there never advancing with nothing on screen to say why. A timestamp that is not plausibly a wall clock is treated as "now" — it arrived through the watch, so it is current by construction.
* **One snapshot, broadcast on the app's own bus.** Guidance outlives the screen that started it: the rider switches to Mapa to watch the trip, or relaunches mid-journey with no planner card on screen at all. Nothing owns it — the banner and the per-plan button both read `guidanceSnapshot()` and subscribe to `bus.on('guidance', …)` (§1.1 R2). Card subscriptions are unsubscribed when `renderPlans` replaces them, or ten searches leave ten dead buttons repainting on every fix.
* **Same trip means the same services, not the same object.** `isGuidedPlan` compares structurally: the planner re-renders its cards once the real walking legs land (§5.6.4), so the object a button closes over is not the one guidance was started with, and reference identity left one card offering to end the journey while another offered to start it.

**The banner** (`client/mobile/src/ui/guidanceBanner.ts`, mounted once from `main.ts`). Every cue is spoken **and** shown: a device with no installed Spanish TTS voice accepts `speak()` and says nothing (§4.2), an articulado is loud, and a rider who cannot hear still has to be told where to get off (§1.1 R5). It shows the `written` cue, never the spoken one. Between cues — which is most of a trip — it carries the live progress line ("Faltan 3 paradas" / "Te bajas en la próxima" / "A 240 m"), because a banner that is a ten-minute-old sentence reads as an app that has stopped working. It never intercepts taps, so it cannot swallow a press meant for the map underneath; its **"Terminar"** button is the one exception, because a journey that can only be ended from the card that started it is a trap. The arrival line lingers 30 s after the journey ends rather than being cleared in the same tick it was published — which showed "Llegaste a…" for a single frame.

**Deliberately not built yet**: guidance **while the app is backgrounded** — a WebView's `watchPosition` stops delivering when the activity is not foregrounded, so the honest form of this needs a foreground service and a notification, which is a native surface rather than a threshold to tune; a **map that follows the journey**, which the drawn plan (§5.6.3) already has every ingredient for; and **live-bus fusion**, using the same `routeEta` projection to say "tu bus llega en 3 minutos" while the rider is still walking to the stop. None of these need new data.

**Verified offline** (2026-08-23, no handset): the engine driven over a four-leg walk → F19 → B74 → walk fixture at 25 m increments emits `walk`, `board`, `prepare`, `transfer`, `board`, `prepare`, `alight`, `walk`, `arrived` in that order and once each, with spoken/written pairs differing exactly where they must ("efe 19"/"F19", "300 metros"/"300 m", "Cra. 13, Calle 45"/"Cra. 13 – Calle 45"); a 400 m-accuracy fix advances nothing and reports the held progress; three strays 2 km off the plan raise `offRoute` on the third and not before; a plan whose middle leg loses its geometry truncates to two steps rather than splicing. Against the real bundled catalog, 92 of the 142 stations with wagons resolve a printed vagón number and the rest correctly resolve none. **Pending**: a rider actually riding — the radii, and `prepare`'s 1200 m ceiling in particular, are calibrated from the network's geometry rather than from a trip.

### 6.1 Platform Goals & Action Items
* **Discovery Expansion**: ✅ Done — see §5.8 for the full reverse-engineered API surface across all six official-app hosts (catalog, live/Bodega, OTP planner, SITP, Firebase Storage, WebView-only), decoded via APK teardown (`research/README.md`).
* **Provenance Tracking**: Log exact source keys for all coordinate shapes and schedules.
* **Relay Panel**: Add monitoring UI dashboard for Colombia Relay health.
* **Test Suites**:
  * Unit tests: code normalization, coordinate simplification, resolver logic.
  * Integration tests: API contracts.
  * Smoke tests: Playwright-based testing for boot flow and search actions. Shipped so far: `tests/visual.spec.ts` (boot snapshot) and `tests/arcgis-layers.spec.ts` (§4.2 layer substitution + recovery).
  * **CI runs them against the real catalog, or not at all** (`.github/workflows/chromatic.yml`). `server/src/data/master_catalog.json` is Git LFS, and a plain `actions/checkout` leaves a 133-byte pointer: the server catches the parse error, boots with an empty catalog, and every catalog-fed layer draws zero features — so `arcgis-layers.spec.ts` failed on `expected > 0, received 0` on **every** run from the commit that added it (run 16) onward, while passing locally where the real 58 MB file sits on disk. The workflow now caches `.git/lfs` keyed on the pointer's own hash and runs `git lfs pull`: pulling through `checkout: lfs: true` instead would re-download 58 MB per push against a 1 GB/month LFS bandwidth budget and break the checkout once the quota went. A size check right after the pull fails the job with the reason rather than letting six layer assertions fail meaninglessly, the report is uploaded on failure (a red run otherwise says only "step failed"), and the job carries `timeout-minutes: 30` — `playwright install` stalled once and sat on the 6 h default before being cancelled.
* **A service stops where its own recorrido says it stops** (`GraphEdge.streetStops`, `routeServesStreetStops`). The router's rule that a troncal ride may only board and alight at an estación is right for a bus in the busway and wrong for everything that leaves it. It severed each padrón service at its first street stop — 14 of the catalog's 16, including `K86`, `M86`, `L81` and the new `F63`/`Z63` — leaving only station-to-station fragments reachable, so a trip to Tibanica - Primavera came back as an hour of zonal buses while `Z63` ran the same corridor in 19 minutes.
  * **Keyed on the recorrido, not on the label.** The catalog's vocabulary is TRONCAL / PADRON / ALIMENTADOR / URBANO, and it files a service under the nearest of those rather than describing it: `F63`/`Z63` arrive as `PADRON` but are run with **articulados duales**, new buses that work inside the busway and outside it. Gating on a label that is already an approximation is how the next service type breaks this again. A stop is in a route's recorrido because the bus stops there, which is the fact the gate actually needs; `busType: PADRON` stays only as a second signal, for a variant whose street stops are coded as stations. The post-search validator carries the same exemption, or it would discard precisely the plans the gate now allows.
  * Measured after the fix: Banderas → Tibanica **52 min zonal → 21 min on Z63**, Banderas → Islandia 50 → 16, Pradera → Laureles 55 → 25; pure-troncal trips unchanged (Polo → Portal Américas rides `F61`, Calle 76 → Portal Tunal rides `H15`). Also simulated with a TRONCAL-typed variant carrying one street stop mid-route — the shape a dual would take if the catalog ever files it as troncal rather than padrón — and it stays rideable end to end, with no code change needed when that lands.
* **A ride's guessed shape is drawn as a guess** (`JourneyStep.estimatedPath`, layer `journey-path-estimate`). `traceSource` has always said when a ride is part straight line (§5.7 #8), but the map drew those metres in the same solid colour as the measured ones — so `A547` from San Victorino to Tibanica appeared as a 15 km ruler laid across the city, which is a claim about where the bus goes. The untraced pieces now travel on the step as their own polylines and are drawn **dashed**, exactly as an unrouted walk is. Both the core line and the casing filter them out rather than drawing underneath, or the dashes would sit on a continuous ribbon and read as solid; the glow still spans the whole ride, so it remains one journey. Per piece, never per step: a ride is routinely part real and part straight (that `A547` leg is 15.7 km drawn, 14.8 km of it dashed in one piece), and a fully traced ride gains no features and renders exactly as before. The cable is exempt — its straight span between stations is its real shape, not an estimate of one.
* **Journey Planning**: Journey planning (origin/destination route calculation) explicitly within project scope. Time-dependent since §5.6.2 — the router plans for a departure moment and honours each route's operating windows.
